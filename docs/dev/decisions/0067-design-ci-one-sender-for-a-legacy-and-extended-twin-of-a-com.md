# Design CI: one sender for a legacy and extended twin of a compact call offer (draft 2026-10-20, not reviewed, not built)

**Status: built 2026-10-21 after the user chose Q-PC-COPIED-ID option A: default on, DEBUG control arm `test_copied_id_pc_pair=false` (CopiedIdTracker, AdvertTwinAds in StrangerNames.kt). V1 (iPhone 0x180A) and V2 (isLegacy on every extended-capable phone) remain open; not yet run on phones.** No wire change. The other answer to the same question is a Windows change (one advertising set per ID); this design is the Android-side option.

**Problem.** Windows sends the PC's compact call offer (kind 0, the iPhone form) as two advertising sets from two random addresses: a legacy set (Flags, the 16-bit UUID list with `0x180A`, the 128-bit UUID list with the compact UUID) and an extended set on the 1M primary and 1M secondary PHY with the same three ADs plus a 128-bit Service Data AD. `CopiedIdTracker` (StrangerNames.kt:244-274) sees one ID at two addresses at once, repeatedly, and marks it "More than one phone is using this ID"; the row's call button then opens the "Call anyway" prompt (MainActivity.kt:8145-8153). It happens only on phones whose call-list scanner also receives extended adverts: with Find PCs on, that scanner runs with `legacy=false` (`pc_scan: event=started ... extended_supported=true | legacy=false`), so an extended-capable phone hears both sets; a phone without extended scanning, or with `setLegacy(true)`, hears only the legacy set and never warns.

**What Android reports per sighting.** `ScanResult.isLegacy()`, `getPrimaryPhy()`, `getSecondaryPhy()` (`PHY_UNUSED` = 0 for a legacy advert), `getAdvertisingSid()` (`SID_NOT_PRESENT` = 0xFF for legacy) and `getDataStatus()` are public from API 26 (Android 8). A scan with `ScanSettings.setLegacy(true)` (API 26) reports legacy adverts only. The raw bytes come from `ScanRecord.getBytes()` (the advertising data, with the scan response appended for a legacy scannable advert). Below API 26 there is no extended scanning, so the twin never reaches the app. `BluetoothDevice.getAddressType()` is newer and not needed here.

**Rule (proposal).** For a compact **kind-0 call offer** only, the copied-ID tracker treats two addresses as one sender when all of these hold, and otherwise behaves exactly as today:
1. exactly two addresses carry the ID in the tracker's window, one whose sightings are `isLegacy() == true` and one whose sightings are `isLegacy() == false` with a non-zero secondary PHY;
2. byte-identical Flags AD, 16-bit UUID list and 128-bit UUID list (the compact UUID) in both; the 16-bit list must contain `0x180A` (the Windows sets carry it; whether an iPhone's does is V1);
3. the extended set may carry further ADs (the PC's Service Data); they are not compared.

A third address, two legacy or two extended addresses, any byte difference in those three ADs, or a 22-byte announcement (any version), a stream offer or a window offer: the warning works as today. Scope is kind-0 compact call offers because that is the only form a PC sends twice; Android phones send one set per role and iPhones only legacy.

**What an attacker gains.** The warning is a hint shown before the call; the handshake still checks the key bound to the ID (a copy cannot answer as the real phone), so the exemption can only hide the hint, never admit a wrong key. To use it, an attacker must copy a compact ID whose real sender is heard at exactly one legacy address, and add exactly one extended twin with byte-identical ADs including `0x180A`. Against a PC, which already sends both, any copy is a third address and still warns. Residual: a legacy-only sender whose legacy set includes `0x180A` (a PC heard by a phone that receives only its legacy set, or an iPhone if V1 finds `0x180A` there) can be shadowed by one extended twin without the hint. If V1 finds `0x180A` in iPhone adverts, the exemption must also require something the iPhone form cannot have, or not ship.

**iPhone interaction.** iPhones send the compact form as legacy only, so an iPhone is never one half of a twin and its own sightings are unchanged. The only interaction is the residual above (an extended copy of an iPhone's ID), which the `0x180A` condition closes if V1 holds.

**Test plan.**
- JVM (the tracker with the switch on and off): a legacy plus extended twin with identical ADs, alternating every 600 ms, does not warn; adding a third address warns; two legacy addresses warn; two extended addresses warn; a difference in Flags, in the 16-bit list or in the UUID list warns; a twin without `0x180A` warns; a 22-byte announcement twin warns; switch off: the twin warns as today.
- Phone: A15s with the PC compact-only and Find PCs on: no warning, the call starts from the row; M31 unchanged; a second Windows or Android test sender copying the PC's ID as a third set: the warning appears.

**Verification items.** V1: capture an iPhone's compact call offer with the raw observer: does its 16-bit UUID list contain `0x180A`? V2: that every extended-capable required phone reports `isLegacy()` and the secondary PHY correctly for both sets (A15s shown; S22, S24, Xiaomi, ASUS to check).
