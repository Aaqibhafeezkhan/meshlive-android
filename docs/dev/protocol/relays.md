# Relays

Part of the [protocol reference](README.md): relayed calls, multi-hop discovery, liveness and route withdrawal.

## Experimental relayed calls and multi-hop discovery (off by default)

DEBUG `test_relayed_calls`; otherwise the Settings > Experiments switch "Relayed calls (beta)" (honoured only while Manual video settings is on). Design: DECISIONS "Design C" (reviewed draft R14-R22, then an independent review recorded there). With the switch off every byte on air and on the link is unchanged: no consent bit, no relay flag, no reach page, no link-hello bit, and hop type 12 is rejected as unknown exactly as by old builds. Not yet tested on phones.

**Scope.** Call offers only, LE CoC and GATT only. Fixed-prefix (version 2) targets only, unless both this experiment and `test_rotating_ids` are on, in which case only role-0 RDI (version 5) targets are used (reach pages version 6, `SETUP` message 4; see "Rotating IDs and relayed calls" below). Streams, viewer requests, titles, names and Classic phones are not relayed this way. Cost cap 2 relays (DEBUG `test_relayed_calls_max_relays` 1..4); the wire carries 1..4.

**Capability bits (all other readers test only the bits they need).**

| Where | Bit | Meaning |
| --- | --- | --- |
| Call-offer `capabilitySummary` | 4 (`0x10`) | The target consents to be found through other phones. Never set on stream offers. |
| Call-offer flag `FLAG_RELAY_CAPABLE` (bit 1) | - | Set on an idle relay-helper's own cost-0 call offer, so callers can connect to its listener. Existing flag, new use on call offers. |
| Link hello transport mask | 4 (`0x10`) | "Understands `RELAY_SETUP` (hop type 12)". Signed by every endpoint with the experiment on, caller and helper. |
| Link hello of an active relay-helper | 6 (`0x40`) and `maxChildren` 1 | The existing call-relay capability and relay capacity, signed only while the helper accepts SETUP (not paused, not busy). The end-to-end hello is unchanged. |

**Hop record type 12 `RELAY_SETUP`** (a `BMS1` hop record like type 11; a reader rejects it as unknown unless its owner opted in). SETUP is accepted only as the first record after the link handshake (BMH2, or BMH3 with declared throwaways under Amendment CP) (and after a negotiated `BDO1` opening: with both experiments on a helper is a rotating call listener and its own `BDO1` comes first; a fixed-prefix helper never has one) of a listener that signed bits 4 and 6 and `maxChildren` 1, and only from a peer whose link hello signed bit 4. READY and FAIL are accepted only by the initiator that sent a SETUP, as the single reply, with a matching setup ID. The first record on a listener is dispatched in this order: `BDO1` when negotiated, then exactly one of type 11 (store-and-forward, when on), type 12 SETUP (helper), or type 4 (the endpoint handshake). Payload, big-endian:

```text
"BRS1" (4) | message (1) | body
  SETUP 1: target prefix (6) | budget (1, 1..cap) | remaining ms (4, 2000..20000) | setup ID (8, random per hop)
  READY 2: setup ID (8) | relays (1, 1..budget)
  FAIL  3: setup ID (8) | reason (1)
```

SETUP is 24 bytes, READY and FAIL 14. FAIL reasons: 1 no route, 2 busy, 3 child authentication failed, 4 timeout, 5 refused (policy, rate, battery), 6 loop. A decoder rejects other magics, messages, reasons, a zero budget, a budget above 4, a remaining time outside the range, `relays` outside `1..4`, trailing bytes, and a target equal to the zero prefix.

**Setup rules (hop-local; every SETUP, READY and FAIL is regenerated per hop).**

1. The caller connects to a relay-helper's call listener (the helper's own offer carries `FLAG_RELAY_CAPABLE`), completes the link handshake and requires the helper's link hello to show bits 4 and 6 and `maxChildren` at least 1. It sends SETUP with the cost it saw and the deadline left.
2. The helper checks, in this order: record format; its switch and pause state; busy (own call, ringing, exchange, stream, or already relaying); rate limits (3 SETUP per parent identity per minute, 10 per minute overall); parent identity is not itself and not the target (a `SETUP` for the helper's own ID answers FAIL 1, like a missing entry, so a consent-off phone is not revealed; FAIL 6 is for parent and child loops only); budget is within the cap; the table holds the target at a cost within the budget. Any failure answers FAIL (5 refused, 2 busy or 1 no route) and closes.
3. Budget 1, or a cost-1 entry for the target whatever the budget: connect to the target's own offer; its authenticated link identity must equal the target prefix (the existing cost-0 child admission). Otherwise pick the entry's next-hop relay, connect to its listener on the same bearer, require the bearer bit of its link hello, bits 4 and 6, `maxChildren` 1, a link identity equal to the prefix of the helper offer selected, and not the target and not itself (existing `PrivateCallRelayChain.childProblem` plus the prefix check), and send SETUP with budget - 1, a new setup ID and the deadline minus the elapsed time minus 1 s. When that allowance is below 2,000 ms the helper answers FAIL 4 (timeout) instead; every wait (connect, authentication, write, reply) is bounded by one monotonic deadline taken from the SETUP's remaining time.
4. READY travels back one hop at a time and carries the number of relays from that hop down to the target (its child's count + 1; 1 when it connected to the target itself). The caller records that number as the call's relay count. A relay that sent READY switches to the opaque copy mode, with exactly the record types, liveness and close rules of "Private-call relay chains". A child FAIL becomes a FAIL upstream with the same reason; a child that is silent past the deadline becomes FAIL 4.
5. The caller refuses a READY with `relays` above the budget it sent or above the cap, and a link that closes or is silent past the deadline plus 2 s (reply grace for the last hop's cleanup, not extra setup time). READY's relay count is a relay's claim, not proof of topology. The caller also requires the first hop's authenticated link identity to equal the prefix of the helper offer it selected when the hop answers with a real key (Amendment CP: a hop that declared a throwaway is not bound). A closure before READY is reported as FAIL 4, not FAIL 1.
6. After READY the chain tears down unless the end-to-end handshake crosses within 10 s and the callee's first end-to-end content record (its Ringing answer to the Invite) within 20 s; heartbeats and caller-originated content do not count. One absolute deadline (the SETUP's remaining time) also covers a helper's connect, authentication and wait for the next hop: on expiry it answers FAIL 4 and closes both links. After child authentication a helper also refuses a child that is its parent or the target's own parent (`PrivateCallRelayChain.parentProblem`). A helper also closes a connection that has not completed the link handshake and delivered its first record within 20 s of being accepted. A callee declines a relayed incoming call that rings 60 s without an answer; it counts the call as relayed when its authenticated link peer differs from its authenticated call peer, whatever relay count the Invite states. A second type 12 record on a running chain is a violation and closes both links.
7. A relay holds one parent and one child. The budget strictly decreases and ends at the authenticated target, so a chain is a loop-free path of at most the cap.

**Reach table rules.** Entries come only from the scanning phone's own sightings. A direct sighting needs announcement version 2, `FLAG_PRIVATE_CALL_AVAILABLE`, route cost 0, the consent bit and an LE transport. A page entry needs relay prefix, target and via from a decoded reach page, `cost + 1` not above the cap, a target that is not this phone, and `via` not equal to the first two bytes of this phone's prefix (poison reverse). Admission, caps and eviction are exactly the admission list in DECISIONS "Design C" (two sightings at least 2 s apart from one advertiser address; 8 new targets per 30 s; 4 per relay prefix; 32 entries; refreshed-20-s and used-in-success entries are protected; failure skip 30 s, FAIL-no-route drop 5 min). Ages only grow: a direct sighting has age 0 when seen; a learned entry adds the local time since its page; entries older than 62 s, or not refreshed locally for 30 s, are dropped; after a route is lost, worse-cost entries for the target are ignored for 10 s. The table is never persisted and release builds never log it. A relay advertises its own direct entries (a consenting target it hears itself) as soon as admitted, and neighbour-learned entries only after 5 s and only while that neighbour's relay is also heard in a connectable offer with `FLAG_RELAY_CAPABLE` (the consistency check applies to learned entries only, so a target that consents but does not help is still found), best (lowest cost, then lowest age, ties shuffled) first, at most 4, and stops while paused or busy.

**Reach page** (manufacturer data `0xFFFF` of a legacy, non-connectable, scannable set that carries the app's service UUID; 250 ms interval, one page per second):

```text
version 4 (1) | relay prefix (6) | relay flags (1): bit 0 LE CoC, bit 1 GATT, bit 3 idle; other bits zero
| page (1): index (high nibble) | count (low nibble, 1..4)
| entries (1..2) x ( target prefix (6) | cost (high 3 bits, 1..4) | age (low 5 bits, 2 s units) | via (2) )
```

18 bytes (one entry) or 27 bytes (two), 31 bytes with the advertising-data header. Old scanners reject it (length is not 22). A decoder rejects an index at or above the count, a count outside 1..4, no entries, cost 0 or above 4, a target equal to the relay prefix, duplicate targets in a page, and reserved relay-flag bits. A phone starts the set only when the advertising-set probe found at least two free sets (`TitleAdvertiser` precedent). A scanner reports reach pages before its per-address duplicate filter, as for title pages.

**Identities on relayed-call edges (Amendment CP, built 2026-10-27; `test_relayed_pseudonymous_edges`, on; DECISIONS Design C "Amendment CP").** Every relay edge (caller to helper, helper to helper, helper to target) runs BMH3, never BMH2 while pseudonym mode is on (the choice is made once per duty, so no retry falls back to BMH2). Its initiator sends no contact tag and presents a throwaway that declares `PSEUDONYM`, fresh per connection and never the end-to-end attempt key; nothing is pinned or admitted. A hop that answers with a real key must open the selected offer (the helper's own offer, or the target's); a hop that declared a throwaway is not bound, and the caller's end-to-end check authenticates the target. The first record of a link with a throwaway on either side may be `SETUP` (on a helper) or an end-to-end handshake; store-and-forward is refused and a verification-code link never carries `SETUP`. A rotating helper answers `SETUP` message 1 with FAIL 5. The per-parent limit is keyed on the link's remote address for a pseudonymous parent (an unknown address shares one bucket); the overall limit and one relay at a time stay. A responder skips the `BDO1` link opening only when it presented a throwaway itself. Experimental (`test_relayed_contact_helper`, off): a caller that recognises the helper as exactly one contact tags the helper's own offer and runs real/real with the opening check (the helper then learns who calls). A relay can sit in the middle of a stranger call (no tag): the caller stays protected by the reveal binding, but a callee that accepts reveals itself to whoever holds the call, which may be the relay; a target therefore declines any relayed call unless its relayed calls and relay consent are both on, and rings a relayed stranger call only with `test_relayed_stranger_calls` on (default on within the experiment), labelled "via a phone nearby". A strict Contacts-only target is unreachable through relays.

**Identity.** None of this changes who authenticates whom: the caller still requires the end-to-end peer's prefix to equal the target it selected (and the full fingerprint for a verified contact); the helper's link identity, the target's link identity and the relays' hellos are checked as above. A reach page, a table entry and a SETUP record are hints and requests, never proof of identity.

**Rotating IDs and relayed calls (reach pages version 6; DEBUG `test_relayed_rotating`, default on while both experiments are on; `=false` restores the old exclusion).** Relaying must not spread the stable prefix, so with both `test_rotating_ids` and `test_relayed_calls` on a phone neither sets nor reads a fixed-prefix reach entry and keeps everything in role-0 RDIs. The rules are those above with these substitutions:

1. *Offers.* A relayed-call phone's cost-0 call offer is version 5 (role-0 RDI). The consent bit (capability bit 4) and the helper flag (`FLAG_RELAY_CAPABLE`) are set on it exactly as on a version 2 offer (two more stable bits, RV14); "target" and "helper" below mean a version 5 offer carrying them. A rotating phone keeps two tables, one per population: its own pages and helper offers are version 5 and version 6 only (it never advertises a fixed-prefix target), while as a caller it may still use a fixed-prefix helper and target like any phone it can call directly (the link is then checked by prefix, as before). A non-rotating phone cannot see version 5 offers or version 6 pages. A route never mixes the two: a version 5 `SETUP` goes only to a version 5 helper.
2. *Reach page version 6.* The version 4 layout (18 or 27 bytes) with `version 6`: the relay field is the relay's own **current role-0 RDI**, each target field is the target's role-0 RDI as the relay scanned it, and `via` is the first two bytes of the next hop's role-0 RDI (the target's own RDI for cost 1). Old scanners and version-4-only readers reject it (version byte). Vectors: relay `44e69c0a7a7d`, flags CoC + idle, one entry (target `fecba64983fd`, cost 1, age 3 units, via `fecb`) = `0644e69c0a7a7d0901fecba64983fd23fecb` (the same bytes with version 4 are the fixed-prefix page); two entries (page 1 of 2) = `0644e69c0a7a7d0912fecba64983fd5fa1b2974ae410ea9120974a`; `SETUP_RDI` for target `974ae410ea91`, budget 2, 20,000 ms, setup ID `0102030405060708` = `4252533104974ae410ea910200004e200102030405060708` (`SETUP` is the same with message byte `01`). A relay with both experiments on advertises version 6 pages only, never version 4 (that page would carry its fixed prefix), and none while a Visible-by-handle window runs or during the boundary silence (no page names an ID that no offer carries); a relay without rotating IDs keeps version 4 and never lists a version 5 target.
3. *Table.* Each population has its own table, so a version 2 prefix and a version 5 RDI never collide. A version 6 entry's age and cost rules, admission (two sightings two seconds apart, 8 new targets per 30 s, 4 per relay, 32 entries) and expiry are unchanged. Poison reverse compares `via` with the first two bytes of the receiving relay's **current and previous** RDI. **The whole table flushes at the phone's own boundary** (RV6) and the reach set restarts on a new set with the new RDI after the usual silence; learned entries again need two sightings and five seconds before they are advertised, so relayed reach is empty for up to about 30 s per hop after each boundary. A cached first-hop offer (older than 30 s or from a previous epoch) is never dialled, and a setup that straddles a boundary either completes inside the callee's 60 s pin or fails cleanly and is retried (RD7: the pin lasts 60 s after the callee's boundary; no extra age rule is applied, which fails safe).
4. *`SETUP` message 4 (`SETUP_RDI`).* Identical to `SETUP` (24 bytes) except that the target field is a role-0 RDI and the target is looked up in the rotating table; `READY` and `FAIL` are unchanged. A reader accepts message 4 only when rotating IDs and relayed calls are both on (`RelaySetupCodec.decode(acceptRdi)`) and rejects it as unknown otherwise. The caller sends it only to a first hop it selected as a version 5 helper offer; each helper regenerates it for its next hop as message 4 when its table entry is version 5.
5. *Hop checks.* Every link to a version 5 helper or target is checked with the selected offer's `BDO1` (link hello bit 3, role 0), replacing the prefix comparisons of the setup rules: the caller's link to the first helper must open the helper offer it selected; a helper's link to its next hop opens the next relay's offer it selected (budget above 1) or the target's own offer (budget 1 or a cost-1 entry), and the existing relay-capacity checks (`childProblem`, `parentProblem`) apply to node IDs only. The caller's end-to-end check is the callee's `BDX1` OPENING over the chain (above), which must open the RDI the caller selected from the reach entry; the pin is taken when the relay's connection to the callee is accepted. A target RDI older than 62 s at the caller, or learned before a boundary the callee has already passed by 60 s, fails the check; the next attempt uses a fresh entry.
6. *Privacy.* No relay advertises or forwards a stable identifier: reach pages, helper offers and `SETUP` carry only the current epoch's RDIs. Each relay on a chosen path still learns the target's RDI, its adjacent link identities and both signed endpoint hellos (C2). A passive observer near a relay learns "a rotating call-ready phone is within N hops of this relay" for one epoch; contacts holding leases can recognise the RDI in a page exactly as in a direct sighting, which lets them see "Alice via 1 phone" before connecting (unconfirmed).

**Debug lines (DEBUG builds; release builds log none of the table):** `rotid_open: role=relay_hop|call_endpoint | result=`, `relayed_calls: enabled= | help= | consent= | maxRelays= | require=`, `relayed_reach_table: entries= | rotating_entries= | pages= | offers=` (`entries` is the fixed-prefix table, `rotating_entries` the role-0 one; with both experiments on the relayed rows live in the second), `relayed_setup: role=caller|helper | result=ready|failed|refused|accepted|invalid|pre_setup_timeout | budget= | relays= | reason=`, `relayed_helper: state=RUNNING|PAUSED | reason= | scan= | relaying=` (also `reach_pages status=`/`skipped` and `relay_ended`), `relayed_call: ringing_cap_declined`.

### Draft: on-demand route seek (Design OR; revision 3 after reviews 1 and 2, DEBUG prototype only, Experimental)

Design, reasons and the review tables: DECISIONS "Design OR: on-demand relayed route query". DEBUG launch extras only, off by default and effective only with `test_relayed_calls`: `test_relayed_on_demand` (arm O) and `test_relayed_on_demand_keep_tables` (arm B: tables and pages kept, searches answered too). No release or Advanced setting exists. With both off nothing below exists: message 5 is rejected as unknown exactly as today, `RELAY_SEEK` is never sent, and helpers scan and advertise reach pages as above.

**Scope.** Every participant runs relayed calls, rotating IDs and BMH3. Targets are version 5 role-0 call offers only. Link identities follow "Identities on relayed-call edges" (Amendment CP) when `test_relayed_pseudonymous_edges` is on; with it off, helpers and targets must have BMH3 pseudonyms off (a phone with pseudonyms on neither helps, pause reason "pseudonymous toward strangers", nor is sought) and the table below applies. The caller's own pseudonym setting is never restricted. A Contacts-only phone neither helps nor can be reached through a helper (helpers send no contact tag). Fixed-prefix (version 2) targets, compact (iPhone) targets and BMH2 links are out of scope.

**Helpers in on-demand mode** run no reach-table scan and advertise no reach pages. Their own cost-0 call offer, the consent bit, `FLAG_RELAY_CAPABLE`, the link-hello bits 4 and 6 with `maxChildren` 1, and the helper pause rules are unchanged. In the keep-tables arm a helper does both.

**Handshakes with CP off** (every link of a searched route is BMH3 R_FIRST; with CP on the three link rows are CP's throwaway-to-pseudonym edges without hop binding, and the end-to-end row is unchanged):

| Link | Initiator presents | Responder presents | Initiator checks before going on |
| --- | --- | --- | --- |
| Caller to first helper | a fresh throwaway, random tag (an explicit "toward a helper" option: the helper's own offer has route cost 0) | real key, `OPENING`, `RELAY_SEEK` | the `OPENING` opens the selected helper offer; `RELAY_SEEK` bit 0; link-hello bits 4 and 6, `maxChildren` 1 |
| Helper to next helper | the helper's real key, random tag | real key, `OPENING`, `RELAY_SEEK` | as above, on the same bearer |
| Last helper to target | the helper's real key, random tag | real key, `OPENING` | the `OPENING` opens the sought ID |
| End to end (through the chain) | the caller's real key, contact tag bound to the sought ID | real key | the expected contact's full node ID, then the `BDX1` opening of the sought ID |

The helper's onward links use BMH3, the same implementation as Amendment CP. Loop freedom does not rely on node IDs (CP's throwaways are fresh per link): every phone on a path, the caller included, holds a phone-wide relay-duty reservation and refuses a second request.

**BMH3 extension type 5 `RELAY_SEEK`** (draft, registered in the BMH3 extension table; non-critical, an older BMH3 build skips it). Allowed only in a responder block (msg2, msg4) of a **link** handshake, pseudonymous or not; value 1 byte, a feature bitmask: bit 0 `SEEK` version 1, bit 1 reserved (OR-T proof), bit 2 reserved (OR-C probe), other bits zero and ignored. Signed only by a call listener that would admit a `SEEK` now (helping, not paused, not on duty, budgets not exhausted). A responder block with `OPENING` (90), `BUILD_TAG` (5) and `RELAY_SEEK` (4) behind a 13-byte `PAD` fills the 112-byte area exactly. A `SEEK` is sent only to a peer whose authenticated responder block has bit 0.

**`SEEK`: hop type 12 message 5** (`BRS1`, big-endian; accepted under the first-record dispatch and link-hello conditions of `SETUP`, only on a link where this phone signed `RELAY_SEEK` bit 0; with CP off, never from or to a pseudonymous peer):

```text
"BRS1" (4) | message 5 (1) | budget (1, 1..2) | remaining ms (4, 2000..20000)
| setup ID (8, random per hop) | nonce (8, random per request, not all zero) | token (6)
| skip count (1, 0..3) | skip count x RDI prefix (2)
```

33 to 39 bytes, inside one `BMS1` hop record, never on air. `READY` and `FAIL` are the existing messages 2 and 3; reason 6 (loop) is never sent for a search. A decoder rejects a budget outside 1..2, a remaining time outside the range, an all-zero nonce, a skip count above 3, duplicate skip prefixes and trailing bytes.

**Token** (no secret; a lookup hint, never identity proof):

```text
token = SHA-256("BluetoothVideoMesh/RelaySeek/Token/1" || 0x00 || nonce (8) || RDI (6))[0:6]
```

`RDI` is one role-0 rotating ID of the target. The caller's **primary** selector is the RDI of the epoch of a direct recognition of the contact in the current epoch, else of the centre `myE + skew` of `RecognitionTable` (only days whose key the lease holds; nothing after revocation or pruning). The **neighbour** selector is the adjacent epoch on the side of the nearer boundary, used only within 120 s of the target's predicted boundary, and never for a lease older than 14 days. Vectors come with the code (JVM test).

**Caller rules.**

1. The attempt ends 45 s after the tap (`RELAYED_CONTACT_WAIT_MS`, as in the proactive arm). From the tap the caller holds its own relay-duty reservation: it refuses requests, stops signing `RELAY_SEEK` and withdraws its helper flags at its next offer restart.
2. A contact whose own call offer is heard is called directly. Otherwise a low-latency scan keeps running during the search; the contact's offer appearing before a `READY` closes the search link and starts a direct call.
3. First hops: version 5 helper offers from the caller's own scan (`FLAG_RELAY_CAPABLE`, the call's bearer), ordered by the helper that last reached this contact in the current epoch, then by signal (`test_relayed_seek_order`), at most `test_relayed_seek_first_hops` (default 3). Each is revalidated at dial time: older than 10 s means a refresh scan of at most 1 s charged to the attempt, or skip.
4. Rings, stopping at the first `READY`: ring 1 budget 1 with the primary selector to each first hop; ring 1b (only in the boundary window) budget 1 with the neighbour selector; ring 2 (only with a relay cap of 2) budget 2 with the primary selector and a skip list of the first two bytes of the RDIs of the first hops that answered `FAIL` 1 in ring 1. With `test_relayed_calls_require=2` rings 1 and 1b are skipped. A first hop that answered `FAIL` 2 or 5, failed its binding, lacked `RELAY_SEEK` or closed without an answer is not asked again in this attempt; a close is remembered for 60 s.
5. A request is sent only if `min(20,000, attempt end - now - 2,000) - test_relayed_seek_connect_ms` (default 4,000) is at least 9,000 ms for budget 1 or 14,000 ms for budget 2; it carries `remaining = min(20,000, attempt end - now - 2,000)`. The caller counts requests and physical dials (each connect attempt, PHY or transport retry) per attempt and stops at `N(S + 1)` requests and `2N(S + 1)` dials (`S` = 2 inside the boundary window, else 1).
6. `READY` and everything after it follow setup rules 4 to 7 unchanged; the end-to-end contact tag and the `BDX1` opening are bound to that request's RDI.
7. After "Can't find", the caller backs off its automatic retries for that contact (30 s, doubling to 120 s; reset when the contact is heard directly or a new helper appears). A user's tap is never blocked by the backoff (DECISIONS "Who carries the risk"). `test_relayed_seek_no_backoff` (DEBUG) disables it for the attack cell.

**Helper rules (in order).**

1. Format, switch, pause, scope, parent checks, budget within 1..2 (a plain `SETUP` handled as a search is clamped to 2): otherwise `FAIL` 5 and close.
2. A `FAIL` cached for the same nonce, token, budget and skip list within 60 s (64 entries) is re-sent with this request's setup ID, without work. A `READY` is never cached.
3. Take the phone-wide relay-duty reservation atomically (searching, connecting, waiting, relaying and teardown; released after both links close); already held: `FAIL` 2.
4. Budgets over rolling 10 minutes, scaled by `test_relayed_seek_budget_scale` (default 1): search duty at most 60 s, on-demand scanning at most 30 s, at most 12 outgoing dials and 12 outgoing handshakes, at least 10 s since the end of the previous search; a scan start only while at least two starts remain in the app's 30 s window for the owner. Duty runs from accepting the request to sending `READY` or `FAIL` (plus up to 2 s of teardown after `FAIL`); scanning is on-demand scan wall time; a dial is each connection attempt including PHY and transport retries and alternate addresses; a handshake is each outgoing link handshake. Only work done is charged; the duty and scan time of a search that ends in `READY` are credited back. If the remaining duty budget is below the request's minimum (9 s for budget 1, 14 s for budget 2): `FAIL` 5, no radio work. While any budget is exhausted the listener stops signing `RELAY_SEEK`; after 60 s of exhaustion its next offer restart omits `FLAG_RELAY_CAPABLE` until recovery.
5. Fix one monotonic deadline `D = now + min(remaining, remaining duty budget)`. Every later step uses what is left of `D`; a parent that closes cancels the scan, dials and child at once; up to 2 s of reply grace after `D` may be used for cleanup, never for new work.
6. In the keep-tables arm: test the token against the table's version 5 entries; only a fresh entry with cost at most the budget and not on the failure skip list (`setupRoute` semantics) continues as setup rule 3 with a regenerated message 4 `SETUP` (remaining time at most 20,000 ms by construction); otherwise continue with step 7.
7. Offers heard in the last 5 s from any scan this phone ran anyway are used first; otherwise scan at low latency for at most `test_relayed_seek_scan_ms` (default 3000), shortened so that the onward minimum fits (6 s for the target link; for children `test_relayed_seek_connect_ms` + 9 s). An offer matches when it is a version 5 cost-0 call offer with `FLAG_PRIVATE_CALL_AVAILABLE`, the consent bit, an LE transport equal to the link's bearer and `token(nonce, RDI)` equal to the request's; this phone's own current or previous RDI never matches. After the first match the scan continues for at most 1 s more, collecting at most 3 distinct advertiser addresses with the matching RDI (heard twice first, then strongest). The same scan records at most `test_relayed_seek_fanout` (default 2) version 5 helper offers on the same bearer, not this phone, whose RDI does not start with a skip prefix. The scan result is kept for 10 s.
8. Matches: dial the collected addresses in order; with CP off the target's `OPENING` must open the matched RDI and an identity failure moves to the next address; with CP on the first address that completes the handshake is used. Then setup rule 3 continues with budget 1.
9. Budget 2 and no target link: for each recorded helper, revalidated at dial time (older than 10 s: refresh within `D`, the scan budget and the start quota, or skip), and only if `D - now - test_relayed_seek_connect_ms` is at least 9,000 ms: dial it (handshake table), require `RELAY_SEEK` bit 0, and send a regenerated `SEEK` with budget 1, a new setup ID, the same nonce, token and skip list, and remaining `D - now - 1,000` ms. Any child failure (`FAIL` 1, 2, 4 or 5, an identity failure, no `RELAY_SEEK`, a close) moves to the next child. A child `READY` is passed upstream as in setup rule 4.
10. With nothing left: `FAIL` 1 if no target or child was reached or any child answered 1; `FAIL` 4 if `D` ran out; otherwise the last child's reason. Budget 1 and no match: `FAIL` 1.
11. Every physical attempt counts against a per-request cap of 3 dials and the phone-wide dial budget.
12. Nothing about a search is advertised, persisted, or logged in release builds. `FAIL` 1 never counts against a parent; a parent is refused for 5 minutes only after a protocol violation (a malformed record, a second type-12 record, a deadline overrun), keyed on its link identity, or on its remote address for a CP throwaway.

**A plain `SETUP` (message 4) to a helper in on-demand mode** (a proactive caller) is handled as a search for its single RDI with the same reservation, budgets, deadline and collection rules, budget clamped to 2, comparing IDs directly instead of tokens, without a skip list.

**Target-side consent.** Unless relayed calls are on and its current "Let phones nearby relay calls to me" setting is on (whatever its last advert said), a target closes unanswered a first end-to-end handshake record that arrives over a link whose peer signed the call-relay mark (link-hello bit 6), so no identity leaves it, and, as a second check, declines before ringing every incoming call that is relayed (authenticated link peer differs from authenticated call peer). Proposed for `SETUP` routes too.

**Copied target IDs.** An advertiser address whose link failed the opening of the sought ID is not dialled again for that epoch by this helper.

**Reserved: client puzzles (OR-PZ, proposed, not built).** Before any user-facing build, a helper that has used half of any budget in its window answers a new request with a puzzle bound to the link and admits it only with the solution, the difficulty doubling with each further quarter used, so a spammer, not the genuine caller, pays for load (DECISIONS "Who carries the risk"). Wire to be specified with its review.

**Bound.** Depth at most 2 relays on the wire. With `N` first hops, fan-out `F` and `S` budget-1 rings, an honestly executed attempt makes at most `N(S + 1)` first-hop and `NF` second-hop requests and `2N(S + 1) + 3N(S + 1) + 3NF` physical dials (63 with `N` = 3, `F` = 2, `S` = 2), before the 45 s deadline and the minimum-allowance rule prune it. A dishonest helper can exceed its share; each phone's own budgets bound what it spends.

## Lifecycle, liveness and route withdrawal

Lifecycle and media share ordered endpoint-content sequence space. Pause clears queued media and sends authenticated `PAUSED` every two seconds. Resume queues `LIVE` before media. End clears queued media, queues and flushes `ENDED`, then closes the link. Repeated `PAUSED` is intentional liveness. An advertised paused hint is untrusted and cannot replace the authenticated lifecycle record.

Each parent acts first on immediate socket EOF/read/write failure or GATT disconnect; it closes only the affected child link. Authenticated version-1 keepalive has a one-byte payload and terminates at the immediate parent, which independently generates its own upstream keepalive.

| Link | Heartbeat period | Silent-link timeout |
| --- | ---: | ---: |
| RFCOMM / CoC child | about 1 second | 8 seconds |
| GATT direct viewer or receiver-node child | about 1 second | 6 seconds |

The receiver writes its keepalive once per pass of its control loop, and that loop wakes at least once a second to send link reports; the 2-second constant (`receiverHeartbeatIntervalMs`) only bounds the wait. The period has been about 1 second since link reports were added, and the timeouts were measured with it; a keyframe request adds one more keepalive. Restoring 2 seconds would save about 34 bytes and one write per second per child link and would halve the number of keepalives inside each timeout, so it is not done.

EOF/callback/write failure takes precedence over the timeout. Matched GATT kill/rejoin tests established that callbacks and forwarding writes can leave a stale direct-viewer session; these heartbeats bound that immediate silent link. They do not recreate the retired graph-wide metrics stream. No queue, bitrate, FPS, drop, decoder, thermal or liveness metric crosses more than one immediate link or changes the broadcast encoder target.

A receiver's hop-local link report travels in the same heartbeat type and describes only the link from its adjacent sender; it is never forwarded (a call relay replaces it with a version-1 heartbeat).

| Version | Payload |
| --- | --- |
| 1 | `01` (liveness only) |
| 2 | `02`, arrival-train kbps (2), flags (1: bit 0 link late), added delay ms (2): exactly 6 bytes |
| 3 (2026-10-09) | the version 2 fields with version `03` (flags bit 1: delivery only), then received media bytes (4) and receiver link clock ms (4): 14 bytes |

Received media bytes count, in arrival order, the media this receiver has taken off the link since it started, modulo 2^32: each whole media packet's payload and, for experimental call video fragments, each fragment's chunk bytes when the fragment arrives (never the reassembled packet again). These are exactly the bytes its sender counts as written, record by record (display-rotation packets are excluded in calls). The link clock is milliseconds since this link started at the receiver, modulo 2^32, at the arrival of the last counted byte (not when the report was written, and not device uptime). The sender maps that byte offset to its own write time for it: the one-way delay minus its rolling 2-minute minimum is the queue in front of the media, and the return path's delay is not part of it. Counters that go backwards are a peer reset, not a 2^32 wrap. Before its first counted byte a receiver has no arrival to report, so it sends version 2 (the version-1 hello already announced version 3); a sender ignores a version 3 report that counts zero bytes, which older endpoints send as "0 bytes at 0 ms" and which would otherwise time the first media from the link's start, the whole ring included. Flag bit 1 marks a report sent only to refresh delivery: its lateness fields repeat the last full report and must not feed a lateness trend.

Version 1 and 2 parsers accept only these exact payloads and close the link on anything else, so version 3 is sent only to a hop known to accept it. Version 3 and later parsers read the first 14 bytes, ignore flag bits 2-7 and trailing bytes (up to 64 bytes in all) and reject shorter payloads, so a later version never closes a version 3 link. On a direct private-call link each current endpoint sends one version-1 heartbeat after the endpoint handshake to say it accepts version 3; earlier endpoints never send version 1 on a direct link and take it as liveness. An endpoint sends version 3 only once the call and its relay-hop count are known and the call is direct, so a call relay never receives it. A stream parent has no message that older viewers accept for such a hello (they reject heartbeats from a parent), so stream viewers send version 3 only under the experimental stream delivery reports, which require every phone in the stream to run that build. A capability bit in the signed hello would carry this negotiation for streams too; it needs its own protocol and security review.

Decoder recovery seals an empty `KEY_FRAME_REQUEST`; each viewer-forwarder authenticates it and creates the equivalent upstream request, coalescing it with local recovery. Terminal acknowledgement works similarly. A parent waits up to two seconds for its active child before acknowledging upstream, so a missing child cannot block the chain indefinitely. The blind-relay harness instead forwards endpoint keyframe control as opaque `BME1`.

An overloaded immediate parent sends authenticated one-byte `ROUTE_CONTROL`, reason `LOCAL_CAPACITY=1`, waits up to four seconds for the matching `ROUTE_CONTROL_ACK`, then closes that child link. It neither ends nor changes the source stream. The receiver suppresses the exact node-prefix/stream-token/transport route for 30 seconds and returns to discovery; it does not repeat ordinary same-route reconnect. Triggering queue/cadence measurements remain private to that parent.

Explicit `ENDED` returns the receiver to discovery without retrying that broadcast. Unexpected loss preserves the last frame and searches for the same logical broadcast token and codec until the user leaves. A replacement can be the original source or another viewer-forwarder/transport, but its adjacent identity must match the announcement and its authenticated source must match the originally accepted source. The replacement reauthenticates and starts at a fresh keyframe; recovery is break-before-make. A recovery request uses six bytes for the failed immediate-node prefix that ordinary viewer requests do not need, keeping the discovery body 22 bytes. That hint can prioritize/gate attempts and never replaces authenticated identity/liveness.
