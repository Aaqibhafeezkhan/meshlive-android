# Bluetooth media protocol

For implementers and security reviewers: the normative wire formats and security rules. How the pieces fit together is explained in [ARCHITECTURE.md](ARCHITECTURE.md). This reference defines the current authenticated application protocol over Classic RFCOMM, LE L2CAP CoC and LE GATT. All integers are network byte order. Plaintext compatibility and silent transport fallback are rejected.

## Security layers and participants

```text
Bluetooth transport: RFCOMM, LE CoC or bounded GATT byte stream
  BMH2 adjacent-link handshake: persistent signed identity + ephemeral P-256 ECDH
  BMS1 hop records: directional AES-256-GCM, ordered per Bluetooth connection
    BMH2 endpoint handshake: separate signature/KDF domain, opaque to a blind relay
    BME1 endpoint content: stream/media, lifecycle, timing and authenticated controls
    BFG1 forwarded-stream grant: source ID + stream ID + current media-open key
    BGK1 static group epoch key: independently wrapped for each final receiver
```

Direct streams use both handshakes. A direct stream or private call has one peer endpoint session. A normal viewer-forwarder is an admitted viewer and can decrypt for local playback. With forwarding enabled, it authenticates one child using fresh link and endpoint handshakes, wraps the current media-open key in `BFG1`, then copies unchanged upstream `BME1` ciphertext. The child checks the grant's source/stream IDs against its first authenticated mesh envelope and independently opens the shared media sequence. This is immediate-parent admission; the source does not maintain a graph-wide endpoint list, and forwarding adds no second codec or media decrypt/re-encrypt pass.

A forwarding chain has a separately authenticated endpoint session for each adjacent parent/child pair. Child keyframe requests and terminal acknowledgements are authenticated locally and regenerated toward the upstream parent, because adjacent sessions use different directional keys. Queue, decoder, thermal and bitrate telemetry is never forwarded graph-wide.

The hidden blind-relay harness has only adjacent-link keys and cannot open endpoint media. Its branched group mode creates one source `BGK1` epoch key and wraps it in an independent endpoint session for each final receiver. It can copy one shared encrypted media record to multiple children. This is distinct from the trusted normal viewer-forwarder; static key distribution does not implement live revocation or re-key.

## Identity and key agreement

- Android's persistent P-256 ECDSA signing key lives in Android Keystore. Windows uses a non-exportable named CNG user key.
- The node ID is the first 16 bytes of SHA-256 over the identity key's DER SubjectPublicKeyInfo.
- Each handshake creates fresh ephemeral P-256 ECDH keys and a 32-byte random nonce. The signed hello binds role, node ID, identity key, ephemeral key, nonce and transport/codec capabilities.
- Initiator/responder derive 64 bytes through HKDF-SHA-256, split into directional 32-byte AES keys.
- Link signatures and KDF use `BluetoothVideoMesh/LinkHandshake/1` and `BluetoothVideoMesh/LinkSession/1`.
- Endpoint signatures and KDF use `BluetoothVideoMesh/EndToEndHandshake/1` and `BluetoothVideoMesh/EndToEndSession/1`. A valid link hello is invalid in the endpoint domain.

`BMH2` is a clean cutover: `BMH1` peers cannot authenticate or downgrade the connection. Discovery-selected link identities must match the selected announcement prefix, including hybrid BLE-control/Classic-RFCOMM after operating-system pairing. Direct DEBUG connections still authenticate a persistent app identity but lack that discovery binding.

Classic link security is independent of the app's. Streams and forwarders have always used insecure RFCOMM; calls and relays use Android's secure RFCOMM, which requires a MITM-authenticated bond on both phones. The experimental Classic without pairing (the register in [ARCHITECTURE.md](ARCHITECTURE.md), off by default) makes every role insecure: Android pairs Just Works without storing a bond, so the radio link has no authenticated link key, as on LE CoC and GATT. Nothing in BMH2, BMS1, BME1, BFG1 or BGK1 changes, and the link and endpoint handshakes still bind the announced node prefix. An active radio attacker can therefore sit between the phones at the link layer and see record sizes and timing (the metadata a passive observer of LE links already sees), but cannot open, forge, reorder or replay records, and cannot impersonate either identity. Remembered Classic addresses are hints bound to an authenticated identity only after BMH2 succeeds on them; a relayed handshake can point a hint at a relay, which costs a failed or relayed attempt, never trust. A first contact by Classic inquiry needs the target to be discoverable, which exposes its name and public address to nearby scanners for the visibility period.

## Identity verification

Added 2026-10-10 (API only; the UI binds it). Fingerprints, codes and checks are computed locally from keys the BMH2 endpoint handshake already authenticates; no record format changes.

- **Why.** Discovery binds a link to the 48-bit (12-hex) announcement prefix, and calls/streams check the endpoint identity against that prefix. The node ID itself is 128 bits and the signed hello proves possession of the key, but an attacker who grinds about 2^48 P-256 keys gets one whose node ID starts with a victim's prefix and passes the prefix check. Comparing the full key fingerprint closes that gap for contacts the user has verified.
- **Fingerprint.** `SHA-256(identity SubjectPublicKeyInfo DER)`, the exact bytes `NodeId.fromPublicKey` hashes, so the first 16 bytes are the node ID and the first 6 the announcement prefix. Shown as 64 hex digits (16 groups of four). Each authenticated endpoint session (`EndToEndVideoSession.peerFingerprint`) carries the peer's fingerprint.
- **Safety code (Signal style).** Each party has its own 30-digit half: `h1 = SHA-512("BluetoothVideoMesh/IdentityVerification/SafetyCode/2" || fingerprint)`, `h(i+1) = SHA-512(h(i) || fingerprint)` up to `h5200`; group `g` (0-5) is the big-endian 40-bit integer from bytes `5g..5g+4` modulo 100000, zero-padded. The pair code is the two halves sorted as strings: 60 digits in twelve groups of five. Both phones show the same code for the same pair, and it never changes for the pair. Each half depends on one key only, so a man in the middle must find a key whose half equals the victim's half: a second preimage of about 2^100 tries, each costing 5,200 hashes and a key generation. There is no birthday shortcut (the version 1 code hashed both keys together, which allowed one, and was replaced before release). The QR comparison of the full 256-bit fingerprint remains the stronger path.
- **QR payload.** `BVMID1.<64 hex fingerprint>.<base64url, no padding, UTF-8 NFC display name>`. Encoders write uppercase hex (QR alphanumeric mode); parsers accept all-uppercase or all-lowercase hex. The parser rejects any other magic/version, field count, length or alphabet, mixed-case hex, padding, non-canonical base64, invalid UTF-8 and names that are blank, longer than 64 bytes, or contain control, format (bidi embeddings, overrides and isolates U+202A-202E and U+2066-2069, directional marks, zero-width characters, BOM), private-use, surrogate, unassigned or separator code points. Names are NFC-normalized. The display name is an unauthenticated label; only the fingerprint is compared.
- **Verified contacts.** `noBackupFilesDir/identity-verification/verified-contacts.bin`, sealed with its own non-exportable Keystore AES-256-GCM key (`bluetooth-video-mesh-verification-v1`). The file and key exist only after the first contact is verified. A peer becomes verified only when the scanned (QR) or confirmed (safety code) fingerprint equals the full fingerprint of an endpoint handshake completed in this process with that node ID; the last 1,024 authenticated peers are remembered by node ID for this. A second key with a verified contact's prefix cannot be marked verified until the old contact is explicitly forgotten.
- **Session check.** Every end-to-end handshake (calls through any relay chain, direct and forwarded streams, group endpoints) records the peer fingerprint and compares it with the verified contacts right after the signature verifies and before any content key is used. A verified contact with the same 48-bit prefix but a different fingerprint is `MISMATCH`: it is logged as `SECURITY IDENTITY MISMATCH`, the UI listener is notified, and by default (`MismatchPolicy.REFUSE`) the handshake fails with "possible impersonation". `WARN` continues and leaves the warning to the UI. With no verified contacts nothing changes.
- **Forwarded streams.** The forwarder's own fingerprint is checked in its handshake. The original source is known only by the 128-bit node ID that the authenticated forwarder states in its `BFG1` grant: the receiver compares it with verified contacts of the same prefix (equal node ID: verified; same prefix, different node ID: `MISMATCH` under the same policy). This trusts the forwarder, which is an admitted viewer holding the media key and could re-seal content anyway.
- **Group branches.** A group source that refuses one receiver drops only that receiver: it sends that receiver an empty `WRAPPED_KEY` control (the existing type, no new value). The receiver's endpoint cannot open it and fails closed, and the relay reports it gone. The other receivers keep their keys and the stream continues; the refused receiver is not counted, and its later controls are ignored.
- **Damaged store.** A store that exists but cannot be opened is `STORE_UNREADABLE`, with a cause: `CORRUPT_FILE` (AES-GCM authentication or structure fails: damaged, or sealed under a lost Keystore key) stays unreadable until the user resets the store (`resetVerifiedContacts()`); `KEYSTORE_ERROR` and `IO_ERROR` are retried on the next access. The cause is logged and UI listeners are told once per episode. The policy is fail-open (design decision): nobody is refused because of it, every peer counts as unverified meanwhile, and the store is never overwritten implicitly.
- **What it does not do.** It proves which key a phone holds, not who holds the phone. Unverified peers are still accepted exactly as before (prefix check only). The store has confidentiality and integrity against offline tampering (AES-GCM under a Keystore key) but no rollback or deletion protection: anyone who can delete or roll back app files on the phone can make a verified contact unverified (never falsely verified), which disables the mismatch refusal for that contact. Store-and-forward contact cards keep their own safety number (key plus mailbox key). A wipe or reinstall creates a new key, so the contact becomes unverified (new prefix), not a mismatch.

## Build tag in the link hello and update verification (updater, default on; wire change 2026-10-11)

Status: designed 2026-10-11 for the "Newer version nearby" notice (ARCHITECTURE register "Check for updates" and "Tell me about newer versions nearby"). No record type, length or version number changes, so every BMH2 build keeps interoperating. Not yet tested on phones (PLAN).

**Why the hello, and why not a new field.** The link hello is the one authenticated artifact both phones already exchange on every connection, and its signature binds it into the session transcript. `HandshakeHelloCodec` is exact-length (a longer capability block or trailing bytes fail with "Unsupported capability version" or "Trailing handshake data"), so a new field would cut off every older build, including the published 0.1.0-beta. A new hop record type is also rejected as unknown by older readers. The hello does have two places an older build cannot object to: a transport-mask bit it never tests, and a 32-byte nonce it treats as opaque.

**Field.** Link-hello transport-mask bit 7 (`0x80`) means: the first two bytes of this hello's nonce are a build tag, and the other 30 are random.

| Link-hello transport-mask bit | Meaning |
| --- | --- |
| 0, 1, 2 | Transports: Classic, LE CoC, LE GATT |
| 3 | `BDO1` link opening (rotating discovery IDs) |
| 4 | `SETUP` (relayed calls) |
| 5 | Unused in link hellos (end-to-end hellos use it for `LABELS`) |
| 6 | Call relay |
| 7 | **Build tag** (end-to-end hellos use bit 7 for call video fragments; a link hello and an end-to-end hello are different signature domains and never share a reader) |

```text
nonce[0..1] = tag, big-endian u16:  bit 15 = project release key,  bits 14..0 = release number R (1..32767)
nonce[2..31] = 30 random bytes
```

`R = installed longVersionCode / 10`: the base `versionCode` of `app/build.gradle.kts` with the ABI digit removed (ARCHITECTURE "Distribution and releases": code = base x 10 + 0/1/2), so the tag never says which CPU type a phone has. A debug or non-split build (code below 10) has no release number and sends no tag. Bit 15 is set when the installed APK's only signer is the published release certificate pinned in the app (`AppSharePolicy.PUBLISHED_RELEASE_CERT_SHA256`); an F-Droid build, a self-built APK and a debug build send 0. The tag is sent only in **link** hellos (never end-to-end hellos, which a relay copies, so only the adjacent phone learns it), never in an advertisement, and only while the user's switch "Tell me about newer versions nearby" is on. A DEBUG benchmark launch sends it only with `test_newer_versions_nearby=true`; otherwise the hello bytes are exactly as before.

**Receiver rules.**

1. Read the tag only after the BMH2 handshake succeeded (`MeshHandshake.finish` verified the peer's signature over its hello, which includes the bit and the nonce). A failed or unverified handshake yields nothing.
   The tag then reaches the notice (`LinkBuildTags.sink`) **only from a link this phone opened** (it called, joined or relayed with that phone): a stranger who connects to our listener could otherwise plant a note, and a note leads a user toward installing a file (independent review F2). The responder side still parses the tag and keeps it on the session; it just does not report it.
2. Take it only if bit 7 is set, `R` is 1..32767 and the local switch is on. An older build never sets bit 7, so it yields no tag.
3. Remove bit 7 from the capabilities the rest of the app sees (`SecureBluetoothSession.peerCapabilities`) and keep the tag in a separate field, so no transport test, relay check or negotiation can read it. Local capabilities never carry bit 7, so the existing `peer.transportMask and local.transportMask` overlap tests are unaffected.
4. The tag is a **claim by the peer's identity key about its own build**, not proof about its APK. The hello is signed by the identity key, never by the APK signing key, so a modified app can claim any value. It therefore only ever decides whether to *show a notice*; it never starts a download or an install.

**Notice rules** (`NewerVersionNearby`, JVM-tested). Show "Newer version nearby" only while all hold: the switch is on; the claim `R_peer` is greater than the installed release number and at most 20 above it (a bound so one forged number cannot suppress later notices for long); a phone with the project release key sees only claims with bit 15 set (a build signed by someone else cannot update it); and the user has not dismissed this claim (a dismissal hides claims up to that number for 7 days, then the number is forgotten). A claim that is not repeated for 14 days fades. The stored state is the best claim, when it was seen and the dismissal; no peer identifier is stored. The notice is a quiet row on the home screen, never a sound, a notification or a dialog, and it never appears during a call or stream.

**Compatibility.** An older build parses a tagged hello unchanged: it checks the nonce length (32) and reads `transportMask` only with `and` tests (`transportMask and transport.capabilityMask`, `and LINK_HELLO_BIT`, `and CALL_RELAY_CAPABILITY`, ...); no reader compares the whole mask or looks at nonce contents. The Windows receiver (`SecureBluetoothProtocol.cs`) checks only the nonce length and copies the mask. The iPhone app (`NearbyCore/MeshHandshake.swift`) also checks the nonce length only and reads the mask with `&` tests; its call-fragment test (bit 7) reads the end-to-end session's capabilities, never the link's, so a tagged Android link hello cannot switch fragments on. The HKDF salt `SHA-256(initiator nonce || responder nonce)` still has at least 240 random bits from each side, and the fresh ephemeral ECDH keys are what make the session keys unique, so a two-byte tag costs no cryptographic strength. The tag is part of the signed, transcript-hashed hello, so it cannot be added, removed or changed by anyone who does not hold the identity key without failing the handshake. Tested: a tagged and an untagged phone handshake in both roles; a tagged hello decodes with the unchanged codec; the tag is invisible in `peerCapabilities`.

**Privacy.** The hello is not encrypted: anyone who completes or captures a link handshake already sees the node ID, identity key and capability bits. The tag adds the release number (coarse) and one bit "project-signed build". It is never in an advertisement, so a passive scanner of adverts learns nothing, and with rotating discovery IDs a stranger still learns the identity only by connecting (stated residual there). Stated residual: a peer that connects to an updated phone can tell whether it is outdated, which could help it pick a known bug; the switch turns this off in both directions (a phone that does not send also does not show notices). Forcing the same disclosure on phones with the switch off is not possible, because an older build sends no tag at all.

**BMH3 links.** The tag does not travel in a BMH3 link's cleartext (no nonce field, no bit 7): it is the `BUILD_TAG` extension inside the sender's encrypted block (see "Experimental BMH3 identity-hiding link handshake"), with the same receiver rules.

**Update verification (not a wire format; used by the online check and by an APK received from a nearby phone).** No path installs automatically. An APK is installed only after Android's own confirmation, and only if all of these hold, checked on a private copy and bound to the bytes installed:

1. The package name equals this app's.
2. `versionCode` is strictly higher than the installed one (never a downgrade), and its ABI digit (`versionCode % 10`) is the installed one or 0 (universal), so a 32-bit-only file never replaces a 64-bit install.
3. `PackageManager.getPackageArchiveInfo(..., GET_SIGNING_CERTIFICATES)` reports exactly one current signer (no multi-signer APK). On Android 10 the call must also pass `GET_SIGNATURES`, or the platform collects no certificates and `signingInfo` is null (AOSP android10-release; fixed in Android 11).
4. That signer's certificate SHA-256 equals the installed app's signer, or the APK carries a signing lineage (`signingCertificateHistory`) whose last entry is that signer and which lists the installed certificate before it (a key rotation signed by the old key; Android enforces the lineage's capabilities at install). For the online check it must also equal the pinned release certificate, and the online check is offered only when the installed app already carries that certificate (a debug or F-Droid-signed copy cannot be updated from a GitHub release).
5. For an online download, the file's SHA-256 equals the release's published value (the asset `digest` of the GitHub API response, else the release's `SHA256SUMS`); with neither, nothing is installed.
6. The SHA-256 computed over the private copy while it is verified equals the SHA-256 of the bytes written into the `PackageInstaller` session (one pass, hashed in transit), so a file swapped between verification and installation is detected.

Android independently refuses an update whose signing certificate differs from the installed one and a lower `versionCode`; the checks above fail first with a readable reason and add the pin, the ABI rule and the hash bindings. The online source is a value (`UpdateSource`: `releases/latest` URL, the release-download prefix its assets must have, the redirect hosts); GitHub is the only one shipped, and a mirror is one more instance, no more trusted than GitHub because the checks above run on the file. A later certificate rotation needs the next certificate added to the pin set in a release signed by the old key (`ReleaseSigner.PINNED`); only then does a lineage APK signed by the new key pass the online check on installed copies.

## Hop and endpoint records

The `BMS1` hop header is 17 bytes:

| Field | Bytes |
| --- | ---: |
| Magic `BMS1` | 4 |
| Type | 1 |
| Sequence | 8 |
| Ciphertext length including GCM tag | 4 |

The whole header is AES-GCM associated data. The nonce is four zero bytes followed by the 64-bit sequence. Each direction starts at zero and requires the exact next sequence. Active types are endpoint handshake (`4`), endpoint content (`5`), immediate-child heartbeat (`6`), serialized mesh envelope (`7`), group relay control (`8`), immediate-route withdrawal (`9`) and withdrawal acknowledgement (`10`). Removed plaintext-video types `1`/`2` and congestion-report type `3` are rejected. Store-and-forward type `11` is rejected as unknown by every reader except one that explicitly opts in on a link it owns (see "Store-and-forward messages").

The `BME1` endpoint header is 18 bytes:

| Field | Bytes |
| --- | ---: |
| Magic `BME1` | 4 |
| Content type | 1 |
| Sequence | 8 |
| Packet flags | 1 |
| Ciphertext length including GCM tag | 4 |

The header is also AES-GCM associated data, using the sequence nonce under the endpoint directional key. Endpoint opening accepts increasing sequence gaps after media drops but rejects replay and reordering; this differs from exact-next `BMS1` hop ordering. Active types are stream header (`1`), media packet (`2`), lifecycle (`4`), keyframe request (`5`), private-call signal (`6`), wrapped broadcast-group key (`7`) and terminal acknowledgement (`8`). Congestion-report type `3` is rejected. Non-media content must have zero packet flags.

Media contains compressed video or Opus audio, distinguished by the audio flag. Visible flags permit relay routing and dependent-video drops until a recovery keyframe. The decrypted packet repeats those flags; a mismatch fails closed. Lifecycle payload is exactly one byte: `LIVE=1`, `PAUSED=2`, `ENDED=3`. Keyframe requests and terminal acknowledgements have empty payloads.

`BTV3` contains video format, display rotation, audio codec, sample rate and channel count. Each inner packet has length, flags, one shared monotonic presentation timestamp and one compressed video/audio payload. It is accepted only inside authenticated `BME1`; Android rejects `BTV1` and `BTV2`. The retained Windows normal receiver's older video-only BTV2 path still needs BTV3 audio/discovery integration.

Mesh routing and inner media flags use separate namespaces. `BMV1` reserves bit 4 for lifecycle and bit 5 for terminal End; `BTV3` uses those positions for DEBUG integrity and video discontinuity. Source serialization removes those two bits only from the outer media envelope. Full inner flags stay authenticated in `BME1` and repeated in the decrypted packet. An opaque relay checks outer media flags against the mapped metadata. Only a lifecycle End gets the outer terminal bit; a recovery keyframe must not stop discovery or child delivery. Bit 7 (`128`) marks a video packet as discardable (a temporal enhancement frame whose droppability the source verified from the AV1/VP9 bitstream). Only the Experimental temporal-layering option (off by default) sets it; receivers accept it either way, and with the option off no queue skips anything.

## Private-call signaling

`BMC2` is an exact 23-byte payload inside endpoint-content type `6`:

| Field | Bytes |
| --- | ---: |
| Magic `BMC2` | 4 |
| Signal | 1 |
| Random non-zero call ID | 16 |
| Reason | 1 |
| Relay-hop count | 1 |

Signals are Invite (`1`), Ringing (`2`), Accept (`3`), Decline (`4`), Cancel (`5`), Hang-up (`6`), Camera off/on (`7`/`8`) and Microphone muted/unmuted (`9`/`10`). Reasons are None (`0`), Rejected (`1`), Busy (`2`), Unsupported (`3`), Normal (`4`) and Error (`5`). Decline accepts only Rejected/Busy/Unsupported; Hang-up accepts only Normal/Error; all other signals require None. Unknown values, invalid length, zero call ID and invalid state transitions are rejected.

Only Invite can carry a non-zero relay count: the number of relays between caller and callee, which the caller reads from the route cost of the offer it connects to. The wire parser accepts counts `0..15`; the app builds at most four relays (below). Both endpoints validate call ID and state before acting. Camera/microphone start after recipient acceptance. `BMC2` is never accepted as plaintext BLE control.

For the opaque call relay, A and C alone hold content keys. B copies both ordered encrypted directions through independent adjacent queues/liveness without camera, microphone, decode or re-encode. The envelope binds call ID, endpoint identities, direction and endpoint records; adjacent radio identity remains separate from endpoint identity.

### Private-call relay chains

A call may cross a chain of opaque relays: caller -> R1 -> ... -> Rn -> callee, with n at most four (`PrivateCallRelayChain.MAX_RELAYS`; the six required phones form at most four relays between two endpoints). On by default since 2026-10-09; DEBUG `test_call_relay_chain=false` (benchmark tunable `call_relay_chain`) restores the one-relay rule exactly. The call relay itself is DEBUG-only. No record type, flag or signal changes: chains reuse the discovery route cost, the BMH2 link hello's signed `maxChildren`, and the existing Invite relay count. With chains on, a call relay also sets transport-mask bit 6 (`0x40`, call relay) in the capabilities of its signed BMH2 link hello. Every reader tests only the transport bits it needs, so older peers ignore it; with chains off the hello is unchanged.

- **Downstream first, one parent, one child.** A relay authenticates its child with a fresh BMH2 link handshake before it advertises anything. Only then does it advertise the child's offer (the callee's node prefix and flags) at route cost + 1, accept exactly one parent within 180 s (`PARENT_WAIT_MS`: enough for three outer relays and the caller to connect), and leave the air (Classic too, with chains on; CoC and GATT already stopped advertising). A relay whose parent never comes stops and releases its child. Each relay serves one call and stops when either side closes.
- **Child admission (hop-local).** An offer at route cost 0 is the callee itself: the child's authenticated link identity must equal the announced prefix, exactly as for one relay. An offer at route cost 1..3 is another relay: the child's link identity must not be the announced callee (Classic refuses a direct link, as for a relayed caller), must not be this relay, and its signed link hello must declare relay capacity (`maxChildren` at least 1; call endpoints sign 0) and the call-relay bit (forwarding receivers and stream relays also sign `maxChildren` 1 but never the bit). Over Classic a relayed child is only the advertising device itself (its discovered address, or its exact bonded address or unique bonded name): no bonded-phone fallback and no inquiry, so a relay cannot attach to another call's relay or a receiver that happens to answer. A relay never takes an offer for its own prefix or above route cost 3, so no advertised count exceeds four.
- **Parent admission (hop-local).** A relay refuses a parent whose link identity is itself, its own child or the callee it relays for.
- **No loops.** A relay has a child before it advertises, and it takes one parent only after that. A cycle would need some relay to be another's child before that relay had a child of its own, so every chain is a path that ends at a route-cost-0 endpoint. The route cost grows by one at every hop and stops at four. No signal travels more than one hop: each relay reads its child's advertisement and its two adjacent link hellos only.
- **Caller limit.** The caller ignores and refuses an offer whose route cost exceeds four instead of clamping it into the Invite.
- **End-to-end identity.** The caller runs the BMH2 endpoint handshake through every relay and requires the endpoint identity to match the discovered callee prefix ("Call peer identity changed between discovery and connection"); the callee authenticates the caller the same way. Relays copy endpoint handshakes, ciphertext and ordered records unchanged and replace heartbeats with version-1 liveness, as one relay does.

**Malicious relay.** Route cost, prefix and flags in a BLE advertisement are unauthenticated hints, and a relay's signed `maxChildren` proves only that it chose to sign relay capacity. A malicious relay, or a phone that advertises a callee's prefix at any route cost, can therefore drop, delay or refuse the call, attract it to a longer route, or report a false relay count, which changes only the caller's relayed video cap. It cannot impersonate an endpoint: endpoint signatures and keys use their own domain, the node ID is a hash of the identity key, and an endpoint hello that a relay answers itself carries the relay's identity, which the caller's prefix check refuses. It cannot read, forge, reorder or replay media or call signals, because `BME1` and `BMC2` are sealed with endpoint keys it never holds, and a modified record fails the endpoint's open. It sees what one relay sees: adjacent identities, signed public endpoint hellos, and record sizes and timing. The 48-bit discovery prefix is the existing binding between a discovered person and an endpoint identity; chains add no weaker step.

Admission, overload and capacity guards stay hop-local: each relay still holds exactly one parent and one child, the endpoints keep their admission and rate rules, and relayed calls keep the relayed video cap (15 FPS, 110 kbps; an experimental measured cap is in the register in [ARCHITECTURE.md](ARCHITECTURE.md)). A relay that cannot keep up exerts backpressure on its parent link; a stalled hop ends the call through the existing liveness and close paths.

### Voice calls and push-to-talk

Status (2026-10-11): no longer experimental. Voice calls are the Settings > Features switch "Voice calls" (shipped default off until the phone test passes; DEBUG `test_voice_calls` is the benchmark switch), and hold-Mute-to-talk is part of every call. The wire is unchanged.

Voice calls add no signal, reason, capability bit or version; `BMC2` stays 23 bytes. The only change is ordering: Camera off (`7`) may now precede acceptance. A voice caller queues Invite and then Camera off in its ordered endpoint sequence. A callee with the experiment on treats Camera off while it is ringing as a voice offer; Camera on while ringing withdraws the offer. A voice answer queues Accept and then Camera off. Neither side starts a camera or video encoder, and no video packet, codec configuration or keyframe is sent. Each `BTV3` header still declares Opus audio and the codec/format that a later upgrade would use. A receiver creates its video decoder only when the first video packet arrives.

Existing Android peers, and peers with the experiment off, already accept Camera off/on in every call phase. They see a video call whose caller has video off, and they answer with their own video. The voice caller shows that video when the first frame renders. During the call, each endpoint controls only its own camera with Camera on/off, as in video calls: adding video is an upgrade, and turning off your own video is a downgrade. The voice layout appears while neither direction carries video. A negotiated two-sided switch, where one side asks the other to turn its camera on or off, would need a new signal value. The `BMC2` decoder rejects unknown signal values, so that value would need a capability gate and review; it is left for later.

### Call codec preference bit

In an end-to-end call hello, decode-mask bit 7 (`0x80`) means "decode VP9 when you can encode it; the other listed codecs are decodable fallbacks". A legacy Qualcomm phone (API 32 or older) sets it, with its real decoders, instead of advertising VP9 only. A sender that has a VP9 encoder sends VP9; one that has none sends another listed codec. The bit is not a codec: codec tests ignore it, link hellos never carry it, and relays copy the end-to-end hello unchanged, so direct and relayed calls decide alike. The control arm `test_call_codec_fallback=false` advertises VP9 only, as before.

### Experimental call video fragments (off by default)

`test_call_video_fragments` (benchmark tunable `call_video_fragments`) adds one endpoint content type, video fragment (`9`), for direct calls only. Its reason: a GATT write blocks for the air time of the whole record, so call audio waited 620-1193 ms behind one large video frame (calls-noloss-m31asus-51cc8028).

- **Negotiation.** An endpoint with the experiment on sets bit 7 (`0x80`) of the transport mask in its signed end-to-end hello. The link hello is unchanged. Existing decoders accept unknown transport bits and test only the transport bit they need. A sender fragments only when both hellos carry the bit and the call is direct (relay count 0). With the experiment off, neither the bit nor type `9` is ever sent, so the wire is exactly as before. A receiver that did not advertise the bit rejects type `9`; every other endpoint reader (streams, relays, forwarders) rejects it as an unknown type, exactly as before.
- **Format.** A video media packet whose encoded `BTV3` packet (13-byte header plus payload) exceeds 3,072 bytes is cut into chunks of at most 2,048 bytes (the sender chooses the size; see Chunk size). Each chunk is sealed as its own `BME1` record of type `9`, with the frame's packet flags in the header. The payload is a big-endian total length (4 bytes), a big-endian offset (4 bytes), and then the chunk. Fragments use the same directional key, nonce sequence and replay/reorder rejection as every endpoint record, and `BMS1` hop ordering is unchanged.
- **Chunk size (sender choice, no wire change).** The format names each fragment's total and offset and the receiver accepts any positive chunk length up to the frame total, so chunk sizes are not part of the contract. The default sender uses 2,048 bytes. The experimental arm `test_call_fragment_airtime_ms=N` (benchmark tunable `call_fragment_airtime_ms`, default 0 = off, needs `test_call_video_fragments`) instead sizes each chunk as measured link rate x N ms, clamped to 675..4,096 bytes, re-evaluated for every fragment. Every fragment costs 75 bytes of framing and authentication besides its chunk: hop record header 17 and tag 16, endpoint record header 18 and tag 16, fragment header 8 (the 13-byte `BTV3` packet header is paid once per frame). The 675-byte minimum is the smallest chunk with at most 10% of the fragment on the wire being that overhead (2,048 bytes is 3.5%, 4,096 bytes 1.8%). A frame is cut into the fewest, near-equal chunks of at most the target (no runt tail, none below the minimum), and a packet of at most 1.5 x the target chunk goes whole (3,072 bytes for 2,048). The rate is this call link's peak delivery goodput over the last 10 s from the peer's version 3 link reports (which count media bytes, so small fragments do not starve them), else the peer's arrival-train estimate, else this phone's learned single-link probe, which may only shrink the chunk below 2,048; with none of them the chunk stays 2,048. The arrival-train estimate itself needs records of 8,000 bytes or more and therefore stops updating once frames are fragmented. Chunk sizes (rate dependent) are traffic metadata, like fixed sizes.
- **Interleaving.** Between two fragments the sender may write queued call audio media packets, and only those. In the airtime arm the sender also writes all queued audio before the first fragment, so no fragment starts while call audio is queued. The receiver accepts a frame's fragments only in order: the first at offset 0, each next one at the previous end, all with the same total and flags. The flags may not include audio or codec configuration, and the total is at most the largest endpoint plaintext. Once complete, the receiver decodes the concatenation as a `BTV3` media packet with the same flag check as a whole media packet.
- **Failure.** While a frame is unfinished, a non-audio media packet or a stream header fails the call closed, as does any gap, overlap, change of total or flags, empty chunk or overrun.
- **Metadata.** Fragment sizes and timing replace whole-frame record sizes as traffic metadata.

Push-to-talk adds no wire value. Holding the button sends Microphone unmuted (`10`), and releasing it sends Microphone muted (`9`). The microphone and Opus encoder keep running, and the sender drops captured audio while muted. Security is unchanged: all signals use the authenticated, ordered endpoint sequence. As with camera off today, a relay or radio observer can infer a voice call or a released talk button from the absence of video or audio records. That is record size/timing metadata.

## Peer labels: handles, names, call subjects and stream titles

Status (2026-10-11): no longer experimental. The Settings > Features switch "Names and titles" (shipped default off until the phone test passes; DEBUG `test_peer_labels` is the benchmark switch). Naming design phase 1 with review fixes R1-R10 and R13 (design decisions in DECISIONS "Naming, uniform handle and relayed discovery"). With the switch off, every byte on air and on the link is unchanged. The wire is unchanged by the promotion; the look-alike warning (UTS #39 skeletons) is display only and sends nothing. Not yet tested on phones.

**Handle (UI only, no wire change).** `prefix48 = SHA-256(identity SPKI DER)[0:6]` (the announcement node prefix). Encode `prefix48 << 2` (50 bits) as 10 Crockford Base32 symbols (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`), most significant first, shown `SSSSS-SSSSS`; the last symbol's low 2 bits are zero. Parsing is case-insensitive, maps `I`/`L` to `1` and `O` to `0`, ignores hyphens and spaces, and needs exactly 10 symbols with a zero tail. Vectors (`PeerLabelTest`, generated by the design's `handle_vectors.py`): `010203040506` -> `04106-1050R`, `a1b2c3d4e5f6` -> `M6SC7-N75YR`, `000000000000` -> `00000-00000`, `ffffffffffff` -> `ZZZZZ-ZZZZW`. People who are not your contact always show the full handle (R5: 25 bits are ground in minutes). Logs, `BleL2capPeer.label` and host tools keep the 12-hex prefix (R10). The handle proves nothing before connecting; after connecting it is the existing 48-bit prefix check. Only the full fingerprint (QR or safety code) verifies a person.

**Capability.** End-to-end hello transport-mask bit 5 (`0x20`) = "accepts and sends `LABELS`". It is never set in a link hello or a `BGK1` group hello. Old readers test only their own bits. A `LABELS` record is sent only when both endpoint hellos carry the bit; an opener that did not advertise it rejects type `10` as an unknown type, exactly as before.

**Signed label `BNL1`** (big-endian):

```text
"BNL1" | version 1 (1) | kind (1): 1 person name, 2 stream title, 3 call subject
| SPKI length (2, 1..512) | identity SubjectPublicKeyInfo DER
| sequence (4; counts within one binding only, starts at 0)
| binding type (1): 1 call ID, 2 stream ID | binding (16)
| text length (1, 1..64) | UTF-8 text
| signature length (2, 1..256) | ECDSA P-256 SHA-256 DER signature over
    "BluetoothVideoMesh/Label/1" || 0x00 || every byte before the signature length
```

There is no timestamp (R2: it leaked clock skew). Every label is bound to the `BMC2` call ID or a stream ID, so it cannot be replayed into another call or stream, and no per-signer state outlives the session. A direct stream that has no mesh stream ID binds to the all-zero stream ID; that binding is accepted only from the authenticated endpoint peer of that direct stream (a forwarded grant naming the zero stream ID gets no labels). Labels are signed with the existing identity key, once per binding.

**Container `LABELS`** (BME1 content type `10`, packet flags 0): `"BLB1" | count (1, 0..3) | count x (length (2) | BNL1)`. Count 0 is valid (R4).

**Receiver checks, in order.** Container lengths; label magic/version; known kind (unknown kinds are skipped, for later kinds); `SHA-256(SPKI)[0:16]` equals the expected signer (the call's endpoint peer; the direct stream's endpoint peer; for a forwarded stream the source node ID in `BFG1`); signature; binding equals this call ID or stream ID; the text is already canonical under the text rules below. A label that fails is dropped and `SECURITY LABEL REJECTED kind=… reason=…` is logged without the text; a higher sequence replaces a lower one within the session; more than one container per 2 s or eight per minute is ignored. A label never fails a call or stream.

**Text rules (`LabelText`).** Trim, collapse whitespace runs to one space, NFC. Byte limits: person name 32, stream title 48, call subject 64. Reject control, format (bidi controls, ZWJ/ZWNJ), private-use, surrogate, unassigned and line/paragraph separator code points; more than 3 consecutive combining marks; U+2713/2714/2705/2611/1F5F8; scripts outside UTS #39 Moderately Restrictive (one script plus Common/Inherited; Latin plus one other script except Cyrillic or Greek; Latin+Han+Hiragana/Katakana, +Bopomofo or +Hangul); and handle-shaped text: after NFKC and lowercasing, `^[0-9a-z]{5}-[0-9a-z]{5}$`, or text that parses as a full or short handle **and** contains a digit (R6: "Brave Tiger" stays valid). The unassigned check uses the receiver's Unicode version, so a newer character drops the name to the handle on an older phone (fails safe).

**Calls (direct and relay chains).** `LABELS` is an ordinary endpoint record; existing call relays copy it unparsed.
- Caller: one container (its name if set, and the subject) bound to the call ID, queued immediately before Invite in the ordered endpoint sequence.
- Callee: holds at most one container received before the Invite of the same session and verifies it against that Invite's call ID (R3).
- Callee's own name (R1): sent only immediately before Accept, or at Ringing when the caller is a verified contact (full fingerprint). A declined, cancelled or unanswered call never reveals the callee's name.

**Streams.** A stream hop exchanges `LABELS` only when both endpoint hellos carry bit 5 **and** the link peer is the endpoint peer (no opaque stream relay between, since stream relays inspect BME1 types). Then exactly one record is sent at a fixed position: a direct source sends it as the first endpoint record, before the stream header (title bound to the mesh stream ID, or to the zero ID for a non-mesh stream); a forwarder sends it right after `GROUP_KEY` under the child's endpoint session, containing only the labels it verified from the `BFG1` source for that stream ID, byte for byte (count 0 if none). The receiver verifies after reading the header (the stream ID is known then). A forwarder can withhold labels but not forge, edit or rebind them; per PROTOCOL "Forwarded streams", a malicious forwarder can still name itself as the source and sign its own title (R22).

**Public title pages.** A second legacy, non-connectable, scannable advertising set beside the stream offer (source or verified forwarder): primary PDU = the service UUID `c8d5a101-…`; scan response = manufacturer `0xFFFF`:

```text
version 3 (1) | stream route token (4, of this advertiser's stream offer) | SHA-256(title)[0:2]
| page (1): index << 4 | count (count 1..3, index < count) | 1..19 title bytes (whole code points)
```

Interval 250 ms, one page per second (about 4 advertising events per page). Old scanners reject the payload (not 22 bytes). Scanners with the switch on route version-3 payloads to a title board before the per-address dedup, so rotated pages are seen; they reassemble by (token, digest, count) within 30 s, require valid canonical UTF-8 matching the digest, and show nothing for a token with two different digests within 60 s. An advertised title is shown as "unconfirmed"; after joining, the signed kind 2 label replaces it. If no set is free (a one-time probe of free legacy sets, logged `BENCHMARK adv_set_probe free=… | extAdv=… | multiAdv=… | maxAdvData=…`, found fewer than 2 free sets, so one stays spare for the stream offer's own stop + restart and OS advertisers; a forwarder that never probed probes first; or the start fails, e.g. `ADVERTISE_FAILED_TOO_MANY_ADVERTISERS`), only the signed title exists; the stream is never affected. iPhones cannot advertise manufacturer data, so an iPhone broadcaster has no public title.

## Experimental iPhone compact discovery (off by default)

Settings > Features "Find iPhones" (default off until its phone test passes; a benchmark launch uses only the DEBUG extra `test_ios_compact_discovery`). It changes discovery hints only. Android's own advertisement, every handshake, record, key, admission and overload rule are unchanged. A scanner that refuses the masked filter (`SCAN_FAILED_FEATURE_UNSUPPORTED`, `OUT_OF_HARDWARE_RESOURCES`) drops only that filter for the rest of the process and keeps scanning for the app's own announcement (`compact_filter: event=dropped`). Not yet tested on phones or against an iPhone.

**Why.** An iOS app can advertise only a local name and service UUIDs, never manufacturer data. In the foreground one 128-bit UUID fits in the advertising PDU an Android scanner reads; further UUIDs go to Apple's overflow area, which only iOS reads, and a background iPhone puts every UUID there. An iPhone therefore announces itself in one service UUID instead of the 22-byte manufacturer-data announcement (company `0xFFFF`) plus `c8d5a101-…`.

**Layout.** Read the UUID as one big-endian 128-bit integer `U` in canonical string order (Java most- then least-significant bits, `CBUUID.data`; the on-air AD value is the same bytes reversed, which both stacks undo).

| Bits of `U` | Field |
| --- | --- |
| 127..112 | Magic `0xC8D6` |
| 111..110 | Version `1` |
| 109..108 | Kind: `0` private-call offer, `1` viewer request, `2` stream offer, `3` rejected |
| 107..60 | Node-ID prefix (6 bytes, as in the 22-byte announcement) |
| 59, 58, 57 | GATT transport (0 = LE CoC; Classic is not representable), relay capable, stream paused (stream offers only) |
| 56..54 | Codec mask: 54 VP9, 55 AV1, 56 reserved for H.264 |
| 53..50 | Route cost 0..15 |
| 49..19 | Route-token bits 30..0. Call offer: 0. Others: token = `0x80000000 or field` |
| 18..0 | Call offer: 0. Viewer request: 18..12 bitrate in 25 kbps units, 11..0 zero. Stream offer: 18..11 the `sequence` byte, 10..9 resolution index (426x240, 640x360, 854x480, 3 = unspecified), 8..7 FPS index (15, 24, 30, 3 = unspecified), 6..0 bitrate in 25 kbps units |

**Decoding.** Strict: wrong magic or version, kind 3, the paused bit outside a stream offer, a call offer with any of bits 49..0 set, or a viewer request with any of bits 11..0 set rejects the UUID. Codec bits are carried, never rejected: bit 56 becomes `capabilitySummary` bit 2, which today's codec tests ignore, so a later H.264-capable iPhone stays visible to this build. The result is an ordinary `DiscoveryAnnouncement`: a call offer gets `FLAG_ACCEPTING_CONNECTIONS | FLAG_PRIVATE_CALL_AVAILABLE`, a viewer request `FLAG_ACCEPTING_CONNECTIONS`, a stream offer `FLAG_STREAM_AVAILABLE`, each ORed with the GATT, relay and paused flags; unspecified geometry/FPS and bitrate 0 decode as 0 (unknown); there is no route recovery. Every real route token has bit 31 set (`StreamRouteToken`'s advertiser mask sets it and logical tokens are 1..2^31-1), so implying the bit loses nothing. Not representable, and never sent by an iPhone: Classic, route recovery, route cost above 15, a viewer request without a route token (the DEBUG direct-receiver mode), geometry/FPS outside the tables (index 3), a bitrate above 3175 kbps (saturates). Android stream settings (100-1500 kbps in 25 kbps steps, the three resolutions, 15/24/30 FPS) are all exact.

**Scanning.** With the switch on, every `BleL2capDiscovery` passes a second `ScanFilter.setServiceUuid(C8D60000-0000-0000-0000-000000000000, mask FFFF0000-0000-0000-0000-000000000000)` in the same `startScan` call. Filters are ORed and it is still one scan start, so the scan-start quota is unchanged. When manufacturer data `0xFFFF` is present it is used exactly as before; otherwise the first service UUID whose top 16 bits are `0xC8D6` is decoded. The DEBUG `scan_stats` line appends `compact` and `compactInvalid` counters while the switch is on and is byte-identical while it is off. After discovery the existing clients connect unchanged: the iPhone hosts the same GATT database (`c8d5a101-…` with the `c8d5a102-…` PSM characteristic, dynamic PSM, insecure channel; or `c8d5a105-…` with `c8d5a103-…`/`c8d5a104-…` chunks), then BMH2, BMS1 and BME1 run as today.

**Security.** The same trust level as the 22-byte announcement, which any advertiser can already forge: every field is an unauthenticated hint. The full 48-bit prefix is present, so the link and endpoint identities must still match it (and the full fingerprint for verified contacts); prefix grinding still costs about 2^48 key generations. Route tokens are broadcast correlation values, not secrets, and keep 31 bits of entropy. A random foreign UUID passes the filter with probability 2^-16 and must then pass the version, kind and reserved-bit checks; a false or forged match only causes a connection attempt that fails at GATT discovery or BMH2, bounded by the existing admission and overload guards. The decoder is fixed-size integer arithmetic.

**Limits.** An iPhone is discoverable only while its app is in the foreground, and it can advertise one role at a time (one UUID). An iPhone viewer that lost its parent advertises an ordinary viewer request. Masked service-UUID filters are public API since API 21 and AOSP re-checks every filter on the host for every result. Each `ScanFilter` takes one controller filter slot, and a scanner with more filters than free slots runs all-pass with host filtering (more wake-ups), so the switch doubles each scanner's slot use. Whether a phone's controller applies the 128-bit mask in hardware is per phone and unmeasured.

## Experimental rotating discovery IDs (on by default for user sessions since 0.2.0-beta)

Promoted 2026-10-12 (0.2.0-beta): on by default for user sessions (one constant, `RotatingDiscoveryFeature.DEFAULT_ENABLED`; an explicit stored choice in the Advanced setting "Rotating discovery IDs" wins, with or without the Advanced view); a DEBUG benchmark launch reads only `test_rotating_ids`. Evidence: phone test P5 (zero carry-over at 3 of 3 boundaries) and the cases P1-P4 and P7 of the combined privacy session of 2026-10-11 (README "What nearby phones can see"). Reviewed design 2026-10-10 (RV1-RV19); the review settled on these answers (a time-limited Visible-by-handle window instead of permanent dual advertising, Everyone with a growing delay, mutual verified contacts with 4-week leases, 15-minute epochs). Phase 1 (strangers, call-ready presence, role 0) was coded first; **Phase 1b** (stream offers, viewer requests, forwarders, call-relay chains and the endpoint opening `BDX1`) and **Phase 2** (contact presence leases and the recognition table) were designed and coded 2026-10-11 and are described below; reach pages version 6 for relayed calls are in "Experimental relayed calls and multi-hop discovery". Classic roles, the DEBUG direct-receiver mode, `BGK1` group hops and the DEBUG stream relay keep version 2 and the fixed prefix (PLAN "Discovery privacy" lists the remaining phases). Off: every byte on air and on the link is unchanged, and version 5 / compact v2 adverts are rejected exactly as by old builds. Not yet tested on phones. **Hardening 2026-10-11** (reference-app review; reviewed by an independent reviewer, findings RH1-RH14 marked where they changed the text): non-discoverable connectable sets and an explicit, never automatic neutral name ("Pre-handshake exposure"), independent random daily keys instead of one long-lived presence key ("Keys and epochs", "Recognition and presence leases"), address reuse on legacy-only controllers ("Address reuse on legacy-only controllers") and the field inventory ("Fields that stay constant across epochs"). With the switch off none of it runs.

**Keys and epochs.** Epoch `e = floor(unix_seconds / 900)` (u32), day `d = floor(e / 96)`. Role `r` (u8): 0 call offer, 1 stream offer, 2 viewer request, 3..255 reserved. All integers big-endian; domains end with `0x00`. Each identity keeps a presence **generation** `g` (u32, from 1) and, for each day in its window, an **independent random day key** `L_d` (32 bytes from a CSPRNG), the daily Temporary Exposure Key model of Google/Apple exposure notification (GAEN), in no-backup app storage. There is **no master key and no derivation between days**: `L_d` is not computable from any other `L_x`, from `g` or from the node ID, and it is not a ratchet (a contact holding one day's key must not be able to compute any later day, and a leaked key must reveal no earlier one). Earlier builds derived `L_d = HMAC(P, ... || d)` from one long-lived `P`, so one extracted store named every past and future ID; that derivation now exists only to migrate such stores (below). Every salt, the owner's own included, is keyed by the day's key (RV11, RD5), so contacts that later receive the keys compute the same IDs:

```text
salt = HMAC-SHA256(L_d(e), "BluetoothVideoMesh/Discovery/Salt/1" || 0x00 || u32 e || u8 r)      (32)
RDI  = SHA-256("BluetoothVideoMesh/Discovery/Id/1" || 0x00 || nodeId (16) || u32 e || u8 r || salt)[0:6]
```

The **day-key window** is `[dayOf(E - 1), dayOf(E) + 27]` for the phone's monotonic epoch `E` (below): today and the next 27 days (the 28 keys a lease delivers) plus yesterday while `E` is the first epoch of a day (the poison-reverse check also computes the previous epoch's ID). A key is created once, when its day enters the window (the whole window when a generation starts, afterwards the key of day `dayOf(E) + 27` when the day changes) and is **deleted when its day leaves the window**; a key is never recreated within a generation. A state that lacks a day it needs (first use, or a phone that was off for more than 27 days) creates it at once. **Write ordering (RH13):** a day key is delivered in a lease only after the file holding it was written (atomic replace, then the lease); a key that could not be stored is used for advertising from memory only and never delivered, and a crash before the write loses a key nobody has seen (a later lease then carries the regenerated key, and the receiver rule of RD1d replaces the stale record). A new generation (revocation, forward-jump recovery, "Reset presence key") creates the whole window again from fresh randomness. Maintenance (deleting the day that left the window, creating the next day's key, storing the result) runs once per day on the recognition thread; it never blocks an advertiser, because every key the next epoch needs already exists.

**Seizure property.** A phone read at epoch `E` (an unlocked phone, an extracted store) yields exactly the keys of its window: it can name no ID of a day before `dayOf(E - 1)` (those keys are deleted and nothing derives them) and none of a day after `dayOf(E) + 27` (those keys do not exist yet and are drawn later; they are not a function of anything stored). **What it does give its reader (RH3):** every ID of the window, that is this phone's IDs until `dayOf(E) + 27`. A phone that was out of its owner's hands (taken at a border and handed back, lent, or read by an examiner) can be followed by passive sensors for up to four weeks, and GAEN differs here: a GAEN phone draws each day's key on that day and holds no future keys, while a lease must hand its contacts 28 days at a time. The remedy is "Reset presence key" (a new generation: the whole window is replaced; contacts recognise the phone again after the next mutual call). The IDs are the ones its contacts already hold, so the seized phone adds nothing to *their* capability; it also gives away the node ID, the contact store and the generation. A contact's copy is bounded the same way: it deletes lease days earlier than `dayOf(myE + skew) - 1` (one day of margin for the +-8 epoch window). Residuals: the sealed file is rewritten atomically when the window moves, but ciphertext of an earlier version may remain in flash blocks until they are overwritten and decrypts with the same non-exportable Keystore key (the same limit GAEN has for its daily keys; Android's file-based encryption probably makes old blocks unrecoverable without the user's credential, filesystem behaviour is unverified); a lease holder keeps its day keys for their days, so a holder that is itself seized reveals the IDs of the days it still holds.

**Monotonic epoch (RV4).** The phone persists `lastEpoch`. A tick happens only when the wall epoch differs from the one seen at the last tick, or 960 s of `elapsedRealtime` passed since it (900 s plus one minute, so a normal boundary never double-ticks); at a tick `E = max(wallEpoch, lastEpoch + 1)`. Every other advertiser restart (after a call, a retry, a mode change) reuses `E`. After a reboot `E` is reused only while the wall still shows the epoch of the last tick. If `E - wallEpoch > 96` lasts one hour of consistent wall time (wall minus elapsed stable within 2 min), the phone starts generation `g + 1` with a fresh day-key window and `E = wallEpoch`. An epoch, once left, is never advertised again, and repeated restarts cannot push `E` ahead. **Open issue (RH4, found in the 2026-10-11 hardening review; not changed here):** because `E = max(wall, last + 1)` never goes down, a backward step of the wall clock (a manual fix, a time zone or NITZ correction, an NTP step across a boundary) leaves `E` ahead of the wall for good. Recovery starts only above 96 epochs, so a lead of 3 to 96 epochs makes every opening fail `OPENING_STALE` (tolerance 2: the phone cannot receive a version 5 call or stream join) and contacts holding a lease younger than 14 days (window +-1) cannot recognise it until a new lease arrives. The recommended fix is a new generation once `E - wall` has exceeded `EPOCH_TOLERANCE` for an hour of consistent wall time (cost: contacts re-sync); alternatives are holding `E` until the wall catches up (one ID stays on air longer than 15 minutes, which is linkable) and a wider tolerance (a weaker forgery bound, RV9). It is an open design question; until it is decided the behaviour above stands.

**DEBUG short epoch (`test_rotid_epoch_s=<60..900>`, harness only).** Not part of the wire format and never in a release: a debug build of a debuggable package reads the extra once at cold start, before rotating discovery starts, and uses `e = floor(unix_seconds / S)` with `S` in 60..900 instead of 900, so a functional phone test sees three boundaries in `3 S` seconds. Every rule above keeps its meaning in epochs (two-epoch opening tolerance RD4, the previous-ID grace, the `E - wall` bound of RV4 in epochs of one day, the per-epoch BMH3 replay cache and signing budget, the reach-table flush), and the 10-25 minute Visible-by-handle window is 10 minutes to 10 minutes plus `S`. Presence-lease **days stay real days**: `d = floor(e * S / 86400)` (equal to `floor(e / 96)` at 900 s), so day keys, the 28-day window, leases, and the day roll behave as in a normal launch (use `test_presence_day_offset` to roll days); only the advert ID changes more often. Both phones of a test must use the same `S`: epoch numbers differ otherwise and the selected advert fails the two-epoch check as stale, by design (at `S` = 60 the tolerance is about two minutes of clock difference). `lastEpoch` is stored with its `S`; a launch with another `S` (including the next normal 900 s launch) restarts the counter at the wall epoch and keeps the generation, so no forward-jump recovery is needed; contacts' stored epoch skews, counted in the old length, are only corrected by the next lease exchange. Log line: `rotid_epoch_s: requested= | epochSeconds= | applied=`.

**Announcement version 5.** The 22-byte version 2 layout with byte 0 = `5` and bytes 1-6 = the role's RDI. A call offer's route token stays 0. Stream offers and viewer requests carry `logical XOR mask(RDI)` (Phase 1b). Old scanners reject version 5 ("Unsupported announcement version").

**Compact UUID version 2 (iPhone).** The compact v1 layout with version bits 111..110 = `10` and bits 107..60 = the RDI; it decodes to announcement version 5. A decoder without the switch rejects it like any other version.

**Link opening, hop type 13 `BDO1`.** Link hello transport-mask bit 3 (`0x08`) means "sends and accepts `BDO1` as the first hop record". Call endpoints (their link hellos, every transport) set it; from Phase 1b so do LE stream hops and a call relay's child-facing hello (never an endpoint hello, a relay's parent-facing hello, a Classic stream hop or `BGK1`). When both link hellos carry it, the first hop record in each direction is exactly one `BDO1`, before the store-and-forward dispatch; a reader rejects type 13 as unknown at any other point:

```text
"BDO1" (4) | version 1 (1) | count (1, 0..2) | count x entry (43)
entry = RDI (6) | epoch (4) | role (1) | salt (32)
```

Decoding is strict (magic, version, count, exact length). A sender opens only IDs of the role it advertised that are **pinned to this connection**: an ID that is on air, or that left the air less than 60 s earlier (the connection was accepted under it, or the boundary just passed). An ID that went off air long ago (a long call, a Visible-by-handle window, an absence) gets no fresh grace when the next one starts, and an arbitrary or older epoch is never opened. A call listener sends its role-0 entries and a call initiator count 0 (it advertised nothing); on a stream hop the connector sends role 1 and the listener role 2 (Phase 1b, below).

**Check (RV15).** The check follows the advert the caller selected, never the peer's hello. A selected version 5 or compact v2 advert requires bit 3 and an entry with that role whose RDI equals the selected 6 bytes and recomputes from the authenticated link node ID (`RDI(nodeId, e, r, salt)`); otherwise the call fails as a prefix mismatch fails today ("Peer identity changed between discovery and connection"). The entry's epoch must also lie within two epochs of the verifier's wall-clock epoch (RD4, Phase 1b item 8). A selected version 2 advert uses the prefix check, whatever the hello says. A direct version 5 call also requires the link identity to equal the end-to-end identity; a relayed one (Phase 1b) is verified end to end by the callee's `BDX1` OPENING. Verified contacts still need the full fingerprint, exactly as today.

**Rotation (RV6, RV12, RV1).** Classic call availability keeps version 2 (the Classic address is permanent and the Classic connector finds a callee by its fixed prefix; RV2), so only LE CoC and GATT call offers rotate. At each UTC boundary an idle call listener stops (break-before-make), stays silent for a uniform 1-8 s and reopens on a **new** advertising set with the new RDI. Reopening also gives a new GATT server and, on stacks with per-session LE CoC listeners (Android 11+), a new PSM; Android 10 stacks keep one long-lived listener per role (`CocListeners`, AOSP leak) and therefore the same PSM (stated residual). A call or connection in progress keeps its link. Experimental title-page sets also restart on a new set at the boundary. Within an epoch, `StableAdvertisingSet` keeps its address through the low-latency -> balanced step as before. The boundary check runs on the main-thread handler at the boundary and at least every 60 s (no exact alarm, RV16); Doze can delay it, which keeps the old ID on air longer but breaks nothing.

**Pre-handshake exposure (RV1, revised 2026-10-11).** The GAP Device Name (0x2A00) is served to any central that connects, before BMH2, and Classic name requests answer with the same adapter name. The earlier rule (rename the adapter to `Phone` whenever the switch is on) is **withdrawn**: no reference app renames the user's adapter, a rename changes the phone for headphones, car, watch and PC, an uninstall leaves it, and flipping it per session would be a timed, observable event. Two controls replace it:

1. *Non-discoverable connectable sets (API 34+).* With the switch on and `Build.VERSION.SDK_INT >= 34`, every connectable app advertising set (`StableAdvertisingSet(connectable = true)`: the call listener, the stream source's and forwarder's control servers, the waiting viewer's request) is started with `AdvertisingSetParameters.Builder.setDiscoverable(false)` (public API 34; the default is discoverable). What AOSP does with it (verified against the sources of `android14-release` to `main`): the Flags AD is added to the advertising PDU only for connectable **and** discoverable sets (`le_advertising_manager.cc set_data`; the framework counts its 3 bytes only then), so the PDU is 3 bytes smaller; the set's `discoverable` value travels with the connection (`OnAdvertisingSetTerminated`, `acl.cc`), and the GAP Device Name characteristic is registered with `GATT_PERM_READ_IF_ENCRYPTED_OR_DISCOVERABLE` (`gap_ble.cc`; present in `android14-release` and later, absent in `android13-release`), so an **unbonded, unencrypted central that connected through a non-discoverable set gets `GATT_INSUF_AUTHENTICATION` on 0x2A00** (`gatt_db.cc`). The API documents the other effect: "devices connecting to non-discoverable advertisements cannot initiate bonding" (the app never bonds over LE; enforcement of that sentence was not found in the SMP and DM sources of AOSP main, only the GATT permission above, so a Pairing Request from an unbonded central may still raise the pairing dialog, UNVERIFIED, tested in P7). Not covered, and stated: **links this phone opens as the central** (`acl.cc`: "if we are the central, the peer can always see discoverable characteristics"): an outgoing call, a relay's child link and above all a stream source or forwarder that connects to a viewer request, which anyone can copy or forge (RD2, RD3), so a bystander who advertises one fake request can read the source's adapter name (RH1); controllers with neither LE extended advertising nor vendor multi-advertising (the stack calls every connection to a legacy-only advertiser discoverable, `le_impl.h initialize_role_specific_data`, TODO b/254314964); Android 13 and older; OEM Bluetooth stacks that deviate from AOSP; and anything a Classic role serves. The in-place low-latency-to-balanced step passes the same `discoverable` value (the stack re-reads it in `set_parameters`): the value is fixed when the set starts, so a refusal that another set meets later cannot flip a running set (RH9). **Fallback (RH9):** a stack that refuses the non-discoverable start (`ADVERTISE_FAILED_FEATURE_UNSUPPORTED`, `ADVERTISE_FAILED_INTERNAL_ERROR` or an exception from `startAdvertisingSet`) gets the same set started discoverable, so a privacy flag never costs reachability. This is a privacy downgrade and is therefore visible: the status line reads "this phone's Bluetooth refused a hidden name; starting with the normal advertisement", `rotid_adv: event=rejected | label= | code= | remembered= | action=discoverable` is logged, the neutral-name advice for this phone then reads "recommended", and a refusal that is not transient (everything except an internal error) is remembered for the process. Scanners filter on the service UUID, never on Flags, and the app's non-connectable sets already carry no Flags AD, so discovery by every scanner of the app is unchanged (an iPhone is a phone test: CoreBluetooth does not filter on Flags either, UNVERIFIED). Control: DEBUG `test_adv_non_discoverable=false` (default true while the switch is on; release builds always follow the default) restores the previous sets. Log `rotid_adv: nonDiscoverable= | sdk= | extendedAdv= | multiAdv=` once per process and `nonDiscoverable=` on every `adv_set_churn` line.
2. *Explicit neutral name.* The Advanced setting **"Use a neutral Bluetooth name ("Phone")"** (preference `neutral_bluetooth_name`, **default off**, independent of the rotating switch; DEBUG launch extra `test_neutral_bluetooth_name=true`, with `test_rotating_neutral_name=true` kept as its alias so existing launch lines work) sets the adapter name to the same `Phone` on every phone, so it carries no model or person (RV1). Turning it on first asks, in plain words: it renames the phone **for everything** (headphones, car, watch, PC, Quick Share), the phone's name now is `<name>`, turning the option off restores it, and uninstalling the app while it is on leaves `Phone` until the user renames the phone in Android settings. The saved original name is stored in app preferences and **shown under the switch** for as long as the option is on, so the user can restore it by hand after an uninstall, a data clear or an emergency wipe (the name is `Settings.Secure.bluetooth_name`, written by `BluetoothAdapter.setName`, so it survives crash, force stop, reboot and uninstall; only the saved copy is lost). The advice text next to the switch says it is **recommended** on Android 13 and older, on a legacy-only controller and when Classic roles are used, and **not needed for connections that phones make to this phone** on API 34+ phones with extended or vendor multi-advertising when non-discoverable sets are active (links this phone opens itself still show the name to the other side, RH1). The name is written only when the option changes and when the app starts, gets its permissions or Bluetooth turns on; **never per call, per advertising session or per epoch**. While the option is on and the app has already written `Phone` once, any other name the adapter shows later is the user's own choice and wins (RH12): the option switches itself off, their name is left alone and a message says so (`rotid_name: paused=true`). Before the first successful write, a name other than `Phone` (also the saved original after a failed attempt) is simply written over again at the next start. Switching off restores the saved name only if the adapter still reads `Phone`; a name the user chose meanwhile is kept and the saved copy is dropped. The saved original is shown under the switch whenever it exists, also while a restore is pending (switched off while Bluetooth was off). A failed `setName` keeps the saved original and is retried when Bluetooth turns on and at the next start. The preferences, including the saved name, are in Android's cloud and device-transfer backup while the manifest keeps `allowBackup="true"` (open design question): a reinstall can bring the saved name back. Migration (RH11): builds before 2026-10-11 renamed automatically while the rotating switch was on and kept the original under `rotating_discovery_name/originalName`. A normal launch that finds a saved original, an adapter still reading `Phone` and no stored choice turns the option **on** (nothing changes on the radio: the name stays) and asks once whether to keep `Phone` or restore the original (`rotid_name: migrated=kept`); a DEBUG benchmark launch has the option off and restores the test phone's name (`rotid_name: migrated=true`). A DEBUG benchmark launch changes the name only with the extra above, so test phones keep their names and the legacy Classic candidate plan (which matches bonded phones by name) never sees several phones called `Phone`. After an emergency wipe the name stays as it is and the option reads off.

The PSM characteristic stays readable before the handshake; it rotates with the listener as above. **Also readable by any connected central (RH2):** the GATT database (the service list of the system, the vendor and the app), the Database Hash (0x2B2A, `GATT_PERM_READ`), Appearance and Central Address Resolution (`gap_ble.cc`), and the link-layer version and feature exchange (chip vendor and sub-version). The Database Hash summarises the phone's service set, so it is probably the same in every epoch and differs between phones: a central that connects and never completes BMH2 can link epochs with it (UNVERIFIED, measured per phone in P7). A party that completes BMH2 learns the identity anyway, so this matters for silent probes, which the stranger tarpit (RV8) slows.

**Address reuse on legacy-only controllers (RH7-RH9).** AOSP gives a new advertising set a new resolvable private address only when the controller supports LE extended advertising or the vendor multi-advertising commands; with neither, the set advertises with the host's initiator address (`le_advertising_manager.cc new_advertiser_address`: "we reuse the initiator address if we are a legacy advertiser using privacy, since there's no way to use a different address"), which changes only on the stack's own timer (a random 7 to 15 minutes, `acl_api.cc`). An app can neither choose nor read that address (`setOwnAddressType` and `AdvertisingSet.getOwnAddress` are system and privileged API). On such a phone the boundary restart changes the RDI but **not the address**, and a passive scanner links consecutive epochs by address. Everywhere else a set keeps its address for at most the stack's timer, so **a second address for the same ID inside one epoch is expected** (not a failure), and a new set after the boundary has a new address. The reuse is a property of the **gd advertising manager** (Android 13 and newer; Android 12 runs it only behind a flag, `btif_ble_advertiser.cc`); Android 10 and 11 use `btm_ble_multi_adv.cc`, which generates a fresh address for every instance and writes it with LE Set Random Address (RH5). The app detects the capability, not the address: with the switch on, `!isLeExtendedAdvertisingSupported() && !isMultipleAdvertisementSupported()` marks the phone **legacy-only (suspected)** on Android 13 and newer, **unknown** on Android 12 and **fresh** on Android 10 and 11. It logs once per process `rotid_address_reuse: source=capability | extendedAdv= | multiAdv= | sdk= | status=suspected|fresh|unknown` (no address, no identifier; the test `multiAdv` is false for a vendor multi-advertising controller with fewer than five instances, so `suspected` can be wrong and the tracker is the ground truth). A legacy-only controller has exactly one advertising instance (`controller.cc`, enforced by `allocate_advertiser`; Android 10 `ReadInstanceCount` also returns 1): two app sets on air at once prove `fresh`, repeated `ADVERTISE_FAILED_TOO_MANY_ADVERTISERS` on a second set supports `suspected` (`adv_set_probe: free=` measures it), and on such a phone the call listener, discovery, title and reach sets and system advertisers compete for the one slot (RH6), shows in Settings below the switch "This phone's Bluetooth chip may keep its address when the ID changes, so a scanner nearby could still link your IDs; rotating IDs protect less here", and marks the neutral name as recommended. A DEBUG scanner logs `rotid_address_reuse: event=observed | scanner= | address= | node= | previousNode=` when an address announces a new RDI. `tools/rotid_tracker.py` reports per phone the count of "new ID under the same address" (**blocking for P5**, one gate for every phone: reuse across a boundary is a privacy FAIL for that phone, reported next to the declared status, and the weaker-privacy note is shown; checking that the declared status matches the observation is a separate consistency line, not a pass), counts "second address for one ID inside an epoch" as INFO (sequential: Android's timer; concurrent: a second advertiser carrying the same ID, such as a relay mirror) and prints a layout census (below). Only unresolved random addresses of an unbonded scanner count: a scanner bonded to the advertiser, or holding its IRK, reports the resolved identity address (types 2 and 3) for every set, which says nothing about the advertising address (RH7); such sets are reported as INFO `address_identity_resolved`.

*Reductions now (switch on, version 5 adverts only; version 2 and Classic are unchanged):* (1) a version 5 viewer request carries `capabilitySummary = 0`: no sender or receiver reads the viewer's decode mask before the handshake (the source matches flags and token), and the link hello already carries `decodeCodecMask`, so a per-model constant leaves the air without losing matching; (2) a version 5 stream or forwarder offer advertises `streamBitrateKbps` rounded to the nearest 25 kbps (an odd adaptive or user-set value no longer marks one phone). Nothing is randomised: every field a receiver matches on keeps its exact value. The remaining per-phone constants (codec bits of calls and streams, the two user-setting bits, the transport bit, the stream's resolution and FPS) are quasi-identifiers of a few bits; they are stated in "Threats that remain", counted by the tracker's layout census (how many distinct layouts the fleet produces per kind) and discussed in PLAN "Design E" (moving the codec bits behind the handshake). *Boundary timing:* the restart stays synchronous at the UTC boundary with a uniform 1-8 s silence (RV12). Spreading the rotation over minutes (Google's Find Hub randomises 1 to 204 s) would make "an ID vanished, another appeared" a rarer event that a scanner can pair, while a synchronous boundary lets every phone in range change within seconds, which maximises the anonymity set of the continuity match. A lone phone is linked by continuity whichever offset is used; the tracker's continuity report measures it, and the constant is not tuned blind. Independent jitter per set of one phone (call, stream, title) is not added: it would not hide the phone but would spread its sets over more seconds.

**Stranger tarpit (RV8).** A call responder delays its BMH2 hello by `2^(n-6)` s (31 ms for n = 1, 1 s for n = 6, capped at 30 s) for the n-th stranger handshake in the current epoch; a handshake whose call rings is forgiven. Verified contacts are never delayed. The delay runs after the initiator's hello verified and before the responder's hello, so it bounds mass probing and battery, not privacy: anyone who connects still learns the identity, once per epoch.

**Visible-by-handle window (design decisions, RV5).** The Settings button "Visible by handle for 10-25 minutes" (DEBUG `test_rotating_visible_window`) makes LE call-ready presence and, from Phase 1b, stream and forwarder offers advertise **version 2** with the fixed prefix from now until the first epoch boundary at least 10 minutes later (`endEpoch = ceil((start + 600 s) / 900 s)`), so old builds and anyone who knows the handle can find the phone. The window starts and ends on a new advertising set (the listener restarts with the usual 1-8 s silence), and version 5 resumes with the new epoch's ID. There is no permanent dual advertising. Stated residual: every window is linkable to every other window (same prefix) and to the part of the epoch just before it. The window lives in memory only; an app restart ends it. Once over it is latched off, and it never outlasts 25 minutes of elapsed time, so a wall clock moved back cannot revive or stretch it; a window that ends between boundaries restarts the listener at once.

**No handle before the handshake (RV3).** A version 5 caller is "Nearby phone" with no handle and no check mark before connecting (unless recognised, below); the handle appears only after the handshake. No connection is ever started by a match; retries only continue a call the user started.

**Phase 1b: streams, viewer requests and forwarders (LE CoC and GATT).** Classic stream roles keep version 2 (permanent address, RV2); so do the DEBUG direct-receiver mode and `BGK1` group hops. Reviewed 2026-10-11 by an independent reviewer; findings RD1-RD7 are marked where they changed the text.

1. *Stream offers.* A source's or forwarder's stream offer is version 5 with that phone's **role-1 RDI** in bytes 1-6 (version 2 with the fixed prefix only inside a Visible-by-handle window, which covers stream offers as well as call offers). The route token is `logical XOR mask(RDI)`, the unchanged `StreamRouteToken` arithmetic over the six advertised bytes, so it changes with the RDI while the logical token stays the stream's random value for its whole lifetime. A running public stream therefore stays linkable by its logical token, by design (RV14: `logical = token XOR mask(RDI)` is computable by anyone); the phone's identity is not on air and the next broadcast has a new token.
2. *Viewer requests.* The request's version **mirrors the selected offer's**: a version 5 offer gets a version 5 request with the viewer's **role-2 RDI**; a version 2 offer gets a version 2 request with the fixed prefix, because a version 2 source cannot decode version 5 and checks "link prefix = announced prefix". A rotating viewer that joins a version 2 source therefore shows its fixed prefix while its request is on air (bounded by the connection wait; the app logs `rotid_downgrade: role=viewer` and shows the status line "This source does not support private discovery; your phone's ID is visible while you join."). Stated residual (RD2): anyone can advertise a decoy version 2 offer carrying a stream's logical token, so a viewer that taps the decoy row broadcasts its prefix; the decoy's owner would learn the same identity from the handshake if it connected. The route token is copied from the selected offer. `FLAG_ROUTE_RECOVERY` is set on a version 5 request only together with the **recovery hint** (item 5) in the six spare bytes; without a hint the flag is clear and the bytes are zero.
3. *Token grace.* A source or forwarder accepts a viewer request whose token equals its current route token or one of the **two** it replaced most recently, each for 60 s after it was replaced (version 2 and 5 tokens alike). A viewer copies the token of the newest offer it received before it starts its request and keeps it for the wait (no scan runs while it waits), so a join is valid across one boundary; a wait that outlasts the grace is retried. A forwarder derives the logical token from the **announced** bytes of the offer it joined (`logical = token XOR mask(announced 6 bytes)`), not from the authenticated node ID's prefix.
4. *Link opening on stream hops.* Link hello bit 3 is signed by an LE stream hop (source, forwarder and viewer, and the forwarder's child link) when the experiment is on; never by a Classic hop or a `BGK1` group hop. With both hellos carrying it, the first hop record each way is one `BDO1`: the **connector** (source or forwarder) sends its pinned **role-1** entries, the **listener** (viewer) its pinned **role-2** entries. Each side checks the advert it selected (RV15): a viewer that selected a version 5 offer requires a role-1 entry in the connector's `BDO1` that recomputes to the six selected bytes from the connector's authenticated link node ID; a connector that selected a version 5 viewer request requires a role-2 entry from the listener. A selected version 2 advert uses the prefix check, whatever the hello says (a `BDO1` that arrives anyway is read and ignored). After a passing version 5 check the endpoint hello must still come from the same node ID as the link (`endpoint.peerNodeId == link.peerNodeId`), the existing hop-local rule; forwarded media keeps its source-node-ID grant check. DEBUG `rotid_open: role=stream|viewer | result=`.
5. *Admission keys and recovery.* A source keys a pending version 5 viewer by its announced six bytes **and its advertising address** (RD3: a copy of someone else's advert from another address is a separate attempt that fails at the opening and cannot starve the real viewer) and, after the link handshake, by the authenticated node ID; a second authenticated link from a node that already has one **replaces the older link** (a viewer whose request rotated while its first link was dying). Recovery hint (`RecoveryHint`, domain `.../Recovery/2`): `Khint = HKDF-SHA256(Kmedia, salt = 32 x 0x00, info = "BluetoothVideoMesh/Discovery/Recovery/2")` and `hint = HMAC-SHA256(Khint, domain || 0x00 || failedNodeId (16) || u32 logicalToken || viewerRdi (6) || u32 routeToken)[0:6]`, where `viewerRdi` and `routeToken` are the request's own bytes 1-6 and token (RD3: the hint changes every epoch, so nothing constant crosses a boundary, and a hint copied into another advert matches nobody). `Kmedia` is the forwarded-stream key a viewer received in its parent's `BFG1` grant; the source holds the same key as the sealer key of that child's end-to-end session. A viewer whose parent is the source itself has no such key and sends no hint. A source that gets a version 5 recovery request computes the hint for each connected child it holds a key for, from the request's advertised ID and token; a match makes the viewer that child's replacement exactly as version 2 does (heartbeat probe, then admit), no match means the ordinary admission path. A bystander can still copy a viewer's whole advert and spend the source's single over-capacity probe slot for one connection timeout (12 s), as any fake viewer request can; the copy cannot open the viewer's RDI, so nothing is admitted.
6. *Rotation (RV6, RV12).* At a boundary the app's stream sets restart together, break-before-make, each on a new advertising set after a uniform 1-8 s silence: the source's offer set and title-page set, a waiting viewer's request set, and a forwarder's offer set and title-page set (a title page carries the route token, so it is rebuilt with the new token rather than restarted unchanged). A link in progress does not depend on any set. A viewer's request set rotates only while it is still waiting for its parent; its GATT/CoC service and PSM stay for that wait (stated residual: a viewer that waits across a boundary keeps its PSM). A forwarder with a child stops advertising anyway and has nothing to rotate. Restarts inside an epoch (a capacity-generation change, a pause) reuse the epoch's RDI (RV4).
7. *Pins (section 6).* Role 1 and role 2 have their own pins (`OpeningPins` per role). A connector evaluates its pins when it sends `BDO1`, a listener when it accepts the connection; a role's ID stays openable for 60 s after its set left the air. A viewer holds one selected ID, so a join that straddles a boundary by more than that 60 s fails as "identity changed" and is retried (RD7, residual).
8. *Epoch window of an opening (RD4).* A verifier accepts an opening entry only if its epoch is within two epochs of the verifier's own wall-clock epoch (`DiscoverySelectionCheck.EPOCH_TOLERANCE`); otherwise the result is `OPENING_STALE`. Without the bound a forger could build one 2^48 table for a fixed epoch and invert any victim ID of any epoch; with it the forgery cost is per target and epoch again (RV9). A phone whose advertised monotonic epoch `E` is more than two epochs ahead of the verifier's clock (RV4 forward-jump window, up to a day) is not callable until it recovers; this fails safe.
9. *Scanning.* Every stream or viewer-request scan passes the experiment's switch to the decoder (version 5 and compact v2 become visible) and filters by the token window of item 3. With the experiment off nothing here runs and the filters are the old exact-token tests.

**Definitions that two implementers must share (review finding).** *Epoch* is the phone's own monotonic `E` wherever it advertises, flushes a table or computes a skew; the verifier's window (item 8) compares an entry's epoch with the verifier's **wall-clock** epoch. A connection is *accepted* when the CoC listener's `accept` returns or the GATT server reports the connection, before any record is read; pins are evaluated then. *Previous RDI* (poison reverse) is the RDI of epoch `E - 1`. An iPhone compact v2 viewer request has no field for a recovery hint, so an iPhone viewer sends none. `FLAG_ROUTE_RECOVERY` without a hint is never sent by a version 5 request.

**Phase 1b: call endpoints and relay chains.**

1. *Endpoint hello bit 3 (`0x08`).* Every call endpoint with the experiment on signs it in its end-to-end hello, on every transport; never a stream endpoint, forwarder or `BGK1` hello. When both endpoint hellos carry it, the **callee's** first end-to-end content record is exactly one `BDX1` **OPENING** (content type 11), queued when the Invite arrives and ahead of any label, Ringing or Decline (RD6: the relay guard then needs no exception, because the OPENING is only ever sent in answer to an Invite). The caller sends none (it advertised nothing). Type 11 is rejected as unknown by every opener that did not advertise bit 3. The OPENING carries the role-0 entries **pinned when the connection was accepted** (evaluated at accept, not at send time: a relay chain can take minutes to deliver the Invite).
2. *Check.* A caller that selected a version 5 offer requires the callee's first end-to-end record to be that OPENING (anything else, or none, ends the call) and a role-0 entry in it that recomputes to the six selected bytes from the callee's **endpoint** node ID (authenticated by the end-to-end hello, so it holds through relays), within the epoch window of item 8. A direct call also keeps the link `BDO1` check and requires endpoint node ID = link node ID. Over a relayed route only this record proves the callee, so the caller queues its Invite first and its signed labels (name and subject) only after the OPENING has passed; the callee takes labels before or after the Invite alike. A hello without bit 3, a missing OPENING or a mismatch fails the call as a prefix mismatch fails today ("Peer identity changed between discovery and connection"). A selected version 2 offer keeps the end-to-end prefix check, and an OPENING that arrives anyway is not examined.
3. *Relay chains.* A call relay with the experiment on decodes version 5 call offers (every scan of a relay passes the switch) and mirrors the child's offer unchanged, version and RDI included, at route cost + 1 (`PrivateCallRelayChain.parentOffer` copies the child). Its **child-facing** link hello also signs bit 3 and the relay is the connector: for a cost-0 child it sends `BDO1` count 0 and requires the child's `BDO1` to open the mirrored RDI (role 0) for the child's link node ID; a cost 1-3 child is another relay (its hello has no bit 3, so no opening) and keeps today's admission, which skips the prefix comparison for version 5 (`matchesCallee` has no meaning for an RDI). Its **parent-facing** hello never signs bit 3: a relay cannot open the callee's ID. The caller's link to the first relay therefore carries no opening, and a caller may call through a relayed version 5 offer (Phase 1 refused it), verifying only end to end by item 2. An on-demand relayed-call helper (Design C) is different: it is a call listener with its own offer, signs bit 3 on its link hello and sends its own `BDO1` before the `SETUP` it reads.
4. *Relay guard.* Unchanged: the callee's first end-to-end content record after the handshake is still its answer to the Invite, because the OPENING is only sent after an Invite.
5. *Residuals.* A relay sees the mirrored RDI (not the callee's prefix) and, as today, both signed endpoint hellos and so both node IDs. The version 5 forgery cost is unchanged (RV9, RD4). `BDX1` records of different kinds have different lengths, so a relay on the path can tell a pair of mutual contacts exchanging leases from the record sizes (stated residual; padding would cost up to 900 bytes per record).

**Recognition and presence leases (Phase 2, RV3, RV10, RV11, RD1, RD5).** Call sessions only, and only between **mutual verified contacts**: each side has the other's full fingerprint in its verified-contact store (QR or safety code) and keeps the per-contact switch "Can see when I'm nearby" on (default on; Q4).

1. *Daily leases (RD5).* Contacts receive the phone's **daily** day keys `L_d` (independent random keys, "Keys and epochs") for today and the next 27 days: a `PRESENCE_LEASE` of up to 28 keys, 914 bytes, the exact bytes of the wire format that earlier builds sent with HMAC-derived keys, so contacts need no change to store or use them. A holder can resolve IDs of days from its delivery on, so a seized or forgotten contact phone cannot resolve what a passive sensor logged more than the current day before the delivery; and since the keys are independent a holder of day `d` learns nothing about day `d + 1` that it was not given. Salts are keyed by `L_d(e)`; the reviewed vectors hold with their key read as `L_d`.
2. *Session flow.* Once the call is **answered** (the callee accepted; an OFFER to a call nobody answered would tell the peer that this phone holds its fingerprint, RD6), a side that qualifies sends one `RECOGNITION_OFFER`. A side that has both sent and received an OFFER in this session sends one `PRESENCE_LEASE` (generation, its current monotonic epoch `E`, today's day and 27 more) as soon as the second OFFER event happens. **At send time** one locked step in the vault (`PresenceVault.deliverLease`) re-checks that the peer is still a verified contact, that the switch is still on and that the store is persistent, records `deliveredGeneration` durably **before** the lease is returned and builds the lease from that one state's key and generation; if any check or the write fails nothing is sent (RD1: a Forget, a switch-off or a revocation between OFFER and LEASE cannot leave a lease on a peer that was just revoked, and a revocation that follows finds the record). An OFFER that is withheld at its own send-time check means this side never offered: it then sends no lease and stores none. The Keystore and disk work of these steps runs off the call's reader thread. A lease is stored only if this side sent an OFFER, received the peer's OFFER, and the authenticated peer fingerprint is VERIFIED in the store right now. A second OFFER or LEASE in a session, an undecodable record, a LEASE without the OFFER handshake, or a peer that is not a verified contact is dropped with `SECURITY DISCOVERY RECORD REJECTED reason=`; it never fails the call. One-sided verification therefore gives the other side nothing: a poster's QR code scanned by a stranger yields no lease.
3. *Receiver rules* (`ContactPresence.receive`): a higher generation replaces the stored record; the same generation merges the delivered days and drops days before the first delivered one, but only if every day both sets contain has the same key, otherwise the record is **replaced** (a sender whose counter was lost can reuse a generation number for a different key; RD1d); a lower generation is ignored (a contact cannot roll a lease back); the skew `sender epoch - my epoch` is clamped to +-30 days; at most 32 days are kept. **Pruning:** at each tick and on every receipt a contact record deletes the days before `dayOf(myE + skew) - 1` (the days its recognition table can no longer use; RH6), so a seized lease holder does not keep the keys of days that are over.
4. *Store* (`PresenceStore`, file `identity-verification/presence-leases.bin`): sealed with the verified-contacts Keystore key (`AtRestCipher`, alias `bluetooth-video-mesh-verification-v1`), atomic writes, never overwritten while unreadable (the same cause classes as `VerifiedContactStore`: corrupt latches until reset, Keystore and I/O errors retry; "Reset presence key" is the reset for a corrupt file: it deletes it, raises the counter and starts a fresh generation, losing the lease records in it). While the store is unreadable the key is re-read at most every five seconds. Contents: this phone's presence state (`generation` and the day-key window: `day, L_d` pairs, 28 to 29, never a master key) and, per contact node ID, the switch, `deliveredGeneration` (the generation of the last lease sent to them, 0 = none), and their lease record (generation, skew, received time, up to 32 `day, L_d` pairs). The file is `"BPS1" | version 2 | generation (4) | key count (1) | count x (day (4), L_d (32)) | contact count (2) | contacts`; version 1 held one `P` instead of the key block. **Migration:** a version 1 store, and the Phase 1 plain `rotating_discovery_presence_key` file (imported at first use and deleted), are converted once at load: the keys of the current window are derived as `L_x = HMAC-SHA256(P, "BluetoothVideoMesh/Discovery/Lease/2" || 0x00 || u32 x)` (so leases already delivered to contacts stay valid and the generation is kept), the version 2 file is written, and `P` is zeroed and never stored again; the derivation exists only for this step and for the migration vectors. If the converted file cannot be written the phone keeps using the derived keys in memory and retries at the next load, and never uses `P` after the conversion (RH5). The **generation counter** that survives a lost or restored store is the epoch-clock state's `generation` (preferences, written with `commit()`): a new window always takes a generation above every one ever used (RD1). On load, a stored state whose generation is **below the counter** is treated as revoked or rolled back and its keys are replaced (contact records are kept). While the store is unreadable the phone advertises with an ephemeral in-memory window (random keys, nobody recognises them), sends no OFFER and recognises nobody; it never regenerates over an unreadable store.
5. *Recognition table* (`RecognitionTable`): rebuilt in full at each tick (RV10), when a lease is stored or removed and when the contact set changes, for roles 0 and 1 and epochs `myE + skew + [-1, +1]` (`[-8, +8]` while the lease record is older than 14 days) that a held lease covers; role 2 is never recognised. Each decoded version 5 or compact v2 call or stream offer does one hash-map lookup. A hit shows the contact's own label and "seen nearby, unconfirmed", **never a check mark** (anyone can replay a contact's RDI) and never a reason to connect: no retry, reconnect or exchange starts from a hit (RV3, until BMH3). Two contacts on one RDI (about 2^-48 per pair) show as an ordinary nearby phone. The check mark appears only after the handshake and full-fingerprint check, as today.
6. *Generations (revocation).* The owner starts a new generation (a whole new window of random day keys; contacts' other records stay) when: the user forgets a contact it had delivered a lease to, turns that contact's switch off after delivery, resets the verified contacts (when any lease was delivered), presses "Reset presence key", the forward-jump recovery of RV4 runs, or the emergency wipe runs (the identity changes then anyway). **Revocation fails closed (RD1):** the counter is raised first; if the new state cannot be stored the old keys are dropped from memory at once, an ephemeral window serves until the store works, and when the store is unreadable at the moment of a Forget, reset or switch-off the counter still moves, so the next load replaces the stored key. Other contacts keep recognising nothing from the old key; each gets the new leases at the next mutual session. Turning the switch off for a contact that never received a lease changes nothing on the wire. A contact deleted here also drops its stored lease record. A Forget or a reset that ran while the experiment was **off** cannot reach the vault, so the next start with the experiment on reconciles the vault with the verified-contact store off the main thread: records of contacts that are no longer verified are dropped and, if a lease of the current generation went to one of them, a new generation starts (skipped when the verified store cannot be read consistently).
7. *Not in this phase:* no automatic connection, no Contacts-only gating (RV13), no lease delivery outside a live answered call.

**Residuals (Phase 2).** A lease holder (a contact, or anyone with that contact's unlocked phone or an extracted store) recognises this phone from the delivery day for up to four weeks, or until the generation changes; it can no longer resolve days it has already pruned (RH6), and it cannot compute a day it was not given (the keys are independent). A forgotten or revoked contact still holds its old daily keys (valid for those days), this phone's node ID and fingerprint, the old generation number and, roughly, when the two last met; a generation change also tells every remaining contact that a revocation happened. A recognised hit is a hint a replayer can fake.

**`BDX1` formats.** `BDX1` = BME1 content type 11, calls only, sent only when both *endpoint* hellos carry bit 3 (Phase 1b and 2, above):

```text
"BDX1" (4) | kind (1) | body
  1 OPENING           count (1, 0..2) | count x entry (43)                 (the BDO1 body after its version byte)
  2 RECOGNITION_OFFER reserved (1) = 0
  3 PRESENCE_LEASE    generation (4, >= 1) | sender epoch (4) | first day (4) | count (1, 1..28) | count x L_d (32)
```

Decoding is strict; a receiver drops and logs any other kind or length and never fails a call. Receiver rule for leases (design decision: mutual verified contacts, per-contact switch on by default, 4 weeks, delivered as 28 daily keys): see "Recognition and presence leases" above (`PresenceLeases.kt`).

## Experimental BMH3 identity-hiding link handshake (on by default for user sessions since 0.2.0-beta)

Settings > Features "Hidden identities" (feature id `bmh3`, DEBUG benchmark extra `test_bmh3`; default ON for user sessions since 0.2.0-beta, one constant `ConnectivityFeatureDefaults.BMH3`, a stored choice wins, a DEBUG benchmark launch reads only the extra; the BMH3 test steps 1, 3 and 6 passed on the S24 and ASUS, steps 4, 5, 7, 8, 10 and 11 not yet run). Sub-options, DEBUG extras only: `test_bmh3_only` (an initiator never speaks BMH2), `test_bmh3_contacts_only` (a responder reveals itself only to a holder of its lease key; `test_bmh3_test_lease=<64 hex>` supplies a fixed lease key for phone tests, standing in for real presence leases until Phase 2). Design 2026-10-11, built on an earlier SIGMA draft that a independent security review corrected (findings SR1-SR14) and then reviewed again in this form by a second independent reviewer (findings BR1-BR11); both are adopted below and recorded in PLAN "Design F". With the switch off every byte on air and on the link is unchanged, and a BMH3 message is rejected exactly as by an old build. Phase 1 covers **private calls and message exchanges** (the call endpoint's link and end-to-end handshakes, direct and through DEBUG call relays); streams, viewers, forwarders, the stream relay, the group harness and Design C reach-page routes keep BMH2 (PLAN "Discovery privacy" item 5). Not yet tested on phones.

**Why.** BMH2 hellos are signed but not encrypted. A sniffer that follows a connection reads both identity keys; anyone who connects learns the responder's key; a sniffed hello can be replayed to draw out the other side's hello (RV13); relays see both endpoint hellos. Rotating discovery IDs hide the advertisement only: bitchat's own design note (docs/PEER-ID-ROTATION.md section 1) says rotating IDs accomplish nothing while a handshake sends the static key in the clear. BMH3 is the handshake that closes this: each side first sends only a one-time key and a nonce, and identities, capabilities, signatures and key confirmation then travel encrypted under keys derived from the one-time exchange.

| Observer | BMH2 | BMH3 |
| --- | --- | --- |
| Passive sniffer on a hop | both identity keys and both capability sets | one-time keys (random), message sizes and timing, and which order was used (3 or 4 messages) |
| Active attacker who connects (stranger, prober) | the responder's identity key | Everyone mode: the responder's identity (once per connection, rate-limited by the signing budget). A Contacts-only responder (below): nothing, unless the attacker holds its lease key |
| Active attacker who answers (fake or replayed advert), **when the caller speaks BMH3** | the initiator's identity from its first hello, and a replayable signed hello | nothing at the end-to-end layer, and at the link layer toward a relay a throwaway key instead of the real one: the caller reveals only after the answerer's signature, key confirmation and the discovery-binding check passed |
| Same attacker, caller speaks BMH2 (version 2 advert without hint or pin, or a BMH2 phone) | the initiator's hello | the same: BMH3 changes nothing for a caller that does not speak it (see "Stripped hint") |
| Relay on a chain | both endpoints' hellos | its two neighbours' link identities only (and with the throwaway key, not even the caller's); a one-relay chain still sees both endpoints, because both are its neighbours |
| Later theft of an identity key | identities were public anyway; session keys were already forward secret | past session keys and past identities stay secret (the identity key only signs) |

**Primitives (all already in the app).** ECDH P-256 (`KeyAgreement("ECDH")`), HKDF-SHA-256 (Extract and Expand over the app's HMAC), AES-256-GCM (`MeshAead`), ECDSA-P256-SHA256 with the Keystore identity key (`SigningIdentity.sign`; same key, alias and purposes), HMAC-SHA-256. No library, key type or Keystore purpose is added.

### Negotiation and downgrade

The initiator chooses before it sends a byte and never retries with BMH2 after a BMH3 attempt failed (an attacker who drops BMH3 gets a failed connection, not a cleartext hello). With the switch on:

| Selected offer | The initiator speaks | Why |
| --- | --- | --- |
| Rotating (version 5) call offer | **BMH3, always** | A fake or replayed rotating advert could otherwise leave the hint out and collect the caller's BMH2 hello (BR1). Old builds cannot produce or decode version 5, so BMH2 would only ever be a downgrade. Cost: a phone with rotating IDs on and BMH3 off cannot be called by a phone with both on. |
| Version 2 call offer with the hint, or a pinned prefix, or `test_bmh3_only` | BMH3 | The callee said so (hint), this phone has seen it speak BMH3 (pin), or the user wants no BMH2. |
| Version 2 call offer, none of those | BMH2, exactly as today | Old phones stay reachable. This is today's exposure, not a new one. |

- **Hint.** `capabilitySummary` bit 5 (`0x20`, `Bmh3Hint.SUMMARY_BIT`) of a **version 2** private-call offer, set by the callee at route cost 0 (not on a relay-helper offer): "this identity accepts BMH3 handshakes". It is not set on version 5 offers (they imply BMH3 for BMH3 initiators; the bit would only be another stable quasi-identifier). Readers of call offers test only codec bits, bit 4 (relay consent) and bit 3 (dual); stream offers compare the whole byte and never carry it. A DEBUG call relay mirrors the child's summary one hop further, so a caller reads it at any route cost and assumes the relay runs the same build (call relays are DEBUG only). The iOS compact encoder cannot represent bit 5 and must mask it (open item, iOS repository).
- **Pin.** After a BMH3 handshake whose answerer proved itself the peer's 6-byte node prefix is remembered (at most 256, oldest dropped, each valid 30 days after its last success) in `noBackupFilesDir/hidden-identity-pins.txt`: never part of a cloud backup or device transfer, deleted by the emergency wipe. A later version 2 offer with a pinned prefix is contacted with BMH3 even if the hint was stripped. The expiry bounds how long a peer that turned the feature off stays unreachable; a user-confirmed BMH2 retry that clears the pin is a follow-up (PLAN).
- **Responder.** With the switch on, a call listener reads the first frame and dispatches on its magic (`BMH2` or `BMH3`). An **Everyone-mode** listener accepts both: refusing BMH2 would protect nobody, because the initiator's hello is already sent and a prober can still obtain the identity through BMH3, and it would strand old builds and phones with rotating IDs but no BMH3 (a rotating-ID phone should therefore not refuse BMH2 with strangers; the protection is on the caller's side, above). A **Contacts-only** listener always refuses BMH2 (silent close), because a replayed BMH2 hello would draw out its own hello (RV13).
- **Stripped hint.** The hint is unauthenticated. An attacker that strips it from a version 2 advert, or that answers a forged legacy advert, makes an unpinned hint-driven initiator speak BMH2, which hands its signed hello to the attacker (SR3): the same exposure as today. Mitigations: pins after a first contact, `test_bmh3_only`, and rotating IDs (which are always BMH3). A signed "BMH3 capable" bit in the BMH2 capabilities was considered and rejected: it could be read only after the initiator's hello was sent, and an attacker simply omits it.
- **Link to a relay.** At route cost above 0 the link peer is a relay that cannot be bound to the selected advert, and route cost is an unauthenticated hint, so a fake relay could answer R_FIRST and collect the caller's link identity (BR2). The caller therefore presents a **throwaway software key** at the link layer toward a first hop at route cost above 0; relay admission uses node IDs of the neighbours (the caller is never the callee or the relay), so it is unaffected, and the end-to-end handshake still proves the real key to the callee after the callee proved itself. Not covered in Phase 1 (stated residuals): a Design C helper is called at route cost 0 on its own advert and learns the caller's link identity, and a route chosen from an unauthenticated reach page keeps the end-to-end handshake on BMH2 (reach pages carry no capability summary) unless `test_bmh3_only` or a pin says otherwise.
- **End to end.** The caller speaks BMH3 end to end when it spoke BMH3 on the link (the same choice), otherwise BMH2. The callee dispatches on the first end-to-end record's magic.

### Messages

All integers are big-endian. Link messages travel as `u32 length | message` on the raw RFCOMM, LE CoC or GATT byte stream (length 1..2048), like BMH2; end-to-end messages are the payloads of `BMS1` type-4 records, like BMH2 endpoint hellos. A message ends where its frame or record ends. Each message is built, signed and sealed once; a retransmission, if a carrier ever needed one, resends the identical bytes (re-signing with ECDSA's random k and re-sealing under the same key and zero nonce would reuse a GCM nonce).

```text
header (8)  "BMH3" | version 1 | purpose (1 link, 2 end to end) | message number | flags (unknown bits must be 0)

msg1  I -> R  header(1, flags) | offer 0x01 | e_I (65) | n_I (32) | tag (16)                      122 bytes
              flags bit 0 MAY_REVEAL_FIRST: the initiator would accept I_FIRST
              offer 0x01 = P-256 ECDH, HKDF-SHA-256, AES-256-GCM, ECDSA-P256-SHA256 (the only suite)
msg2  R -> I  header(2, flags) | e_R (65) | n_R (32) [ | AEAD(k_hs_r2i, B_R) ]                  105 if flag 0, 431 if flag 1
              flags bit 0 R_FIRST: 1 = the responder's block follows, 0 = nothing follows
msg3  I -> R  header(3, 0) | AEAD(k_hs_i2r, B_I)                                                 334
msg4  R -> I  header(4, 0) | AEAD(k_hs_r2i, B_R)           (I_FIRST only)                       334
```

`e` is an ephemeral P-256 public key in SEC1 uncompressed form `04 | x | y`; `n` is 32 random bytes; `tag` is the contact tag (below) or 16 random bytes, indistinguishable on the wire. A responder that would answer I_FIRST and sees `MAY_REVEAL_FIRST` clear closes without replying (normative, not a hint). AEAD is AES-256-GCM with a 12-byte all-zero nonce, a 16-byte tag and associated data = the message's cleartext part (msg2: its first 105 bytes; msg3 and msg4: the header). Each handshake key encrypts exactly one message, so the fixed nonce never repeats under one key. That holds only if `e_I`, `n_I`, `e_R` and `n_R` are fresh from the platform CSPRNG for every handshake: **a responder must never cache, precompute-and-reuse or resend a msg2** (SR5).

**Identity block `B`** (the plaintext inside the AEAD, always 310 bytes):

```text
SPKI length (2) = 91 | identity SPKI (91) | capabilities (7) | extension length (2) = 112 | extensions (112) | signature (64) | finished MAC (32)
```

The identity is the canonical 91-byte P-256 SubjectPublicKeyInfo (`3059301306072a8648ce3d020106082a8648ce3d030107034200 | 04 | x | y`, the point validated as above); the node ID is `SHA-256(SPKI)[0:16]`, computed by the receiver. A key whose platform export is not that exact form is re-encoded first, so one key has one node ID. Capabilities are the existing `NodeCapabilitiesCodec` version 1 bytes (the link or end-to-end hello contents, unchanged). The signature is raw `r | s` (IEEE P1363) with `0 < r, s < n`; Keystore's DER output is converted (strip the sign byte of each integer, left-pad to 32 bytes) and JCA verification re-encodes. The MAC comparison is constant time. Every block has the same size: the extension area is always exactly 112 bytes, filled by a `PAD` extension. This hides an `INTENT` and any later extension inside the handshake; it does not hide that rotating IDs are in use from a sniffer, because the `BDO1` and `BDX1` records that follow still have sizes that depend on the pinned IDs (BR7, stated residual; removing them when both sides speak BMH3 is a follow-up that touches the rotating-ID code).

**Extensions** (`type (1) | length (2) | value`, strictly ascending types, each at most once, the area parses to exactly 112 bytes; a type from `0x80` is critical and fails the handshake if unknown, a lower unknown type is skipped):

| Type | Name | Allowed in | Value |
| --- | --- | --- | --- |
| 0 | `PAD` | any block | zeros, first in the area |
| 1 | `OPENING` | responder blocks only (msg2, msg4) | the rotating-ID opening body of `BDO1` after its magic and version: `count (1, 0..2) \| count x entry (43)`. A rotating-ID listener includes the entries pinned when the connection was accepted whatever the initiator signed (it cannot see the initiator's hello bits); in msg2 the initiator checks it **before** it reveals itself, in msg4 (I_FIRST) after |
| 2 | `INTENT` | msg3 under I_FIRST only | 1 byte: 1 call, 2 stream, 3 store-and-forward exchange, 4 relay; reserved for an "ask first" mode, v1 senders omit it |
| 3 | `BUILD_TAG` | either block of a **link** handshake only | 2 bytes, the u16 of "Build tag in the link hello" (bit 15 = project release key, bits 14..0 = release number 1..32767); sent only while the "Tell me about newer versions nearby" switch is on; a value that is not a valid tag counts as none |

A known type outside its allowed place fails the handshake (a `BUILD_TAG` in an end-to-end block included: bit 7 means call video fragments there). Everything the app can send together fits: two opening entries (`OPENING` 3 + 1 + 86), an `INTENT` (4) and a `BUILD_TAG` (5), behind a `PAD` of at least its own 3-byte header.

**Build tag (the updater's "newer version nearby" hint).** BMH2 carries it in two cleartext places of the link hello (transport-mask bit 7 and nonce bytes 0-1), so a sniffer reads the release number and the project-key bit. BMH3 has no such field to borrow: its nonces are fully random and bit 7 stays unused in its capabilities. A link handshake carries the tag as the `BUILD_TAG` extension inside the sender's own encrypted, signed block, so only the authenticated peer reads it and a sniffer learns nothing from it (the block size does not change). The receiver rules of "Build tag in the link hello" apply unchanged: the tag is the peer's claim about its own build, it is taken only from a verified block, it reaches the notice only from a link this phone opened (`SecureBluetoothSession.peerBuildTag` is set on both sides, `LinkBuildTags.report` runs on the initiating side only), and the capabilities the rest of the app sees never carry bit 7. The end-to-end handshake never carries a tag.

### Key schedule

`D` is the purpose domain `BluetoothVideoMesh/BMH3/Link` or `BluetoothVideoMesh/BMH3/EndToEnd`; every hash, key and signature depends on it, so a link message is invalid at the endpoint and vice versa. `TH(x) = SHA-256(D | 0x00 | x)`. `E(K, label) = HKDF-Expand(K, D | "/" | label, 32)`, labels ASCII.

```text
T (R_FIRST) = msg1 | msg2clear | B_R | hdr3 | B_I          T (I_FIRST) = msg1 | msg2clear | hdr3 | B_I | hdr4 | B_R
dh       = ECDH(e_I, e_R)                                    32-byte big-endian x coordinate
TH2      = TH(msg1 | msg2clear)                              the whole msg1 including tag and flags, and msg2's flags
HS       = HKDF-Extract(salt = TH2, IKM = dh)
k_hs_i2r = E(HS, "hs i2r")      k_hs_r2i = E(HS, "hs r2i")   one message each
fk_I     = E(HS, "finished i")  fk_R     = E(HS, "finished r")
dHS      = E(HS, "derived")
MS       = HKDF-Extract(salt = TH(T_final), IKM = dHS)       T_final = the whole transcript
k_i2r    = E(MS, "app i2r")     k_r2i    = E(MS, "app r2i")  the initiator sends under k_i2r, the responder under k_r2i
EXP      = E(MS, "exporter")                                 reserved for channel binding
```

For a block sent by role `X` (`Initiator` or `Responder`), let `P` be the transcript up to and including the cleartext part of the carrying message, and `prefix_X` the block up to the end of the extensions:

```text
sig_X = ECDSA-P256-SHA256(sk_X, D | "/" | X | " signature" | 0x00 | TH(P | prefix_X))
mac_X = HMAC-SHA-256(fk_X, TH(P | prefix_X | sig_X))
B_X   = prefix_X | sig_X | mac_X
```

The session keys depend on the whole transcript, so both identities, both capability sets, the tag, every flag and every extension are bound into them. After the session keys are installed each phone zeroes `dh`, `HS`, `dHS`, `MS`, the handshake keys and its ephemeral private key. The first `BMS1` (or `BME1`) record in each direction uses sequence 0 under its own direction key; a unit test pins both first records, so a swapped direction mapping (one key, repeated nonces) cannot pass.

### Order, contact tag and local checks

The responder picks the order from its **global mode** only (SR4), because it cannot know why a peer connected:

| Responder mode | Order | Who is protected from an active attacker |
| --- | --- | --- |
| Everyone (default) | R_FIRST (SIGMA-I, three messages) | the **initiator**: it verifies the answerer before it reveals anything. The responder reveals to whoever sent a msg1, which is what Everyone means |
| Contacts-only (`test_bmh3_contacts_only`, DEBUG in Phase 1) | R_FIRST if msg1's tag matches, otherwise I_FIRST (SIGMA-R, four messages): the stranger must reveal first, is silently closed unless admitted, and never learns the responder's identity | **both**, between lease holders; the responder against strangers |

**Contact tag (SR2, BR3).** A rotating-ID phone's contacts hold its daily lease keys `L_d` (this document, "Recognition and presence leases"; since the hardening these are independent random 32-byte keys, deleted when their day leaves the window, not derivations of one master key). `K_tag` needs only a pseudorandom key, so nothing about the tag changes: revocation (a new generation draws new keys) and forward secrecy (a day's key is gone after its window) come from the key lifecycle, and Phase 2 reads the responder's keys from `PresenceVault.dayKey(idEpoch, currentEpoch)` and a contact's from its stored lease record. `K_tag = HKDF-Expand(L_d, "BluetoothVideoMesh/BMH3/ContactTag/1", 32)` and `tag = HMAC-SHA-256(K_tag, TH(msg1 with the tag field zeroed) | binding)[0:16]`, with the 11-byte **binding** `selected (6) | role (1) | epoch (4)`: the 6 advertised bytes of the offer the initiator selected, the role (0, call), and for a version 2 advert the initiator's wall epoch (0 for version 5, whose RDI already changes every epoch). The binding makes a recorded tag worthless against the responder's next advert: without it an attacker who sniffed one tagged msg1 (a relay sees it in the clear) could replay it in later epochs to any Contacts-only phone and see which one answers R_FIRST, which would link the target's RDIs across a day. The initiator sends the tag when it recognised the selected ID as a contact and holds the lease for that day, otherwise 16 random bytes. The responder checks, in constant time and without early exit, each of its **own** lease keys (days of epochs `E-1 .. E+1`) against each advert it has on air or left less than 60 s ago: the RDIs of its pinned opening entries for version 5, its fixed prefix at wall epochs -1, 0, +1 for version 2 (a handful of HMACs, independent of the number of contacts). This is the idea of WireGuard's `mac1` and Briar's per-period transport tag, applied to the existing lease keys: prior shared knowledge is the only way both identities can be hidden from an active attacker, because otherwise whoever authenticates first must reveal to an unauthenticated peer (Krawczyk, SIGMA, identity-protection discussion). Replaying a recorded msg1 inside the same epoch draws a msg2 whose block is sealed under keys only the true `e_I` holder can derive, so it reveals nothing; the replay cache bounds the cost, and what remains is the timing of a signature (listed below). When a tag matched, the responder still requires after msg3 that the initiator is a current lease recipient (`admitInitiator(peer, tagMatched)`); otherwise it closes, logs and, in Phase 2, starts a new presence generation, because a lease has leaked (BR9).

**Initiator rules (SR1, BR4).** A default initiator **refuses I_FIRST**: an attacker who answers picks its own `e_R` and could otherwise demand it, collecting the identity of every user who taps Call on a forged or replayed advert. An initiator that sent a real tag also requires R_FIRST. `MAY_REVEAL_FIRST` is set, and I_FIRST accepted, only after an explicit user confirmation, which Phase 1 does not offer. When the selected row is a recognised or verified contact, the answerer's **full 128-bit node ID** must equal that contact's before the initiator reveals (an attacker who grinds a 48-bit RDI or prefix is a different key); verified contacts also keep the full-fingerprint check below.

**Checks that run before a phone reveals itself.** The existing identity checks move to just after the peer's block verified and before the phone's own block is built:

1. Not a self-connection: the peer's identity differs from the phone's own and `e_I != e_R` (SR6).
2. Discovery binding on the selected advert, never on the peer's flags (RV15). Version 2, route cost 0: the peer's node prefix equals the announced prefix. Version 5: the peer's `OPENING` opens the selected 6 bytes for the peer's node ID within the epoch window (`DiscoverySelectionCheck`). At the link layer this applies only at route cost 0 (above 0 the link peer is a relay and the caller presents a throwaway key); at the end-to-end layer it always applies to the callee. In I_FIRST the same check runs on the responder's block after msg4 and aborts the session before keys are installed (the initiator has already revealed).
3. Verified contacts: the peer's full fingerprint is compared with the verified-contact store; a `MISMATCH` under `REFUSE` closes **before the initiator has revealed anything**, which BMH2 could not do. This protects a prefix collision with a verified contact; for a rotating advert it is the expected-contact rule above that protects against a ground RDI.
4. Relay admission and store-and-forward neighbour rules stay where they are, on the authenticated peer after the handshake returns (a responder learns the initiator in msg3).
5. I_FIRST responder only: the reveal decision; anything but an admitted contact gets a silent close.

**Responder cost guards (SR11, BR5).** A stranger-facing R_FIRST responder signs for every msg1, and one fixed msg1 can be replayed at no cryptographic cost. It therefore (a) keeps a per-process cache of the last 4,096 `SHA-256(e_I)` values (a repeat is a silent close), (b) spends a token from a **signing budget** before it draws a key for a msg1 whose tag did not match: a bucket of 8 signatures refilled one per 4 s, a caller that finds it empty waits for its token for at most 4 s and otherwise the connection closes silently (the escalating RV8 tarpit is not used on this path: it would delay every unrecognised caller, contacts without a lease included, by up to 30 s after about eleven attempts per epoch), and (c) stays under the existing pending-connection and admission guards. A matching tag spends no token. In I_FIRST the responder signs only after the initiator authenticated. Keystore signing time on the six phones is measured in T14.

Any failure closes the connection with no error message: there are no alert codes to fingerprint. Local policy is enforced locally whatever the flags say; a flipped flag also changes `TH2`, so the keys differ and the AEAD fails.

### Composition with BMS1, BME1 and relays

- **Link.** The last message yields the session keys exactly where `MeshSessionKeys` are installed today; `BMS1` is unchanged (17-byte header as AAD, sequence nonce, exact-next ordering). The first record still carries what it carries today (hop type 11, 12 or 13, or the end-to-end handshake). The link `BDO1` exchange stays as it is and runs after the handshake; with BMH3 the `OPENING` extension adds the same check before the reveal.
- **Endpoint.** The end-to-end keys become the `BME1` keys of `EndToEndVideoSession` unchanged; `BFG1`, `BGK1`, `BMC2`, labels and fragments are unchanged. The callee's `BDX1` OPENING record and its checks also stay; the extension adds the pre-reveal check.
- **Pipelining.** The phone that sends the last handshake message may write `BMS1`/`BME1` records right behind it in the same write; the other phone reads them only after the final message verified. A responder never sends data after msg2 before the initiator authenticated.
- **Cost.** The responder now learns the initiator one message later than the first hello of BMH2: in R_FIRST the callee rings at the same moment as today, in I_FIRST about two hop round trips later. Bytes: R_FIRST 122 + 431 + 334 = 887 against about 638; I_FIRST 122 + 105 + 334 + 334. Compute per side: one key pair, one ECDH, one signature and one verification (as BMH2), about ten HMACs and one AES-GCM pass over 310 bytes.
- **Call relay.** `BluetoothPrivateCallRelay` copies type-4 and type-5 records in both directions without parsing, so three- or four-message end-to-end handshakes pass through it unchanged. A relay runs BMH3 with each neighbour: as an R_FIRST responder toward its parent and as an initiator toward its child. A middle relay learns neither endpoint. The stream relay harness parses BMH2 endpoint hellos and the blind group harness passes the source hello through group control; both stay BMH2.
- **Contacts-only through stranger relays.** A relay is the callee's link initiator; a Contacts-only callee answers a relay without the tag with I_FIRST and closes on a stranger relay. In v1 a Contacts-only phone is reachable directly or through relays that hold its lease.

### Platform notes

Android: identity signing is the existing Keystore `Signature("SHA256withECDSA")` over the label plus a 32-byte hash (the key authorises only `DIGEST_SHA256` and needs no user authentication); ephemeral keys are software `KeyPairGenerator("EC")`, decoded after an explicit on-curve and `0 <= x, y < p` check. iPhone (CryptoKit): `SecureEnclave.P256.Signing.PrivateKey.signature(for:)` returns the raw 64-byte form, `derRepresentation` is the 91-byte SPKI, `P256.KeyAgreement` rejects off-curve points, `HKDF<SHA256>.extract/expand` and `AES.GCM` match, and the key must be usable after first unlock without a biometric prompt. Windows (CNG): `NCryptSignHash` returns raw `r | s`; `BCryptDeriveKey` with `BCRYPT_KDF_RAW_SECRET` returns the secret little-endian and must be reversed. The Windows receiver and the iOS app stay BMH2 until updated; the iOS repository carries the vectors.

### Security argument and what it does not do

The construction is SIGMA (Krawczyk, CRYPTO 2003; proven in the Canetti-Krawczyk model, EUROCRYPT 2001 and 2002) in both reveal orders, with a TLS 1.3 shaped schedule (RFC 8446: transcript hashes, separate handshake and application secrets, Finished MACs, a role-labelled signature over the transcript hash). Its identity hiding matches Noise XX (Noise specification section 7.8: the initiator's static key "encrypted with forward secrecy to an authenticated party", the responder's to an unauthenticated one) while the Keystore key stays signing-only; Noise's static Diffie-Hellman would need a second static key per identity, and IK additionally needs the responder's key in advance and loses initiator forward secrecy. Properties: mutual authentication and session-key secrecy; no unknown-key-share (the MAC and AEAD keys come from `g^xy`, so an attacker cannot re-sign someone else's block); forward secrecy including of identities; no key-compromise impersonation; no replay across sessions; downgrade resistance inside BMH3 (the offer, flags, tag and purpose are in `TH2`); cross-protocol separation (every signed context starts with a distinct `BluetoothVideoMesh/...` domain that diverges within 19 bytes: BMH2 link and end-to-end hellos, BMH3 per purpose and role, `BNL1` labels, `BCC1` cards). Reflection fails on the AEAD keys and again on the role labels. There is no machine-checked proof; a Tamarin model of both orders is recommended before promotion.

**Not hidden or not solved** (stated, not hedged):

- **Everyone-mode responders reveal their identity to any active attacker that sends a msg1**, once per connection (the signing budget bounds the rate; it does not stop one probe). Hiding it needs prior shared knowledge (Contacts-only, above) or a pseudonymous per-epoch identity for strangers ("Phase 2: pseudonymous stranger identities", experimental, off by default). Until that switch ships on, the public tracking warning stays true for "a stranger can connect". Contacts-only is DEBUG-only in Phase 1; Phase 2 reads real presence leases.
- A sniffer sees message sizes, timing and the order (3 or 4 messages, which for a Contacts-only phone also says per connection whether the caller was a lease holder), the app's service UUID, the hint bit and the `MAY_REVEAL_FIRST` flag (stable bits), and the advertisement itself (the 48-bit prefix, or the RDI). The GAP Device Name and PSM (RV1), bonded devices' resolvable addresses (RV2) and the Classic address are separate leaks. The `BDO1`/`BDX1` record sizes show that rotating IDs are on.
- An adjacent relay learns its neighbours' identities (it authenticates them), except the caller's when the caller presents its throwaway key. A tag-free connection to a Contacts-only phone costs that phone one ECDH, and Keystore signing latency can fingerprint a phone model; a tag match skipping the budget is visible in timing under flood.
- A replayed tagged msg1 inside the same epoch still draws one signature from the true target.
- With BMH2 a sniffer reads the updater's build tag in the clear; with BMH3 it does not.
- Grinding a key with a victim's 48-bit prefix (about 2^48) passes the discovery binding toward a stranger and then receives the initiator's identity; a recognised or verified contact is protected by the expected-contact and fingerprint checks (SR13, BR4).
- A stripped hint downgrades an unpinned initiator to BMH2 for a version 2 advert (SR3, above). Design C helpers and reach-page routes, stream hops, the stream relay and the group harness stay on BMH2 in Phase 1.
- Signature coverage of the first revealer's block makes the exchange non-deniable between the two parties (as TLS 1.3 client authentication); BMH2 hellos were non-deniable and replayable.
- Post-quantum: a recorded handshake could be opened by a future quantum computer; offer bit 1 is reserved for a P-256 + ML-KEM-768 hybrid.

### Phase 2: pseudonymous stranger identities (on by default for user sessions since 0.2.0-beta, `test_bmh3_pseudonyms`)

Settings > Features "Pseudonymous toward strangers" under the BMH3 row (feature id `bmh3_pseudonyms`, a child of `bmh3`, DEBUG extra `test_bmh3_pseudonyms` next to `test_bmh3`; default ON for user sessions since 0.2.0-beta, one constant `ConnectivityFeatureDefaults.BMH3_PSEUDONYMS`; pseudonym phone test: the stranger, decline, restart and contact cases and the snoop check passed, steps 5, 6 and 8 not yet run). Design decision (2026-10-11): a stranger who connects meets a **pseudonym**, never the long-term identity; the long-term identity goes only to a verified contact (recognised through the presence leases and the contact tag) or to the other party of a call the user accepted. Design 2026-10-11, reviewed by an independent reviewer (findings PR1-PR15, adopted and rejected in PLAN "Design F"; the text below already contains the adopted changes). It needs BMH3 and rotating discovery IDs on; with the switch off not one byte differs from BMH3 Phase 1. Phase 1 of this feature covers **direct private calls**; **message exchanges and relayed calls with a stranger are refused** (they need a stable identity, below); streams are specified and not built.

**What the engine needed.** BMH3 already signs with whatever `SigningIdentity` it is given and already hides the key from a sniffer. What was missing: (1) a rule for which key a phone presents to whom, (2) a way to prove the real identity later, bound to the session, (3) keeping the salt of a rotating ID (it lets anyone who knows a node ID confirm that the phone owns the ID) from a stranger until the user decided, and (4) closing every other way a stranger could still obtain the real key (review PR1-PR4).

**Which key is presented (rule P).**

| Role | Presents the real key when | Otherwise |
| --- | --- | --- |
| Responder (callee), in msg2 | msg1's contact tag matched one of its own lease keys (the initiator recognised the advert as a contact and holds a lease for that day) | a **connection pseudonym**: a fresh throwaway key for this connection |
| Initiator (caller), in msg3 | it sent a contact tag **and** the responder's verified block was the expected contact's full node ID (the existing check) | a fresh **attempt pseudonym**, the same one at the link and the end-to-end handshake of the attempt |

The initiator decides after it verified msg2, the property of R_FIRST that makes the rule possible: it reveals the real key only to the contact it was looking for. A tag was sent but another key answered (a throwaway, a stranger, a forgery): the existing "not the expected contact" failure, so a user who tapped a contact never silently becomes a stranger call; and an initiator holding a real key refuses a responder that declared a pseudonym. A session is therefore **real-real** (contacts; BMH3 Phase 1 exactly) or **pseudonym-pseudonym**. I_FIRST (Contacts-only responders) is unchanged: the responder answers only an admitted initiator.

**The rule fails closed (PR4).** In pseudonym mode every untagged connection meets a throwaway, whatever else is true: an empty list of pinned adverts (an advert set that stopped while the listener stayed up), a Classic listener, a Visible-by-handle window. Nothing in the rule depends on rotating adverts being on air. Version 2 offers are bound by the reveal as well (the revealed node ID must carry the announced prefix).

**A refused caller fails fast (2026-10-12).** The refusal closes the link without a reply, so the caller sees the link end and its hop handshake fail. An outgoing call attempt that is not covered by the first-attempt stall guard (the 1M retry, an attempt without the guard, Classic) now also has a hop-handshake deadline of 10 s after the link opened (`CallSetupDeadlines.HOP_AUTH_MS`; measured authentication takes 71-269 ms): an answerer that keeps the link open and never answers is closed by the caller, and a link that ends early is reported as "closed the connection before the secure handshake finished"; both messages say the other phone may run an older version or accepts calls only from phones it knows (`call_setup: event=hop_auth_deadline`). The answering phone logs `incoming_handshake: result=failed | reason=<fixed reason>` (for example `bmh2_refused`) next to `bmh3: event=refused_bmh2`. The earlier prober call that waited 170 s in OUTGOING lacked this bound.

**BMH2 is refused (PR1).** An Everyone-mode listener accepts BMH2 in BMH3 Phase 1 because "a prober can obtain the identity through BMH3 anyway". With pseudonyms that reason is gone, and a BMH2 hello is answered with the real key. A phone in pseudonym mode therefore closes silently on a BMH2 first message at both layers (as a Contacts-only phone already does) and never speaks BMH2 itself (a caller's BMH2 hello would hand its real key to whoever answers, before any ring), and it cannot be reached by or reach phones that speak only BMH2 (BMH3 switched off, older builds, Design C helpers, the DEBUG relay). This is the price of the claim; the switch says so.

**Pseudonym keys.** A pseudonym is a software ECDSA-P256 key (`KeyPairSigningIdentity`), never in the Keystore, never persisted, never exported, dropped with its connection. The responder uses a new key **per connection** and the caller one **per attempt** (PR7). An epoch-wide key was considered for continuity (a redial reaches the same endpoint) and rejected: the advertised RDI already shows that, an epoch key would make one accepted reveal attribute every session of the epoch (a reveal is a transferable signature that the real key owns the throwaway) and would tie the call roles together. Nothing derives a pseudonym from the node ID, a lease key or another pseudonym (fresh CSPRNG output). The node ID of a pseudonym is `SHA-256(SPKI)[0:16]` like any other, which no code path can tell apart except through the extension below.

**Extension 4 `PSEUDONYM`.** Value empty (length 0), allowed in either block of either purpose, at most once, below `0x80` (an older BMH3 build skips it and treats the key as an identity). Meaning: *the key in this block is a throwaway; the sender expects the peer never to store it as an identity, and the sender speaks the `REVEAL` record below.* It sits inside the encrypted and signed block, so a sniffer cannot see it and nobody can add or strip it. The receiver of a block with `PSEUDONYM` does not run `PeerIdentityGate.admit` on that key (a pseudonym is not an authenticated *person*; admitting it would only fill the 1,024-entry memory of authenticated peers with throwaways), does not pin its prefix, does not look it up in the verified-contact store and shows no node ID or fingerprint. A block that carries both `OPENING` and `PSEUDONYM` fails the handshake. The area has room for it beside two opening entries, an `INTENT` and a `BUILD_TAG` (99 + 3 bytes, a PAD of at least 3).

**What the pseudonymous responder withholds (the confirmation oracle).** A rotating ID `RDI = H(nodeId, e, r, salt)[0:6]` plus its `salt` lets anyone who guesses the node ID (a public key shown on a poster or in a QR) confirm that this phone owns the ID. BMH3 Phase 1 hands the salt to every connecting stranger in the `OPENING` extension, in `BDO1` and in the first `BDX1` record, harmless there because the handshake has just revealed the node ID anyway. A pseudonymous responder therefore (a) puts **no `OPENING`** in its block, (b) clears **link-hello capability bit 3** in its link block (so neither side expects a `BDO1`; the endpoint block keeps bit 3, because the reveal uses the `BDX1` content type), and (c) sends **no `BDX1` OPENING** when the `INVITE` arrives. The salt leaves the phone only inside its `REVEAL`.

**`REVEAL` (BDX1 kind 4, end-to-end content type 11, only after both endpoint blocks carried bit 3).**

```text
"BDX1" | kind 4 | role (1: caller, 2: callee) | SPKI length (2) = 91 | SPKI (91) | opening count (1, 0..2; 0 for the caller)
       | count x entry (43) | signature (64)
K    = HKDF-Expand(EXP, "BluetoothVideoMesh/BMH3/Reveal/1 key", 32)
TH_R = SHA-256(D_R | 0x00 | role | K | SHA-256(own pseudonym SPKI) | SHA-256(peer pseudonym SPKI) | SPKI | prior | count | entries)
sig  = ECDSA-P256-SHA256(real key, D_R "/" Role " signature" 0x00 TH_R)           D_R = "BluetoothVideoMesh/BMH3/Reveal/1"
prior = empty in the callee's reveal, SHA-256(the callee's reveal record) in the caller's
```

`EXP` is the end-to-end handshake's 32-byte exporter (a secret both ends derive from the whole transcript, which contains both pseudonym keys); the exporter itself is never signed, only a key derived from it (PR13). Both pseudonym hashes state which two throwaways the real key claims to speak for, `role` and the role label stop a reveal being replayed in the other direction, and `prior` makes the caller's reveal commit to the exact callee record it verified. A reveal recorded from another session, or forwarded by a man in the middle that terminated both sessions, fails on `K`; only the holder of the real key can sign one. At most one reveal is accepted per direction per session; a reveal from a peer that did not declare `PSEUDONYM`, a second one, a wrong role, a wrong length, more than two opening entries, an `OPENING` entry on a caller reveal or a non-canonical SPKI is a protocol error that ends the call (the rest of BDX1 is lenient because it never fails a call; a reveal decides whether the call continues).

**When the reveal happens (calls).**

1. Handshake: both ends are pseudonyms (rule P). The callee's phone rings as an **unverified stranger**: no node ID, no fingerprint, no name (the caller's name and subject labels are held until step 3, PR6, so a fake or copied advert collects nothing). Nothing about the callee's real identity has left its phone; declining reveals nothing except that a phone answered the advert.
2. The callee's user accepts: the callee queues its `REVEAL` (role 2, with its pinned opening entries) **before** the `ACCEPT` signal in the same ordered control queue, then its name label. The signature is made on the writer thread, not on the Accept tap.
3. The caller checks, in this order: signature and key binding; `PeerIdentityGate.admit(realNode, realSpki)` (a verified contact's prefix with a different key is `MISMATCH` and ends the call before the caller reveals anything); the discovery binding of the **selected** offer against the revealed node ID and the revealed entries (`DiscoverySelectionCheck`, the check BMH3 Phase 1 ran before the caller revealed; a version 2 offer is checked against the announced prefix); a direct call must also have reached the same throwaway at the link and the end-to-end handshake. Any failure ends the call with "Call peer identity changed between discovery and connection", and so does an `ACCEPT` that arrives before a verified reveal. Only then does the caller queue its own `REVEAL` (role 1, no entries) and its name and subject.
4. The callee, on `REVEAL` role 1, checks signature, binding and `admit`; a role 1 reveal before its own role 2 was sent is an error. A `MISMATCH` ends the call.
5. Both phones now replace the throwaway by the real identity for everything about the person: the displayed label, the verified-contact lookup, the safety code and QR verification (the fingerprint recorded by `admit` is what `IdentityVerification` compares), the recent-calls entry, and the presence-lease session, which is created now instead of at the handshake. The **link** stays on the throwaway; labels stay bound to the endpoint key they were signed with.

**Accepting a call from an unverified stranger tells the caller who you are; declining, or letting it ring out, tells nothing. Calling a stranger shows whoever answers who you are.** The binding in step 3 protects the caller (a fake or copied advert cannot produce a reveal that opens the selected ID), not the callee: the callee reveals to whoever holds the session and whatever name that caller claims (a claimed name is unauthenticated and can be a social-engineering lure, PR9). There is no "answer without revealing": the caller cannot tell the owner of the advert from an impostor without the reveal, so such a mode would have to let the caller accept an unbound callee (a later, explicit user choice).

**Message exchanges and relays (refused with a stranger, PR2, PR8).** A store-and-forward exchange needs a stable identity on both ends: its hello sends the phone's contact card (the real SPKI and mailbox key) to anyone who opens a link, offers are keyed on the link identity, bundle IDs and tags stay the same for up to 14 days (they would link epochs), and per-neighbour limits would be keyed on throwaways. In pseudonym mode a link with a stranger therefore carries **no exchange and no relay request**: the listener closes on a first record of those types from a pseudonymous link (either side), and an exchange initiator that meets or presents a throwaway stops. Contacts (real-real through the lease tag path) still exchange as in BMH3 Phase 1. Relayed calls to a phone in pseudonym mode fail closed: a DEBUG call relay presents its real key as the initiator toward the callee's link and meets a throwaway, which an initiator holding a real key refuses; the end-to-end layer through a relay would work, the link layer toward the callee does not in Phase 1 (a later version can let a relay present a throwaway of its own and skip the link opening). Design C helpers and reach-page routes stay on BMH2 and are therefore unreachable.

**Presence lease eligibility and its log (2026-10-12).** The OFFER of a call is sent only when the vault is loaded (a load that failed once is retried, not judged from its first miss), the peer's real identity is a verified contact, and the per-contact switch is on; the identity is the revealed one after a pseudonym call's reveal, never the throwaway. Otherwise nothing is sent and the phone logs `rotid_presence: event=ineligible | reason=` at session creation or `event=offer_withheld | reason=` at send time, with the fixed reasons `no_vault`, `vault_not_persistent`, `no_contact_store`, `peer_unverified`, `peer_mismatch`, `peer_store_unreadable`, `contact_switch_off`. The exchange needs the verification on **both** phones: each phone checks only its own store, so a one-sided verification makes the unverified side withhold and no lease moves.

**Real lease keys (replaces the DEBUG fixed lease for the app's own phones).** The initiator's tag: `RotatingDiscovery.recognize(selected)` returns exactly one hit and the vault holds that contact's lease for `dayOf(hit.epoch)`; `K_tag = contactTagKey(lease)`, binding = RDI, role 0; `expectedPeer = hit.contact`; no tag where the answerer is not the advert's owner (the link toward a relay). Zero or several hits: no tag. The responder's checks: for each call-offer entry pinned at accept, `PresenceVault.dayKey(entry.epoch, E)` gives that entry's `L_d`; the check is (`contactTagKey(L_d)`, `advertBinding(entry.rdi, 0, null)`) and the key copy is zeroed after use. `test_bmh3_test_lease` still overrides both for phone tests. With a tag that matched, `admitInitiator` requires the initiator to be a contact the vault **delivered a lease to** in the current generation; a tagged connection from anyone else means a lease reached someone unintended: the connection is closed and `bmh3: event=lease_misuse` is logged. This is best-effort detection (PR11): a holder of a leaked lease reads the real key from msg2 and may disconnect before msg3, and no automatic new generation is started (a false positive after a lost record would break every contact's recognition), so revocation stays the user's "Reset presence key".

**Streams (specified, not built).** A stream source is public by nature, but its owner is not: once streams run on BMH3, a source presents a **per-stream pseudonym** to every viewer that is not a contact (not the call keys, which would tie the roles together, and not an epoch key, which would break the forwarders' source-node grant when it changed mid-stream, PR7), with no reveal at all (a stream has no accept moment, and a viewer count is not consent). A source may attach a *stream title* label signed by the pseudonym; that is the only thing that identifies it. Becoming a contact needs a *mutual* verification (a one-sided QR scan gives no lease), after which the tag path returns the real key. Until streams move to BMH3, a stream source answers BMH2 and reveals its real key to every viewer; the tracking warning therefore stays true for **stream sources**.

**Verification, mismatch and pinning.** A verified contact that calls with an expired lease arrives as a stranger and is recognised by the reveal (`admit` marks it; the next presence-lease exchange repairs recognition). A pseudonymous peer cannot be verified before it revealed; the in-call Verify button says so, and after the reveal the existing QR and safety-code flows work unchanged. Verification pins the real key (the verified-contact store); nothing pins a pseudonym. The prefix `MISMATCH` rule runs on the real key at the reveal and for contacts at the handshake (the expected-contact full node ID, before the caller reveals). The BMH3 prefix pins (30 days) store a prefix only for an answerer that proved a real identity.

**Abuse and limits.** Pseudonyms are free to mint, so nothing may be limited per pseudonym. The limits are global and per connection, and the state a stranger can observe is scoped so that it cannot bridge a boundary (PR3): the replay cache (4,096 entries) and the signing budget (8 tokens, one per 4 s) of stranger-facing responders belong to the discovery epoch and are dropped two epochs later. With one process-wide cache a prober could replay one msg1 to every candidate RDI after a boundary and read "same phone" from the silent close, and a budget drained just before the boundary would carry over the same way. The pending-connection and admission guards and the ring limits stay as they are; a stranger who rings repeatedly is handled by declining (there is no per-pseudonym block list; the next connection is a new pseudonym by design). A `REVEAL` costs one ECDSA verification per direction per session, only after a user accepted or a verified callee answered.

**Downgrade and active attackers.** A fake or replayed advert gets the caller's per-attempt pseudonym and nothing else: the caller reveals only after a reveal whose signature binds the session and whose key opens the selected RDI, which needs the owner's key (forging the 48-bit RDI binding for an attacker-owned key costs about 2^48 hashes per epoch, the RV9 bound). A prober that connects to a stranger-mode phone gets a throwaway and a ring; it cannot obtain the salt, the node ID or any signature of the real key, on BMH3 or (because it is refused) BMH2. The attacker cannot make a phone present its real key (the tag is an HMAC under lease keys bound to the advert and msg1), cannot strip `PSEUDONYM` (inside the signed block) and cannot replay a reveal. A man in the middle that terminates both sessions can ring the callee and, if the user accepts, learns the real identity (consent), but cannot make the real caller accept it as the callee: the reveal it forwards fails on the other session. Interoperability: a BMH3-on, pseudonyms-unaware caller cannot call a phone in pseudonym mode (its real key is refused by the engine and its own pre-reveal check cannot pass); a pseudonymous caller to an older BMH3 responder gets a real key and a normal opening, stays pseudonymous and sends no `REVEAL` (an older peer did not declare `PSEUDONYM`, so it cannot parse one); a phone without BMH3 cannot connect at all while pseudonym mode is on.

**What a stranger can still link or learn (the honest list, PR15).**

1. Accepting a call from a stranger shows them who you are; calling a stranger shows whoever answers who you are.
2. Someone who can see you can ring nearby phones and watch whose reacts. Holding a connection across the 15-minute change (a connection stops the advert) lets a prober choose when your next ID appears, which can link the old and the new ID in a small crowd; a random reopen delay and a "silent for strangers" mode are future work.
3. Within one epoch, your advert (RDI, and the address when it does not change) and every connection are the same phone.
4. Anyone who connects learns the phone class (capability bytes: codec masks, bitrate ceiling, transport mask and feature bits such as labels, fragments, voice, dual, relay), the app build (the build tag, while the updater switch is on) and the BMH3 timing; these repeat across epochs.
5. Bluetooth leaks outside this protocol: the GAP device name on Android 13 and older and on some chips (unless the neutral name is on), the Database Hash, link-layer features, the fixed PSM on Android 10, Classic Bluetooth (fixed prefix, permanent address), OS beacons, bonded devices' resolvable addresses.
6. Streams you broadcast (until streams move to BMH3) and a Visible-by-handle window are identifiable or linkable.
7. Contacts who hold your leases, or anyone who takes their phone, recognise you for up to four weeks; a display name you set goes to every caller you call.
8. Keystore signing latency separates a real-key answer from a throwaway answer (a lease holder sees it; so can a sniffer who evicts the replay cache of the current epoch and replays a sniffed tagged msg1, PR14, which also shows that a sniffed caller is a contact of the target).

**Debug lines (no identifiers in release builds):** `bmh3: event=present | layer=link|endpoint | role | key=real|pseudonym | reason=stranger|contact|tag`, `bmh3: event=reveal | role=caller|callee | result=sent|verified|<failure class>`, `bmh3: event=lease_misuse`, `bmh3: event=peer | layer=endpoint | pseudonymous=` (DEBUG builds add `peer4=`, the first four bytes of the node ID the peer presented, so the phone test can compare throwaways across connections; release builds never log it).

## Experimental dual listening (off by default)

Settings > Features "Reachable over both Bluetooth LE links" (DEBUG `test_dual_listening` is the benchmark switch; default OFF until its phone test passes). Design and alternatives: PLAN "Design D". With the switch off every byte on air and on the link is unchanged: no hint bit, no second GATT service or server, no extra attempt, and every rule below stays idle (a hint bit received from another phone is ignored). Not yet tested on phones.

**Why.** A call endpoint has one transport (PLAN Design D): the offer's transport flags name it, and the endpoint's listener, link hello and policies follow it. A phone whose LE CoC fails moves to GATT (README "Automatic BLE GATT when LE CoC fails") and becomes reachable only by phones that scan for GATT; and once it is a GATT endpoint it lists only GATT offers, so it also cannot call a CoC phone. Dual listening lets a CoC phone also take a call over GATT on the same advertising address, so a GATT-only phone can call it and a CoC caller whose CoC attempt fails can still reach it, without a new scan.

**Announcement hint.** `capabilitySummary` bit 3 (`0x08`, `DualListeningWire.SUMMARY_BIT`) of the 22-byte announcement means: "this phone also accepts a call over BLE GATT (service `c8d5a105-9f88-4f65-a03d-7f5a2fb921fa`, the existing GATT call service) at the advertising address of this offer, while this offer is on air". The primary transport flags are exactly what they are today (LE CoC: `FLAG_GATT_TRANSPORT` and `FLAG_CLASSIC_TRANSPORT` clear), so every existing build reads and connects the offer as before. Bits of a call offer's `capabilitySummary`:

| Bit | Meaning |
| --- | --- |
| 0, 1 | VP9, AV1 (existing) |
| 2 | Reserved for H.264 (compact codec field bit 56; PLAN iPhone interoperability) |
| 3 | **Dual: also reachable over GATT** (this section) |
| 4 | Relay consent (relayed calls) |
| 5-7 | Reserved, zero |

**Who may set it (all must hold).** The switch is on; the endpoint's transport is LE CoC (the user's choice, or what the CoC-to-GATT safety net left); the offer is a private-call offer (`FLAG_PRIVATE_CALL_AVAILABLE`, not `FLAG_STREAM_AVAILABLE`) at route cost 0, version 2 or 5; it is not a relay-helper offer (`FLAG_RELAY_CAPABLE` clear: a helper stays single-bearer, "One bearer end to end"); and the GATT call service is registered and the second server started successfully **before** the offer is composed. The bit is never advertised for something that does not exist: if the service cannot be registered the offer is the plain CoC offer. It is never set on stream offers, viewer requests, Classic or GATT-primary offers, relay offers or reach pages. Compact (iPhone) form: no bit exists and none is sent; an iPhone offer is GATT-primary and never carries the hint.

**Who may read it.** The caller honors the bit only on a decoded call offer at route cost 0 whose transport flags are clear (LE CoC primary). Anywhere else it is ignored. A DEBUG call relay clears the bit when it mirrors its child's offer one relay further (`PrivateCallRelayChain.parentOffer`), a relayed route's `routedAnnouncement` has none, and a caller ignores it at route cost above 0 whatever a relay did. A relayed route never uses a second transport: relays are single-bearer.

**Old readers (verified 2026-10-11 against the code in this repository).** `DiscoveryAnnouncementCodec.decode` accepts any `capabilitySummary` in 0..255 and `DiscoveryAnnouncement` only checks that range. The only consumers are the codec test `supportsAdvertisedCodec` (`summary != 0 && summary and localDecoderMask != 0`, unchanged by an extra bit), `RelayedCalls.consents` (tests bit 4 only) and `LogicalStreamTarget.matches` (equality of the whole byte, used for stream offers only, where the bit is never set). `CompactDiscoveryAnnouncement.encode` (a reference encoder for vectors; Android never advertises the compact form) refuses unrepresentable summary bits, and its decoder produces none. The iOS reference decoder (`DiscoveryAnnouncement.decode`, `Discovery.swift`) reads the byte without a mask; only its compact encoder (`a.capabilitySummary & ~allowed`, which throws on an unrepresentable bit) and the unreleased iOS call relay (`CallRelay.swift`: `childOffer.capabilitySummary & 0x0f` keeps bit 3, and the compact encode of the relayed offer would then throw and stop that relay advertising) look at it. The iOS relay branch must mask the summary with the codec bits and the relay consent bit before it merges (open item, iOS repository); the released iOS app does not relay. Builds outside this repository are not covered; a decoder that rejected unknown summary bits would drop only the dual phone's offer, never connect it wrongly. `DualListeningWireTest` pins these facts with the vectors below.

**Link and endpoint hellos: unchanged.** Each side signs the transport bit of the link it runs on (`NodeCapabilities.TRANSPORT_BLE_L2CAP` or `TRANSPORT_BLE_GATT`, plus the existing bits 3-7), exactly as an endpoint of that transport does today: a dual callee that accepted a GATT link signs the GATT bit, one that accepted a CoC link the CoC bit, and the caller requires the bit of the transport it used (`peerCapabilities.transportMask and used.capabilityMask != 0`). No bit is added to either hello, and BMH2, BMS1, BME1 and the codec/maximum-bitrate fields derived from the transport are those of the transport in use. No peer needs the hint to complete a handshake.

**Listener (callee).** With the switch on and an LE CoC endpoint:

1. The endpoint takes its CoC lease and then starts the GATT call service in a **second `BluetoothGattServer` that does not advertise** (it waits at least 1.5 s after the last GATT call server closed, the existing GATT restart settle time). The one connectable advertising set stays the CoC control server's, so scanners, scan filters, the advertising-set budget and the address are unchanged. Only after the service is registered does the announcement get the hint and the control server start advertising.
2. The first connection to arrive wins and the endpoint answers it as an ordinary incoming call: a CoC accept, or a GATT client enabling the notify characteristic's CCCD (the existing admission). `acceptIncoming` is serialized and refuses a second connection (`callRunning`). On a CoC win the second server is closed; on a GATT win the CoC lease and the control server (advertising and PSM service) are closed and the GATT server stays until the call ends. The endpoint's link transport (hello bit, codec and bitrate limits, buffer, pacing, audio batching, playout profile, close wait, link-capacity and PHY memory keys) is that of the link it accepted.
3. Every restart of the availability (boundary rotation, end of a call, the 1-8 s rotating silence) closes both servers and reopens them in the same order. A relay duty (`RELAY_SETUP`) is accepted only on the primary transport: a SETUP arriving on the second link is refused (FAIL 5), because the helper's next hops are chosen on the endpoint's own bearer.
4. The second server closes (and the hint leaves the air) whenever the offer does: a call, exchange or relay duty holding the endpoint, or the endpoint closing. The service is never registered twice: while the second server carries a link, a reopened listener advertises the plain CoC offer.
5. Handshake deadline. A dual endpoint closes an accepted link, on either transport, that has not completed the link and the endpoint handshakes within 20 s (`DualSetupBudget.INCOMING_HANDSHAKE_MS`; relayed-call endpoints keep their own pre-setup watchdog). Without it a silent central that enables the second service's notifications would hold the endpoint, and on a GATT win take the CoC listener and the advertisement with it. A CoC or GATT endpoint with the switch off has no such deadline today (an existing exposure the switch does not change).
6. Store-and-forward exchanges are not carried on the second transport: a first record of hop type 11 on a second-transport link is rejected as an unknown type, and a GATT endpoint does not offer an exchange to a row it lists only because of the hint.

**Caller.** The attempt list for a call to a cost-0 offer is a pure function of (this endpoint's transport, the offer, the switch): LE CoC endpoint, offer CoC with the hint: CoC then GATT; CoC without the hint: CoC; GATT endpoint, offer GATT, or CoC with the hint: GATT (a CoC offer without the hint is not listed, as today); everything else, including a GATT offer seen by a CoC endpoint (the safety net's endpoint rebuild stays as it is) and Classic: the endpoint's own transport only. A hinted CoC offer is listed by a GATT endpoint only while the switch is on.

For CoC then GATT the CoC phase ends 9 s after it started (earlier when the outer `LeSetupBudget` deadline is earlier); at that deadline the PSM-reading GATT client and the pending CoC socket are closed, because the CoC client has no bound of its own for a connecting socket. If it fails or hits the deadline the caller opens the GATT call client to **the same `BluetoothDevice` from the same sighting, without scanning**; that attempt is an ordinary GATT setup (one attempt always, retries only while the outer budget allows). Each transport is tried at most once per attempt; the existing one 2M-to-1M setup retry reruns the whole list. The fallback is visible and logged, never silent: the status line reads "Using BLE GATT for this call: L2CAP did not connect" and `BENCHMARK call transport: event=dual_fallback | requested=BLE_L2CAP | effective=BLE_GATT | automatic=true | reason=dual_coc_failed | cocError=<class> | cocPhaseMs=<n>` is written. A CoC failure that is followed by a successful GATT link does **not** move the session to GATT (no `CocAutoGattSession.onCocFailure`, no `onCocConnectFailed`): the phone's own CoC may be fine and only that peer's CoC is not, and the call was served. When both attempts fail the call fails once, with both causes in the log, and the safety net is not told either (its retry would only repeat the GATT attempt); the CoC registration count still includes every connect, so the threshold rule keeps working. A failed plan ends after at most the 9 s CoC phase plus one GATT setup; the existing one 2M-to-1M retry may follow only while its 15 s early-loss window allows and rediscovers by scan as it does today. The phone test measures the time from the tap to the failure notice (limit 30 s). There is no per-peer memory of a failed CoC: it would be keyed by a stable node ID, which rotating IDs avoid, and the cost of a broken CoC is one bounded phase per call attempt.

**Identity binding.** The fallback reuses the selected announcement object, so the checks that bind a link to what the user selected run on whichever transport carried it: version 2 offers: the authenticated end-to-end endpoint identity must have the announced 48-bit prefix (a call does not compare the link identity with the prefix, an exchange does); version 5: the callee's `BDO1` opening on the link and `BDX1` OPENING end to end must open the selected RDI for that identity (RV15; `DiscoverySelectionCheck` takes no transport). Nothing is computed from the hint or from which transport answered. In addition, a link on the second transport is accepted only if the selected offer allowed that transport (`DualListeningWire.offeredTransports`: the primary one, plus GATT when the hint is on a CoC-primary cost-0 offer) and the peer's hello signs it. A phone answering on GATT that is not the selected phone fails the same prefix/opening check as one answering on CoC.

**Known limits of the first version (measured in T12, not hidden).** (1) The call settings the activity chooses when it creates the endpoint (video settings and per-direction caps, codec choice, buffer size, Automatic rate-control memory, the GATT restart delay after a call) follow the endpoint's primary transport; the hello, bitrate and codec limits, pacing, audio batching, playout profile, close wait and link-capacity/PHY memory keys follow the link in use. A call over the second transport therefore starts with the CoC caps (200 against 180 kbps per direction) and adapts through the usual rate control; it compares its first 30 s with a native GATT call. (2) A late CoC accept: if the caller's CoC deadline closes its socket after the callee already accepted it, the callee treats that as a CoC win (second server and advertising closed, endpoint rebuilt after the failed handshake) and the caller's GATT attempt may fail on the stale database; the next attempt works. Closing the losing listener only after the winner authenticated would remove it but changes the accept rules of every endpoint. (3) The CoC phase deadline cuts the connecting socket and closes the PSM-reading GATT client when it exists; the PSM read itself is bounded by its own 6 s control timeout and the budget-gated retry, and the fresh-ACL wait (Android 12/13 stacks) can add up to 2 s. A socket created after the deadline is closed at once.

**Rotating IDs.** One announcement, one RDI, whichever transport answers: the version 5 call offer carries the hint exactly as it carries the consent bit, and the RDI, epoch pins (`OpeningPins` role 0, evaluated when the connection is accepted), `BDO1` and `BDX1` are transport-independent. A boundary restart closes and reopens the second server together with the control server (a new GATT server each epoch, as for a GATT endpoint) and the second service is not advertised, so no new advertising set or address exists to link epochs. Stated residuals: the hint is one more stable capability bit on a rotating phone (like the relay consent bit; added to "Threats that remain" of the rotating IDs section), which is why the switch is separate and default off; the second service UUID is an application constant visible to any central that connects, the same population that can already read the PSM service before BMH2; the GAP Device Name stays the neutral name. A stable identifier is never placed in the second service.

**Relayed calls and reach pages.** Reach pages and `SETUP` carry no summary byte and are unchanged. An on-demand helper, a DEBUG call relay and any relay hop are single-bearer: they advertise no hint, accept SETUP only on the primary transport, and a caller ignores the bit at route cost above 0. A target that is dual is reached through a chain on its primary (CoC) offer as today.

**Classic.** Classic endpoints are never dual (Classic call availability keeps its permanent address and version 2). A hybrid Classic call offer carries no hint.

**Security notes.** The hint is an unauthenticated hint like every announcement field. Forging it on a copy of a victim's advertisement can only cause a caller whose CoC attempt failed to open one GATT connection to that address within the budget; the user started that attempt, nothing connects automatically, and the handshakes decide who is on the other end. An attacker who blocks CoC can force the GATT link: same BMH2/BMS1/BME1, only slower, and visible to the user. A stranger can occupy the second server (first CCCD writer) exactly as a stranger can already connect to the CoC listener or to a GATT endpoint; the endpoint is then busy until the handshake deadline and the RV8 tarpit applies. The dual endpoint's exposure is the union of the two transports' exposures, with the same bounds and no new unauthenticated parser.

## Experimental relayed calls and multi-hop discovery (off by default)

DEBUG `test_relayed_calls`; otherwise the Advanced setting "Experimental: relayed calls". Design: PLAN "Design C" (reviewed draft R14-R22, then an independent review recorded there). With the switch off every byte on air and on the link is unchanged: no consent bit, no relay flag, no reach page, no link-hello bit, and hop type 12 is rejected as unknown exactly as by old builds. Not yet tested on phones.

**Scope.** Call offers only, LE CoC and GATT only. Fixed-prefix (version 2) targets only, unless both this experiment and `test_rotating_ids` are on, in which case only role-0 RDI (version 5) targets are used (reach pages version 6, `SETUP` message 4; see "Rotating IDs and relayed calls" below). Streams, viewer requests, titles, names and Classic phones are not relayed this way. Cost cap 2 relays (DEBUG `test_relayed_calls_max_relays` 1..4); the wire carries 1..4.

**Capability bits (all other readers test only the bits they need).**

| Where | Bit | Meaning |
| --- | --- | --- |
| Call-offer `capabilitySummary` | 4 (`0x10`) | The target consents to be found through other phones. Never set on stream offers. |
| Call-offer flag `FLAG_RELAY_CAPABLE` (bit 1) | - | Set on an idle relay-helper's own cost-0 call offer, so callers can connect to its listener. Existing flag, new use on call offers. |
| Link hello transport mask | 4 (`0x10`) | "Understands `RELAY_SETUP` (hop type 12)". Signed by every endpoint with the experiment on, caller and helper. |
| Link hello of an active relay-helper | 6 (`0x40`) and `maxChildren` 1 | The existing call-relay capability and relay capacity, signed only while the helper accepts SETUP (not paused, not busy). The end-to-end hello is unchanged. |

**Hop record type 12 `RELAY_SETUP`** (a `BMS1` hop record like type 11; a reader rejects it as unknown unless its owner opted in). SETUP is accepted only as the first record after the BMH2 link handshake (and after a negotiated `BDO1` opening: with both experiments on a helper is a rotating call listener and its own `BDO1` comes first; a fixed-prefix helper never has one) of a listener that signed bits 4 and 6 and `maxChildren` 1, and only from a peer whose link hello signed bit 4. READY and FAIL are accepted only by the initiator that sent a SETUP, as the single reply, with a matching setup ID. The first record on a listener is dispatched in this order: `BDO1` when negotiated, then exactly one of type 11 (store-and-forward, when on), type 12 SETUP (helper), or type 4 (the endpoint handshake). Payload, big-endian:

```text
"BRS1" (4) | message (1) | body
  SETUP 1: target prefix (6) | budget (1, 1..cap) | remaining ms (4, 2000..20000) | setup ID (8, random per hop)
  READY 2: setup ID (8) | relays (1, 1..budget)
  FAIL  3: setup ID (8) | reason (1)
```

SETUP is 24 bytes, READY and FAIL 14. FAIL reasons: 1 no route, 2 busy, 3 child authentication failed, 4 timeout, 5 refused (policy, rate, battery), 6 loop. A decoder rejects other magics, messages, reasons, a zero budget, a budget above 4, a remaining time outside the range, `relays` outside `1..4`, trailing bytes, and a target equal to the zero prefix.

**Setup rules (hop-local; every SETUP, READY and FAIL is regenerated per hop).**

1. The caller connects to a relay-helper's call listener (the helper's own offer carries `FLAG_RELAY_CAPABLE`), completes the link handshake and requires the helper's link hello to show bits 4 and 6 and `maxChildren` at least 1. It sends SETUP with the cost it saw and the deadline left.
2. The helper checks, in this order: record format; its switch and pause state; busy (own call, ringing, exchange, stream, or already relaying); rate limits (3 SETUP per parent identity per minute, 10 per minute overall); parent identity is not itself and not the target; budget is within the cap; the table holds the target at a cost within the budget. Any failure answers FAIL (5 refused, 2 busy or 1 no route) and closes.
3. Budget 1, or a cost-1 entry for the target whatever the budget: connect to the target's own offer; its authenticated link identity must equal the target prefix (the existing cost-0 child admission). Otherwise pick the entry's next-hop relay, connect to its listener on the same bearer, require the bearer bit of its link hello, bits 4 and 6, `maxChildren` 1, a link identity equal to the prefix of the helper offer selected, and not the target and not itself (existing `PrivateCallRelayChain.childProblem` plus the prefix check), and send SETUP with budget - 1, a new setup ID and the deadline minus the elapsed time minus 1 s. When that allowance is below 2,000 ms the helper answers FAIL 4 (timeout) instead; every wait (connect, authentication, write, reply) is bounded by one monotonic deadline taken from the SETUP's remaining time.
4. READY travels back one hop at a time and carries the number of relays from that hop down to the target (its child's count + 1; 1 when it connected to the target itself). The caller records that number as the call's relay count. A relay that sent READY switches to the opaque copy mode, with exactly the record types, liveness and close rules of "Private-call relay chains". A child FAIL becomes a FAIL upstream with the same reason; a child that is silent past the deadline becomes FAIL 4.
5. The caller refuses a READY with `relays` above the budget it sent or above the cap, and a link that closes or is silent past the deadline plus 2 s (reply grace for the last hop's cleanup, not extra setup time). READY's relay count is a relay's claim, not proof of topology. The caller also requires the first hop's authenticated link identity to equal the prefix of the helper offer it selected.
6. After READY the chain tears down unless the end-to-end handshake crosses within 10 s and the callee's first end-to-end content record (its Ringing answer to the Invite) within 20 s; heartbeats and caller-originated content do not count. One absolute deadline (the SETUP's remaining time) also covers a helper's connect, authentication and wait for the next hop: on expiry it answers FAIL 4 and closes both links. After child authentication a helper also refuses a child that is its parent or the target's own parent (`PrivateCallRelayChain.parentProblem`). A helper also closes a connection that has not completed the link handshake and delivered its first record within 20 s of being accepted. A callee declines a relayed incoming call that rings 60 s without an answer; it counts the call as relayed when its authenticated link peer differs from its authenticated call peer, whatever relay count the Invite states. A second type 12 record on a running chain is a violation and closes both links.
7. A relay holds one parent and one child. The budget strictly decreases and ends at the authenticated target, so a chain is a loop-free path of at most the cap.

**Reach table rules.** Entries come only from the scanning phone's own sightings. A direct sighting needs announcement version 2, `FLAG_PRIVATE_CALL_AVAILABLE`, route cost 0, the consent bit and an LE transport. A page entry needs relay prefix, target and via from a decoded reach page, `cost + 1` not above the cap, a target that is not this phone, and `via` not equal to the first two bytes of this phone's prefix (poison reverse). Admission, caps and eviction are exactly the admission list in PLAN "Design C" (two sightings at least 2 s apart from one advertiser address; 8 new targets per 30 s; 4 per relay prefix; 32 entries; refreshed-20-s and used-in-success entries are protected; failure skip 30 s, FAIL-no-route drop 5 min). Ages only grow: a direct sighting has age 0 when seen; a learned entry adds the local time since its page; entries older than 62 s, or not refreshed locally for 30 s, are dropped; after a route is lost, worse-cost entries for the target are ignored for 10 s. The table is never persisted and release builds never log it. A relay advertises its own direct entries (a consenting target it hears itself) as soon as admitted, and neighbour-learned entries only after 5 s and only while that neighbour's relay is also heard in a connectable offer with `FLAG_RELAY_CAPABLE` (the consistency check applies to learned entries only, so a target that consents but does not help is still found), best (lowest cost, then lowest age, ties shuffled) first, at most 4, and stops while paused or busy.

**Reach page** (manufacturer data `0xFFFF` of a legacy, non-connectable, scannable set that carries the app's service UUID; 250 ms interval, one page per second):

```text
version 4 (1) | relay prefix (6) | relay flags (1): bit 0 LE CoC, bit 1 GATT, bit 3 idle; other bits zero
| page (1): index (high nibble) | count (low nibble, 1..4)
| entries (1..2) x ( target prefix (6) | cost (high 3 bits, 1..4) | age (low 5 bits, 2 s units) | via (2) )
```

18 bytes (one entry) or 27 bytes (two), 31 bytes with the advertising-data header. Old scanners reject it (length is not 22). A decoder rejects an index at or above the count, a count outside 1..4, no entries, cost 0 or above 4, a target equal to the relay prefix, duplicate targets in a page, and reserved relay-flag bits. A phone starts the set only when the advertising-set probe found at least two free sets (`TitleAdvertiser` precedent). A scanner reports reach pages before its per-address duplicate filter, as for title pages.

**Identity.** None of this changes who authenticates whom: the caller still requires the end-to-end peer's prefix to equal the target it selected (and the full fingerprint for a verified contact); the helper's link identity, the target's link identity and the relays' hellos are checked as above. A reach page, a table entry and a SETUP record are hints and requests, never proof of identity.

**Rotating IDs and relayed calls (reach pages version 6; DEBUG `test_relayed_rotating`, default on while both experiments are on; `=false` restores the old exclusion).** Relaying must not spread the stable prefix, so with both `test_rotating_ids` and `test_relayed_calls` on a phone neither sets nor reads a fixed-prefix reach entry and keeps everything in role-0 RDIs. The rules are those above with these substitutions:

1. *Offers.* A relayed-call phone's cost-0 call offer is version 5 (role-0 RDI). The consent bit (capability bit 4) and the helper flag (`FLAG_RELAY_CAPABLE`) are set on it exactly as on a version 2 offer (two more stable bits, RV14); "target" and "helper" below mean a version 5 offer carrying them. A rotating phone keeps two tables, one per population: its own pages and helper offers are version 5 and version 6 only (it never advertises a fixed-prefix target), while as a caller it may still use a fixed-prefix helper and target like any phone it can call directly (the link is then checked by prefix, as before). A non-rotating phone cannot see version 5 offers or version 6 pages. A route never mixes the two: a version 5 `SETUP` goes only to a version 5 helper.
2. *Reach page version 6.* The version 4 layout (18 or 27 bytes) with `version 6`: the relay field is the relay's own **current role-0 RDI**, each target field is the target's role-0 RDI as the relay scanned it, and `via` is the first two bytes of the next hop's role-0 RDI (the target's own RDI for cost 1). Old scanners and version-4-only readers reject it (version byte). Vectors: relay `44e69c0a7a7d`, flags CoC + idle, one entry (target `fecba64983fd`, cost 1, age 3 units, via `fecb`) = `0644e69c0a7a7d0901fecba64983fd23fecb` (the same bytes with version 4 are the fixed-prefix page); two entries (page 1 of 2) = `0644e69c0a7a7d0912fecba64983fd5fa1b2974ae410ea9120974a`; `SETUP_RDI` for target `974ae410ea91`, budget 2, 20,000 ms, setup ID `0102030405060708` = `4252533104974ae410ea910200004e200102030405060708` (`SETUP` is the same with message byte `01`). A relay with both experiments on advertises version 6 pages only, never version 4 (that page would carry its fixed prefix), and none while a Visible-by-handle window runs or during the boundary silence (no page names an ID that no offer carries); a relay without rotating IDs keeps version 4 and never lists a version 5 target.
3. *Table.* Each population has its own table, so a version 2 prefix and a version 5 RDI never collide. A version 6 entry's age and cost rules, admission (two sightings two seconds apart, 8 new targets per 30 s, 4 per relay, 32 entries) and expiry are unchanged. Poison reverse compares `via` with the first two bytes of the receiving relay's **current and previous** RDI. **The whole table flushes at the phone's own boundary** (RV6) and the reach set restarts on a new set with the new RDI after the usual silence; learned entries again need two sightings and five seconds before they are advertised, so relayed reach is empty for up to about 30 s per hop after each boundary. A cached first-hop offer (older than 30 s or from a previous epoch) is never dialled, and a setup that straddles a boundary either completes inside the callee's 60 s pin or fails cleanly and is retried (RD7: the pin lasts 60 s after the callee's boundary; no extra age rule is applied, which fails safe).
4. *`SETUP` message 4 (`SETUP_RDI`).* Identical to `SETUP` (24 bytes) except that the target field is a role-0 RDI and the target is looked up in the rotating table; `READY` and `FAIL` are unchanged. A reader accepts message 4 only when rotating IDs and relayed calls are both on (`RelaySetupCodec.decode(acceptRdi)`) and rejects it as unknown otherwise. The caller sends it only to a first hop it selected as a version 5 helper offer; each helper regenerates it for its next hop as message 4 when its table entry is version 5.
5. *Hop checks.* Every link to a version 5 helper or target is checked with the selected offer's `BDO1` (link hello bit 3, role 0), replacing the prefix comparisons of the setup rules: the caller's link to the first helper must open the helper offer it selected; a helper's link to its next hop opens the next relay's offer it selected (budget above 1) or the target's own offer (budget 1 or a cost-1 entry), and the existing relay-capacity checks (`childProblem`, `parentProblem`) apply to node IDs only. The caller's end-to-end check is the callee's `BDX1` OPENING over the chain (above), which must open the RDI the caller selected from the reach entry; the pin is taken when the relay's connection to the callee is accepted. A target RDI older than 62 s at the caller, or learned before a boundary the callee has already passed by 60 s, fails the check; the next attempt uses a fresh entry.
6. *Privacy.* No relay advertises or forwards a stable identifier: reach pages, helper offers and `SETUP` carry only the current epoch's RDIs. Each relay on a chosen path still learns the target's RDI, its adjacent link identities and both signed endpoint hellos (C2). A passive observer near a relay learns "a rotating call-ready phone is within N hops of this relay" for one epoch; contacts holding leases can recognise the RDI in a page exactly as in a direct sighting, which lets them see "Alice via 1 phone" before connecting (unconfirmed).

**Debug lines (DEBUG builds; release builds log none of the table):** `rotid_open: role=relay_hop|call_endpoint | result=`, `relayed_calls: enabled= | help= | consent= | maxRelays= | require=`, `relayed_reach_table: entries= | rotating_entries= | pages= | offers=` (`entries` is the fixed-prefix table, `rotating_entries` the role-0 one; with both experiments on the relayed rows live in the second), `relayed_setup: role=caller|helper | result=ready|failed|refused|accepted|invalid|pre_setup_timeout | budget= | relays= | reason=`, `relayed_helper: state=RUNNING|PAUSED | reason= | scan= | relaying=` (also `reach_pages status=`/`skipped` and `relay_ended`), `relayed_call: ringing_cap_declined`.

## Store-and-forward messages

Status (2026-10-11): no longer experimental. The Settings > Features switch "Messages" (shipped default off until the phone test passes; DEBUG `test_store_forward` is the benchmark switch); "Sync messages automatically" is a separate sub-switch. The wire is unchanged. With the switch off, no reader accepts hop type `11`, no endpoint reads a dispatch record, and calls/streams are unchanged. v1 covers two directly adjacent phones only; the carrier role (PLAN Design A v2) exists in code but is hard-off. Design and reasoning: PLAN "Design A".

### Keys and contact card

- Each identity has a static P-256 **mailbox key**: Android Keystore ECDH (`PURPOSE_AGREE_KEY`) on API 31+, otherwise a software key whose PKCS#8 bytes are sealed by a non-exportable Keystore AES-256-GCM key. The same Keystore AES key encrypts opened messages and every metadata file (contacts, neighbour ledger, bundle meta, seen IDs) at rest under `noBackupFilesDir/store-forward`. If the recorded mailbox key can no longer be loaded (Keystore cleared, data restored elsewhere), a new key is created and Messages shows a "message key reset" notice until dismissed, because contacts must receive the new card.
- **Contact card `BCC1`**: `BCC1 | version 1 | identity SPKI length (2) | identity SPKI | compressed mailbox key (33) | created ms (8) | signature length (2) | ECDSA signature`. The identity key signs `BluetoothVideoMesh/StoreForward/Card/1 || everything before the signature`. The node ID is SHA-256(identity SPKI)[0:16]. A card decodes only with a valid signature and an on-curve mailbox point. Text form `BCC1:` + unpadded base64url (about 300 characters, QR-ready; no QR renderer is bundled).
- A card received over a link must match the link's authenticated node ID. It is stored PENDING until the user accepts it, and a pending card authorizes nothing: it is not in the tag table, its bundles are refused (not for me) and stay queued with the sender until acceptance. Ignoring a card removes it and anything held for it; unaccepted cards are dropped after 14 days. A different mailbox key for a known identity is ignored (key-change warnings are open work). Typed card text is accepted immediately. No two held cards (pending or accepted) may share a mailbox key: a link card reusing one is refused (`MAILBOX_IN_USE`), and a typed or accepted card removes pending cards that copied its key (accepting beside another accepted holder fails). Senders are resolved by the node ID inside the key slot, which must be an accepted card holding exactly that mailbox key. Cards carry no proof of possession of the mailbox key: ECDH cannot give a non-interactive proof and a Keystore `PURPOSE_AGREE_KEY` key cannot sign. The identity binding in the KDF (below) and the uniqueness rule leave a squatting card unable to open, forge or block anything.
- **Safety number**: 20 digits (four groups of five) from `SHA-256("BluetoothVideoMesh/StoreForward/SafetyNumber/1" || u16 SPKI length || identity SPKI || compressed mailbox key)`, shown for your own card and for each pending card so users compare them in person before accepting.
- **Pair secret** `Kp = HKDF-SHA256(ikm = ECDH(mailbox_A, mailbox_B), salt = SHA-256(sorted compressed mailbox keys), info = "BluetoothVideoMesh/StoreForward/Pair/2" || the two node IDs sorted)`. Binding the node IDs means the same mailbox key under another identity gives a different secret and different tags (no unknown-key share). **Recipient tag** = `HMAC-SHA256(Kp, "tag" || utcDay u32)[0:8]`, where utcDay is the bundle's created hour / 24. Both members compute the same tag. It differs per pair and per creation day, but a bundle's tag and ID are fixed for that bundle's whole lifetime (up to 14 days), so an observer who sees one bundle again can follow it until it expires. Bundles created on different days carry unlinkable tags. Recipients precompute tags for every held card over the 14-day window.

### Bundle header `BSB1` (carrier-visible, immutable)

| Field | Bytes |
| --- | ---: |
| Magic `BSB1`, version 2 (version 1 is rejected) | 4+1 |
| Created hour, expiry hour (UTC hours since epoch) | 4+4 |
| Priority class (0 text/receipt/location/card, 1 voice, 2 photo, 3 video) | 1 |
| Padded plaintext length | 4 |
| Chunk count (1-256) | 2 |
| Slot count (1-8) | 1 |
| Key slots | 154 x slots |
| Chunk hash list: SHA-256(ciphertext chunk)[0:16] | 16 x chunks |

Bundle ID = SHA-256(header). Decoding is strict: the lifetime must be positive and at most 336 hours (QA4), the chunk count must equal ceil(padded / 8176), and the length must be exact. v1 writes one slot. No proof-of-work field exists in version 1.

**Slot** (154 bytes) = `tag (8) | ephemeral key e, compressed (33) | part1 (49 + 16) | part2 (32 + 16)`. AAD = all fixed header fields and the hash list (everything except the slots, including the slot count) `|| slot index (1) || slot tag`. `salt = SHA-256("BluetoothVideoMesh/StoreForward/2" || e || R)`.
- `k1 = HKDF(ECDH(e, R), salt, ".../sender" || recipient node ID)`; part1 = AES-256-GCM(k1, nonce 0, sender compressed mailbox key || sender node ID, AAD).
- `k2 = HKDF(k1 || ECDH(S, R), salt, ".../content-key" || sender node ID || recipient node ID)`; part2 = AES-256-GCM(k2, nonce 0, 32-byte content key, AAD || part1).

The recipient learns and authenticates the sender (static-static ECDH), and the sender must be a held card whose node ID matches part1. Carriers learn nothing about the sender. There is no signature, so the recipient cannot prove authorship to a third party (deniable, QA7); like Noise X, a compromised recipient key can impersonate others to that recipient. Unknown senders are refused (contacts only, QA2).

**Forward-secrecy limitation (open design decision).** Both slot keys derive from the recipient's long-term mailbox key, so a later compromise of that key decrypts every retained or captured bundle addressed to it and reveals the senders. On API 31+ the key is non-exportable in Keystore: an attacker must keep using the phone. On API 29-30 it is a software key sealed by a Keystore AES key that has no user-authentication requirement, so a temporary app-process compromise can copy it for later offline decryption. Options, not yet chosen:
- per-bundle forward secrecy from one-time prekeys published in the contact card or exchanged over a link (X3DH-like; adds key management and prekey exhaustion);
- periodic mailbox-key rotation with card re-exchange;
- `setUserAuthenticationRequired` (or unlocked-device-required) on the wrapping key, which stops background opening while the phone is locked.

On API 29-30 the unwrapped software private key also lives in the app's memory for as long as the process runs (it is decrypted once when Messages or an exchange first opens the store). Anyone who can read that process memory (a debugger on a compromised phone, a memory-dumping exploit) obtains it, and with it every past and future bundle until the key is reset. API 31+ keeps the private key inside Keystore.

### Content `BSM1`

`BSM1 | kind (1) | created ms (8) | conversation ID (16) | reply-to bundle ID (32, zero if none) | MIME length (1) | MIME | body length (4) | body`. Kinds: text 1, voice 2, photo 3, video 4, location 5, receipt 6, contact card 7. A receipt's reply-to is the delivered bundle ID and its body the received UTC hour (QA3: 1:1 receipts on, hour resolution; no read receipts). The plaintext `u32 length || BSM1` is zero-padded to Padmé size (minimum 1024 bytes, capped at 256 chunks), split into 8176-byte pieces, and each piece is sealed with AES-256-GCM under the per-bundle content key, nonce = chunk index, AAD = `index u16 || count u16`. Ciphertext chunks are 8 KiB except the last. Opening verifies every chunk hash, every tag and zero padding; any failure rejects the bundle.

### Transfer `BSF1` in hop type 11

Each `BMS1` type-11 record carries `BSF1 | message type (1) | body length (4) | body` inside the unchanged authenticated, ordered link session.

| Type | Body | Purpose |
| --- | --- | --- |
| HELLO 1 | version (1), free carrier quota (4; 0 = not a carrier), daily remaining from this neighbour (4), inventory digest (8) | First message each way |
| SUMMARY 2 | count (2), last (1), entries of bundle ID (32), tag (8), class (1), expiry hour (4), chunk count (2), chunks held (2) | Up to 256 entries per message |
| WANT 3 | bundle ID (32), need header (1), chunk count (2), needed-chunk bitmap | Resume from bitmaps |
| HEADER 4 | copy tokens (1, always 0 in v1), BSB1 header | |
| CHUNK 5 | bundle ID (32), index (2), ciphertext (at most 8 KiB) | Verified against the hash list before storage |
| ACCEPT/REFUSE 6 | bundle ID (32), reason: 0 sent (all chunks this phone can give for the WANT), 1 have, 2 quota, 3 expired, 4 rate, 5 too large, 6 invalid, 7 not for me, 8 unknown | |
| DELIVERED_LOCAL 7 | bundle ID (32) | The recipient's phone tells its adjacent peer it holds the bundle. It is sent only to the contact that owns the bundle's tag: the authenticated peer must be that contact and the offered tag must equal the delivered bundle's own tag, so it is no recipient oracle. Acted on only for the receiver's own bundle addressed to that authenticated peer; ignored for carried bundles (QA5) |
| DONE 8 | reason: 0 normal, 1 suspend, 2 timeout, 3 error, 4 rate limited | 4: the responder refuses because this neighbour exchanged too recently or too often |
| CARD 9 | BCC1 card | Sent after HELLO |

Differences from the original design draft (see [PLAN.md](PLAN.md) "Design A"): SUMMARY and CHUNK carry the full 32-byte bundle ID (an 8-byte prefix made WANT ambiguous and let a peer grind collisions); CARD 9 and reason 0 "sent" were added; the HELLO digest is recorded but does not yet skip a sync.

**Exchange.** A responder admits at most one exchange per adjacent identity per 60 s and 10 per hour; otherwise it answers DONE(rate limited) and closes. While an exchange holds the call endpoint, the call listener stays open (one extra LE CoC listen, counted by the registration ledger). An incoming connection then suspends the exchange within one chunk and is answered as an ordinary call. The initiator sends HELLO and CARD. A responder whose call endpoint has the experiment on reads the first record after the BMH2 link handshake with type 11 allowed for that read only: type 11 starts an exchange, and anything else goes unchanged into the endpoint handshake. After a peer's HELLO, each side sends SUMMARY. The bundles offered are its own queued bundles addressed to that authenticated peer. A peer's HELLO carrier quota is self-declared and widens the offer only when this phone itself runs the carrier role (off in v1). With carrying on, complete carried bundles not received from that peer are also offered. Ordering is by class, then size, then age. The receiver admits each entry hop-locally and WANTs it. The offerer answers in order with HEADER (if needed), the CHUNKs it holds and REPLY 0. A side sends DONE(normal) when every WANT is answered, and the exchange ends when both DONEs have crossed. At most 1,024 SUMMARY entries are offered or accepted per exchange. A repeated WANT for a bundle, or more unknown WANTs than that, is a protocol violation. Each WANT becomes one lazily read job, so outbound queues are bounded. Serving stops with ACCEPT/REFUSE 4 (rate) at 8 MB per exchange or 20 MB per neighbour per UTC day. A dedicated writer drains outbound work so that neither side blocks on a full radio buffer. A local suspend (live call, `sf_suspend`) is checked before every record: at most the chunk being written completes, then DONE(suspend) and the link closes. A separate watchdog enforces 10 s without progress and 120 s per exchange. If the writer is stuck in a write to a peer that stopped reading, the watchdog closes the link one second after a suspend request. A malformed or out-of-order message sends DONE(error) and closes. After more than four poisoned chunks the exchange is abandoned. Chunks write idempotently and bitmaps persist after each chunk, so any interruption resumes from the next missing chunk with this or another phone.

**Durability.** An own bundle's header and chunks are fsynced before its meta (the commit point) marks it complete. Received chunks are fsynced in batches of 16 (and when a bundle completes or an exchange ends) before the saved bitmap claims them, so a crash only re-requests the unsynced chunks. Each stored chunk is checked against the hash list before it is served. A damaged own bundle becomes FAILED (shown as failed, no longer offered) and the exchange continues with the next bundle. A bundle whose header cannot be read at startup is kept and listed as failed instead of being deleted silently. Deleting an outgoing message withdraws it. Neighbour ledger records idle for 30 days are pruned, and at most 512 are kept.

**Admission and storage (hop-local).** Per authenticated adjacent identity: 20 MB and 200 bundles per UTC day and 8 MB per exchange. Per sending contact: 50 bundles per day, charged only after the HEADER's key slot authenticates that contact as the owner of the bundle's tag. Before that, admission charges only the adjacent neighbour's allowance, so a stranger who knows a tag cannot spend a contact's allowance. A header whose slot does not authenticate the tag's owner is refused (6 invalid) before any chunk. Inbox 64 MB, counting opened incoming messages; own outgoing 32 MB. Opened messages (both directions) are kept encrypted at rest, up to 96 MB. Each keeps its bundle's expiry hour and is deleted at that hour. The list decrypts only small listing records; bodies are decrypted on demand. Carried: 64 MB, at most 25% per source neighbour and 10% per tag; eviction removes stalled partials (24 h), then class 3 > 2 > 1 > 0, oldest first, and never own or inbox data. Expiry uses the receiving phone's clock: `stored_until = min(expiry, received + 14 d)`, with 2 h skew allowed only at acceptance and a created hour at most 2 h ahead. Opened, rejected, delivered and user-deleted IDs stay in a seen set until expiry + 2 h skew + 1 h, past the last hour acceptance allows, so a replay never reopens or resurrects a message or triggers another receipt. Receiving is crash-safe: the opened message is stored durably first. Only then is the ID tombstoned and marked delivered, and the ciphertext deleted. If storing fails (archive full or a write error) the ciphertext stays, delivery is not acknowledged, and opening is retried at the next exchange. Decrypted voice notes play from memory, and recording leftovers are deleted when Messages starts, pauses or closes.

**What a link observer or peer learns.** A radio observer sees a call-transport link with record sizes and timing. The adjacent peer learns the other's identity (already true of BMH2), mailbox card, the offered tags/classes/sizes/expiry and transfer timing. Contents, senders and recipients of carried bundles stay hidden. Discovery is unchanged: v1 uses the private-call availability advertisement, and a version-3 announcement is not implemented.

## Lifecycle, liveness and route withdrawal

Lifecycle and media share ordered endpoint-content sequence space. Pause clears queued media and sends authenticated `PAUSED` every two seconds. Resume queues `LIVE` before media. End clears queued media, queues and flushes `ENDED`, then closes the link. Repeated `PAUSED` is intentional liveness. An advertised paused hint is untrusted and cannot replace the authenticated lifecycle record.

Each parent acts first on immediate socket EOF/read/write failure or GATT disconnect; it closes only the affected child link. Authenticated version-1 keepalive has a one-byte payload and terminates at the immediate parent, which independently generates its own upstream keepalive.

| Link | Heartbeat period | Silent-link timeout |
| --- | ---: | ---: |
| RFCOMM / CoC child | 2 seconds | 8 seconds |
| GATT direct viewer or receiver-node child | 2 seconds | 6 seconds |

EOF/callback/write failure takes precedence over the timeout. Matched GATT kill/rejoin tests established that callbacks and forwarding writes can leave a stale direct-viewer session; these heartbeats bound that immediate silent link. They do not recreate the retired graph-wide metrics stream. No queue, bitrate, FPS, drop, decoder, thermal or liveness metric crosses more than one immediate link or changes the broadcast encoder target.

A receiver's hop-local link report travels in the same heartbeat type and describes only the link from its adjacent sender; it is never forwarded (a call relay replaces it with a version-1 heartbeat).

| Version | Payload |
| --- | --- |
| 1 | `01` (liveness only) |
| 2 | `02`, arrival-train kbps (2), flags (1: bit 0 link late), added delay ms (2): exactly 6 bytes |
| 3 (2026-10-09) | the version 2 fields with version `03` (flags bit 1: delivery only), then received media bytes (4) and receiver link clock ms (4): 14 bytes |

Received media bytes count, in arrival order, the media this receiver has taken off the link since it started, modulo 2^32: each whole media packet's payload and, for experimental call video fragments, each fragment's chunk bytes when the fragment arrives (never the reassembled packet again). These are exactly the bytes its sender counts as written, record by record (display-rotation packets are excluded in calls). The link clock is milliseconds since this link started at the receiver, modulo 2^32, at the arrival of the last counted byte (not when the report was written, and not device uptime). The sender maps that byte offset to its own write time for it: the one-way delay minus its rolling 2-minute minimum is the queue in front of the media, and the return path's delay is not part of it. Counters that go backwards are a peer reset, not a 2^32 wrap. Flag bit 1 marks a report sent only to refresh delivery: its lateness fields repeat the last full report and must not feed a lateness trend.

Version 1 and 2 parsers accept only these exact payloads and close the link on anything else, so version 3 is sent only to a hop known to accept it. Version 3 and later parsers read the first 14 bytes, ignore flag bits 2-7 and trailing bytes (up to 64 bytes in all) and reject shorter payloads, so a later version never closes a version 3 link. On a direct private-call link each current endpoint sends one version-1 heartbeat after the endpoint handshake to say it accepts version 3; earlier endpoints never send version 1 on a direct link and take it as liveness. An endpoint sends version 3 only once the call and its relay-hop count are known and the call is direct, so a call relay never receives it. A stream parent has no message that older viewers accept for such a hello (they reject heartbeats from a parent), so stream viewers send version 3 only under the experimental stream delivery reports, which require every phone in the stream to run that build. A capability bit in the signed hello would carry this negotiation for streams too; it needs its own protocol and security review.

Decoder recovery seals an empty `KEY_FRAME_REQUEST`; each viewer-forwarder authenticates it and creates the equivalent upstream request, coalescing it with local recovery. Terminal acknowledgement works similarly. A parent waits up to two seconds for its active child before acknowledging upstream, so a missing child cannot block the chain indefinitely. The blind-relay harness instead forwards endpoint keyframe control as opaque `BME1`.

An overloaded immediate parent sends authenticated one-byte `ROUTE_CONTROL`, reason `LOCAL_CAPACITY=1`, waits up to four seconds for the matching `ROUTE_CONTROL_ACK`, then closes that child link. It neither ends nor changes the source stream. The receiver suppresses the exact node-prefix/stream-token/transport route for 30 seconds and returns to discovery; it does not repeat ordinary same-route reconnect. Triggering queue/cadence measurements remain private to that parent.

Explicit `ENDED` returns the receiver to discovery without retrying that broadcast. Unexpected loss preserves the last frame and searches for the same logical broadcast token and codec until the user leaves. A replacement can be the original source or another viewer-forwarder/transport, but its adjacent identity must match the announcement and its authenticated source must match the originally accepted source. The replacement reauthenticates and starts at a fresh keyframe; recovery is break-before-make. A recovery request uses six bytes for the failed immediate-node prefix that ordinary viewer requests do not need, keeping the discovery body 22 bytes. That hint can prioritize/gate attempts and never replaces authenticated identity/liveness.

## Emergency wipe

`EmergencyWipe.panic(context)` (no confirmation, bound by the UI to an in-app gesture such as a triple-tap) and `EmergencyWipe.wipeConfirmed(context, "WIPE")` run one synchronous, single-flight sequence on a worker thread; a concurrent or re-entrant call returns `alreadyRunning`.

1. **Stop admission.** No new end-to-end session is admitted and no Keystore key is created (identity, store-and-forward, verification) for the rest of the process.
2. **Pending marker.** `noBackupFilesDir/emergency-wipe-pending` is written and synced.
3. **Keys first.** Every Android Keystore alias of the app is deleted, so data sealed under them (store-and-forward messages and metadata, the software mailbox key, verified contacts) becomes unreadable even if the wipe is interrupted.
4. **Sessions.** The registered owner ends every call, stream, relay and discovery on the main thread (best-effort hang-up first). The wipe waits for it at most 2.5 s and never runs it unbounded on its own thread.
5. **Data.** Every SharedPreferences file (settings and learned link, rate, PHY, encoder and group-epoch memories) is cleared and deleted. The contents of the app data directory (files, `no_backup` with store-and-forward outbox/inbox/courier data, verified contacts and learned Classic addresses, cache, databases) are deleted, except the native library link, ART code cache and the marker. So are the app's external files and cache (benchmark traces and media).
6. **Second sweep.** In-memory caches are dropped, then the Keystore, preferences and files are swept again for late writers. The report is `complete` only when that final sweep leaves nothing.
7. **Finish.** Every app notification is cancelled (call alerts carry the caller's label; also once right after the sessions end). The marker is removed only when complete. One line is logged (`EMERGENCY_WIPE reason=... | complete=... | alreadyRunning=... | durationMs=...`, no identifiers or secrets), and the process ends.

On the next launch, a remaining marker makes MainActivity resume the wipe before any transport, key or store opens. If it still cannot complete (for example the Keystore keeps failing or storage is read-only), a minimal "Wipe incomplete" screen replaces the app. It has Retry and an App info link (clearing storage there finishes the wipe), and starts nothing; the app never closes silently. After a complete wipe, the next launch creates a new identity, so peers see a new node ID.

No intent reaches the panic or confirmed wipe. DEBUG builds alone accept `--es test_emergency_wipe <token>` on launch or new intent, and only when `<token>` (32-128 lowercase hex) equals the one-shot file `files/debug-emergency-wipe-token`. Write it with `adb shell run-as <package>` (debuggable builds only; internal storage, because on Android 10 legacy storage another app with the storage permission could write external app files). The debug wipe also deletes benchmark inputs in the app's external files.

A wipe cannot guarantee:

- **Flash remanence.** File deletion on flash storage does not overwrite cells; wear levelling and TRIM timing decide when blocks are erased. Files sealed under Keystore keys rely on key deletion instead, which is as strong as the device's Keystore deletion (strongest with StrongBox or rollback-resistant keys). Learned memories, settings, traces and media are plain files and may be recoverable forensically until the blocks are reused.
- **Copies outside the app.** adb backups or device-to-device transfers made earlier, screenshots, the system logcat buffer (which an app cannot clear), recordings saved to shared storage, the system's Bluetooth bond list and cached device names, and anything a peer stored (their verified-contact entry, received messages, carried bundles) are untouched.
- **A running attacker.** Malware or a debugger already on the phone can copy keys or data before the wipe. A phone that is powered off or seized before the wipe is triggered is not wiped.
- **Interruption.** Power loss mid-wipe leaves later steps undone until the next launch resumes them; keys go first to limit that window.

## Confidentiality and failure boundaries

A relay sees adjacent identities/capabilities, signed public endpoint hellos, record direction/size/timing, endpoint type/sequence/flags and its own local queue/drop information. Record timing and size remain traffic metadata.

A blind relay cannot open video geometry/FPS/rotation/audio headers, compressed VP9/AV1/Opus data, media timestamps, keyframe-request payload, wrapped group keys or group-sealed media. A normal viewer-forwarder can decrypt because it is an admitted local viewer; its forwarding branch still copies ciphertext unchanged.

Modified ciphertext/header metadata, replay, reordering, invalid signatures, wrong handshake domains and wrong recipient keys fail closed. Cryptographic identity does not establish human ownership. Full-fingerprint verification (above) is local and opt-in per contact; TOFU pinning of unverified peers, dynamic audience revocation/re-key, larger alternate-path proof and independent security audit remain open. Open/approval/verified audience modes would change admission, not remove hop/content encryption. Current primitives do not constitute independent protocol certification.
